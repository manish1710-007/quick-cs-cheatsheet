Code Review Fundamentals

What code review is, why it exists, and what makes it work

What is a code review?

A code review is a structured examination of a proposed change by someone other than its author, performed before the change is merged, with the goal of improving the quality of the code and of the system it joins. On modern platforms this usually means reviewing a Pull Request (GitHub/Bitbucket) or Merge Request (GitLab), but the practice is older than all of them. The reviewer’s job is not to find every problem — it is to apply independent judgment: does this change do what it claims, is it safe, will the next engineer be able to maintain it?

Why code reviews exist

  • Defect prevention and early detection. A bug caught at review costs minutes; the same bug in production costs an incident, a rollback and a postmortem. Reviews are cheapest quality gate that applies human judgment.
  • Knowledge sharing. At least two people understand every change. Reviewers learn parts of the system they don’t touch daily; authors get exposed to techniques and conventions they haven’t seen yet.
  • Consistency and shared ownership. Reviews spread conventions across the codebase so it reads like one system, not fifty personal styles. Over time this makes the code collectively owned rather than siloed.
  • Design pressure early. Knowing a change will be read by peers nudges authors toward clearer design before bad structure hardens.
  • Institutional memory. The review conversation documents why a decision was made, in context, attached to the code.

A short history

Formal code inspection was defined by Michael Fagan at IBM in 1976: a heavyweight, meeting-based process with defined roles (moderator, author, reader, recorder) and entry/exit criteria. Fagan’s inspections found that structured human examination caught 60–90% of defects in studied projects — far better than the ad-hoc reviews that preceded them. As teams grew and tools improved, the industry moved to lightweight, asynchronous, tool-based reviews: over-the-shoulder reviews, then email patch reviews (the Linux kernel still works this way via mailing lists), then dedicated tools like Gerrit (2008), then GitHub Pull Requests, which turned the branch-merge request into the default unit of review. What survived from Fagan is the core insight: an independent, prepared examiner finds defects the author cannot see.

!Common misconceptions
  • “The reviewer is a gatekeeper who must catch every bug.” No — the author owns correctness; the reviewer adds independent probability of detection. A review is a sample, not a proof.
  • “More comments = better review.” Comment count measures verbosity, not quality. One precise blocker beats twenty stylistic nitpicks.
  • “Senior code doesn’t need review.” Senior engineers introduce defects at lower rates but non-zero rates, and unreviewed code becomes unreviewable culture.
  • “Review is only about finding bugs.” The larger long-term return is maintainability, knowledge flow and design quality.

When code reviews become ineffective

  • Rubber-stamping — approval within minutes with no real reading, usually caused by oversized PRs or review quotas.
  • Giant diffs — beyond roughly 400–800 changed lines, defect detection rates fall off sharply and reviewers skim.
  • Style wars — energy spent on formatting that a formatter should settle automatically.
  • Week-long turnarounds — feedback that arrives after the author has mentally (or branch-wise) moved on loses most of its value.
  • Fear-based dynamics — if reviews are used to grade people, authors hide risk and reviewers soften findings; both destroy the signal.

Pull Request & Git Workflow Mastery

The complete Pull Request lifecycle, commit hygiene and merge strategies

What is a Pull Request?

A Pull Request (PR) is a proposal: “I have a branch with commits; please review and merge it into a target branch.” It bundles four things reviewers need: the diff (what changes), the commits (how the work evolved), the description (why it exists) and a conversation thread (where judgment happens). GitLab calls the same object a Merge Request — the difference is naming and minor workflow details, not substance.

branch→commits→push→open PR→CI→review→approve / request changes→merge→delete branch

Branching strategies

  • Feature branches — one branch per unit of work, short-lived (hours to a few days), merged into the mainline. The industry default and the basis of reviewable PRs.
  • GitHub flow — main is always deployable; branches merge back via PR with passing CI. Simple and effective for continuous delivery.
  • Git flow — main (releases) + develop (integration) + release/hotfix branches. Heavier; suits versioned, scheduled releases.
  • Trunk-based development — everyone merges to main frequently (multiple times a day), incomplete features hidden behind feature flags. PRs stay tiny by construction.

For review quality, the branching model matters less than one property: short-lived, focused branches. The longer a branch lives, the larger the eventual diff and the worse the review.

Commit hygiene: atomic commits

An atomic commit does exactly one thing and leaves the build green. Reviewers read commits to understand the shape of the work — a messy history forces them to review an undifferentiated blob.

bash — conventional commits
$ git log --oneline feature/loyalty-discount
a3f92c1 feat(orders): apply loyalty tier discount at checkout
b81e07d test(orders): cover discount boundary at tier threshold
7c2d4aa refactor(pricing): extract DiscountCalculator from OrderService

The Conventional Commits pattern type(scope): imperative summary makes history greppable and enables automated changelogs. Common types: feat, fix, refactor, test, docs, chore, perf.

Writing a reviewable PR description

Weak descriptionStrong description

“Fixed the discount bug and cleaned some stuff. Also updated config.”

No problem statement, no test notes, mixes three concerns, hides a config change inside “stuff”.

Why: Gold-tier customers received no discount at checkout (issue #482).
What: Adds DiscountCalculator, applies tier rates at order placement.
How verified: New unit tests for tier boundaries; ran the checkout flow on staging with a gold-tier account (screenshot).
Risk / rollout: Feature-flagged behind LOYALTY_V2; flag off by default.
Note for reviewers: Focus on rounding rules in DiscountCalculator — the controller changes are mechanical.

A strong description does half the review’s work before it starts: it tells reviewers where to look hardest, links the requirement so scope can be checked, and states how the change was verified. Attach screenshots for UI changes, API samples for contract changes, and migration notes for schema changes.

Draft PRs and review flow

  • Draft PR — open early to share direction and get design feedback before polishing. Reviewers comment but don’t block. Mark “ready for review” when done.
  • Requesting reviewers — choose people who know the area (CODEOWNERS can automate this). Two reviewers is usually the useful maximum; more creates diffusion of responsibility.
  • Approve / Request changes / Comment — GitHub and GitLab both distinguish these (GitLab’s “Approve” vs “Request changes” appetite is configurable; Bitbucket defaults to “needs work”). Their meaning is covered in the classification and methodology sections.
  • Resolving conversations — the author replies to every thread, then resolves it; disagreements get resolved with data or escalation, not silence. Re-review after updates focuses on the new commits.

Conflicts, updates and closure

  • Handling conflicts: the author rebases or merges main into the branch and pushes; reviewers re-examine only the conflict resolution, which is where subtle bugs hide.
  • Branch vs. incremental review: small PRs get one pass. Long-lived PRs should be reviewed per push — platforms show “changes since last review” (GitHub) or per-commit diffs; use them so the author gets feedback while context is fresh.
  • Abandonment: a PR that is no longer needed should be closed with a comment explaining why, not left to rot. Stale branches get deleted.

Understanding a Pull Request Before Reviewing

Purpose, scope and context first — individual lines last

Read the purpose before the code

The most common junior-reviewer mistake is opening the diff first. Lines of code only mean something relative to an intent. A method that looks wrong may be exactly what the requirement demands; a method that looks clean may solve the wrong problem entirely. Before looking at a single line, establish: what problem is this PR solving, and what would count as solved?

A systematic pre-review workflow

  1. Read the title and description. If the description can’t tell you what the change does and why, that itself is your first review comment.
  2. Open the linked issue / requirement / ticket. Acceptance criteria are your ground truth for scope and correctness.
  3. Skim the commit history. Commits tell the story of how the work evolved and often reveal uncertainty or rework worth asking about.
  4. Identify the change scope. Files touched, lines added/removed, new dependencies. Ask: is this the smallest reasonable shape for the goal?
  5. Locate the affected modules and their architecture context. Open the surrounding code, not just the diff. A diff without context is a Rorschach test.
  6. Identify dependencies and related PRs. Does this depend on a service/API change elsewhere? Are the contracts in sync?
  7. Compare base and feature branches. Confirm you are reviewing the intended diff (git diff main...feature — three dots), not accidentally re-reviewing main’s state.
  8. Trace one end-to-end execution path through the change mentally: request → entry point → logic → data → response/event. You now have a mental model to review against.
  9. Scan for unrelated changes and scope creep before diving deep, so you can request a split early instead of after an hour of review.

Spotting scope creep

A PR that claims to fix a discount bug has no business reformatting an entire file or renaming unrelated constants. Watch the diff for:

88+        if (customer.isGoldTier()) {
89+            return order.totalAfterDiscount(TEN_PERCENT);
90+        }
91+        // TODO cleanup: renamed helper, will refactor rest of file next week

The last three added lines are three separate problems: a TODO that plans future mixing, a debug log of full domain objects (potential sensitive-data leak, see Module 08), and a behavioral change for a different feature admitted in the comment. Each belongs in its own PR — request the split before reviewing the rest in depth.

Recognizing missing context

  • The PR touches an area with no linked requirement and no explanation of user impact.
  • The diff references symbols you can’t find — they may come from an unmerged dependency PR.
  • Config or infrastructure changes appear with no environment notes.
  • The tests reference behavior that the issue doesn’t mention.

When to ask the author instead of guessing

Asking a clarifying question early is cheap; a wrong assumption baked into an hour of detailed comments is expensive. Ask when: the stated goal and the implementation seem to disagree; you can’t determine whether a change is intentional; or the risk profile (data, security, money, availability) is unclear. Phrase questions as questions — QUESTION comments like: “The ticket says SMS notifications, but I only see email here — is SMS coming in a follow-up, or is this the full scope?”

Correctness & Logic Review

Finding defects in code that compiles, passes style checks and looks confident

The core skill: code that compiles is not code that works

Logic defects are invisible to compilers and linters because they are valid code expressing the wrong behavior. Your tools are: reading the requirement, enumerating inputs (including edge and failure cases), and tracing execution paths. This module trains the defect patterns that appear again and again in real PRs.

Off-by-one and boundary errors

Review technique: for every comparison, ask “what happens exactly at the boundary?” Thresholds, limits, empty collections, single-element collections, the first and last index, zero, negative values, maximum values. Then check whether the code’s behavior at that point matches the requirement’s wording — requirements love the words “at least”, “up to” and “within”, and each one pins a boundary.

Null handling and wrong assumptions

Java-specific trap: == on boxed Integer compares references. It works for values in the -128..127 cache range (so it passes small-number tests) and fails in production with larger values.

Missing return paths and silent fall-through

When reviewing a method that returns a value, enumerate the states the inputs can be in and confirm every one produces a defined outcome — including the states the author didn’t think about.

Incorrect exception handling and swallowed failures

For each try block ask: what states are possible after the catch? If execution continues, is continuing actually safe for this business operation? Money, inventory and access-control paths almost never are. (See Module 14 for the full observability treatment.)

Resource leaks

Review rule: every acquired resource (connection, stream, channel, lock, temp file) must have a visible owner and a guaranteed release path — try-with-resources in Java, with/try-finally in Python, using in C#, await using in TypeScript.

Race conditions and idempotency (preview)

Idempotency violations are logic bugs at system scale: a payment endpoint that charges again when the client retries, a consumer that double-processes a redelivered message, a POST that creates two rows for one logical action. Whenever a PR adds an operation that can be retried, ask: what happens if this runs twice?

Technique: tracing execution paths

  1. Pick a representative input and walk it line by line, writing down variable values.
  2. Repeat for a boundary input (empty, zero, max, exactly-at-threshold).
  3. Repeat for a failure input (null, absent record, downstream timeout).
  4. For state machines, draw the states and confirm only legal transitions are possible.
  5. For money and quantities, do the arithmetic yourself — especially rounding and currency mixing.

Boundaries tested at exact thresholds · every input state has a defined outcome · nulls and absent records fail with intent · catch blocks leave the system in a safe state · resources released on every path · shared state and retries considered · business rules (especially money and rounding) re-derived independently.

Readability, Naming & Clean Code Review

Evaluating whether the next engineer can maintain this code

Code is read far more often than it is written, usually under time pressure by someone who did not write it. Readability review asks one question: how quickly can a competent newcomer understand and safely change this? This module is the review-oriented companion to the Clean Code Mastery guide — here we focus on what to check in a diff, not on writing from scratch.

Before and after: the same logic, two reviewability levels

PricingService.java+18 -9
12-public double calc(double a, double b, int t) {
13-    double r = a - b;
14-    if (t == 1) { r = r * 0.85; } else if (t == 2) { r = r * 0.95; }
15-    if (r < 0) { r = 0; }
16-    return r;
17-}
12+/** Net amount after loyalty discount. Deducted amounts apply before tier rates. */
13+public BigDecimal netAmountAfterDiscount(BigDecimal grossAmount,
14+                                     BigDecimal deductedAmount,
15+                                     CustomerTier tier) {
16+    BigDecimal net = grossAmount.subtract(deductedAmount);
17+    BigDecimal rate = tier.discountRate();          // GOLD -> 0.85, SILVER -> 0.95
18+    BigDecimal discounted = net.multiply(rate);
19+    return discounted.max(BigDecimal.ZERO);
20+}

What changed and why each matters: names state the domain concepts (net amount, tier rate) instead of algebra (a, r, t); the magic numbers moved into the CustomerTier enum where they have meaning and one home; double became BigDecimal because money in binary floating point loses cents (a correctness issue hiding inside a readability rewrite — see Module 09); the clamping intent is now named (max(ZERO)). None of these required more code — only better words.

Naming review checklist

  • Variables name the concept they hold, not the type: retryDelay, not int2; eligibleCustomers, not list.
  • Methods say what they do: reserveInventory not handleInventory; predicates read as questions: isEligibleForDiscount. A method called getX that also caches, validates and publishes is lying.
  • Classes/Interfaces are nouns matching the domain vocabulary — the same concept should have the same name everywhere (pick “customer” or “client”, not both).
  • Encodings like strName, oOrder, I svc Hungarian leftovers add noise; modern IDEs know the types.
  • Gratuitous context: OrderOrderLineService inside an order package. Shorter is clearer when context is already established.

Comments: when they help and when they mask

Good comments explain why — the constraint, the workaround’s reason, the link to the incident: // Stripe requires the idempotency key to be stable across retries of the SAME logical payment. Comments that restate what the code does (// increment i) are noise; a comment needed to explain what is usually a naming failure. A comment like // this is tricky, don't touch without a reason is a defect in itself.

Overengineering and premature optimization

Readability review also protects against cleverness: speculative abstraction for a second use case that never comes, a hand-rolled cache in front of an operation that takes 2ms, generics gymnastics nobody on the team can read. If the abstraction has one caller and zero foreseeable seconds, suggest the simple version — YAGNI is a review principle, not just a slogan. Symmetrically: don’t demand patterns the codebase doesn’t use. Consistency beats theoretical purity.

!Preference vs. defect — the discipline
Before commenting on style, ask: “Can I point to a rule, a measurable cost, or a future failure mode?” If yes, it’s feedback with substance. If no — if it’s only taste — either skip it or mark it explicitly as a non-blocking NIT. Formatting disagreements belong to the formatter config, not the review.

SOLID Principles & Object-Oriented Design Review

Evaluating design in a diff — without turning reviews into pattern police

SOLID is a vocabulary for design pressure, not a checklist of mandatory patterns. In review, each principle answers a specific question about the change in front of you. Use them to explain risk, not to win arguments.

S — Single Responsibility

Question: does any one class change for more than one kind of reason? The violation signal in a diff is a class that now mixes domains — business rules and persistence and notification.

Fix direction: extract collaborators with single reasons to change (PricingService, OrderRepository, OrderNotifier), keep OrderService as the orchestrator. Review comment: “This class now owns pricing, persistence, email and audit — four change axes. Could we extract the notifier and repository now? The pricing extraction can come later if it’s too much for this PR.”

O — Open/Closed

Question: when the next variant arrives, does it require editing existing tested code? The smell is a growing switch on type that every new case must touch.

Balance: with two variants and no third in sight, the switch is fine. OCP earns its complexity at three-plus variants with independent evolution. Say which situation you believe you’re in, and why.

L — Liskov Substitution

Question: can the subclass stand in for its parent without surprises? Classic signals: a subtype that throws for inputs the parent accepted, narrows a postcondition, or requires stronger preconditions.

In real reviews the pattern appears as: an Optional-returning subclass of a null-returning parent, an Override that silently does nothing, or a “restricted” implementation that throws UnsupportedOperationException for half the interface (also an ISP violation).

I — Interface Segregation

Question: are implementers forced to carry methods they don’t use? Fat interfaces couple every consumer to every other consumer’s needs. Split ReportService (generate, email, archive, translate) into role-sized interfaces so a scheduler depends only on generate().

D — Dependency Inversion

Question: does high-level policy depend on low-level detail? In Spring terms: controllers and services should depend on interfaces (or Ports in hexagonal terms), with infrastructure (JPA repos, HTTP clients, Kafka producers) plugged in behind them. The test: can you unit-test OrderService without a database? If it news up PaymentApiClient internally, it can’t — ask for constructor injection.

Design review without dogma

  • Tie every design comment to a concrete future cost: “when we add refunds, this method must change too”, not “this violates OCP”.
  • Respect the codebase’s existing idiom; propose its next step, not the textbook end-state.
  • Separate “must fix now” (structural problems that harden if merged) from “next PR” (improvements that can safely follow).
  • When two defensible designs compete, prefer the one that is smaller and easier to reverse — and say that’s why.

Architecture & Maintainability Review

Reviewing changes beyond functions and classes: boundaries, direction, and slow debt

Architecture review = asking where new code lives and what it may touch

Function-level review asks “is this code correct?” Architecture review asks: “is this code in the right place, pointing at the right things?” Nearly all architectural decay arrives as reasonable-looking PRs: a quick direct query here, a shared constant there. Each is individually defensible; together they erase the boundaries that kept the system changeable.

The four questions of boundary review

  1. Dependency direction: does this change make business logic depend on infrastructure? (e.g. a domain class now imports org.springframework or javax.persistence directly — in hexagonal terms the ring arrows now point outward). Enforce with ArchUnit:
  1. Module boundaries: does the change reach into another module’s internals instead of its published API? A repository from another service’s package, a private table read directly, a common module growing domain types.
  2. Shared libraries: adding a type to a shared lib couples every consumer to that concept’s evolution. Shared code should be either genuinely generic (utilities) or duplicated on purpose (team autonomy).
  3. API boundaries: do internal refactorings leak into the external contract — a field rename that breaks clients, a new required parameter, an error format change? (Contract review detail in Module 10.)

Solving today’s problem, creating next year’s

Learn to recognize the PR shape: a small local improvement that crosses a boundary it shouldn’t. The famous case: an urgent report needs order data, so the Reporting service gets read access to the Orders database “just for SELECTs”. Six months later: reporting queries slow the order path, schema changes must now coordinate two teams, and nobody remembers why the rule existed. The review question is not “does it work?” but “what must change together in the future because of this line?”

Technical debt: introducing it consciously or not at all

Debt is sometimes rational — a tactical hack shipped before a deadline. The review requirement is that it be visible, bounded and owned:

  • Visible: a // TECH DEBT: comment naming the trade-off and trigger condition, plus a ticket link.
  • Bounded: the hack stays inside one module; it must not become the pattern successors copy.
  • Owned: a tracking issue exists with an owner and a review date. Debt without a ticket is just a defect with good PR.

Also review the other direction: a PR that adds extensibility nobody asked for (speculative hooks, config flags with one possible value) is debt with negative interest — every reader pays for flexibility that never cashes out.

Migration complexity and backward compatibility

Architectural changes usually arrive as multi-step migrations. Review that the plan covers: both shapes coexisting during transition, compatibility shims with a removal date, data backfill, and a rollback story. A PR that only implements step one is fine — if the description names the other steps. See Module 11 for the data side and Module 17 for large refactors.

Security-Focused Code Review

Finding vulnerabilities before they ship — aligned with the OWASP Top 10

Security review is correctness review for an adversary: assume every input is hostile, every secret is targetable, and every error message is intelligence. The patterns below map to the OWASP Top 10 and the OWASP Code Review Guide; each includes what to look for in a diff and the remediation to request.

Injection: SQL, OS, LDAP

Also flag: dynamically built ORDER BY/LIMIT from request params (can’t be bound as values — validate against a whitelist), Runtime.exec with concatenated input, string-built SPARQL/LDAP, and native queries with + in JPA @Query.

Broken access control and IDOR

The most common serious web vulnerability: the endpoint authenticates the user but never checks authorization on the specific object.

Review rule: every endpoint that touches an object by id must show an ownership or authority check in the diff, not “the UI only shows the user their own orders”. Check horizontal (same role, other user’s data) and vertical (regular user hitting admin routes) dimensions. Mass assignment is the sibling bug: @RequestBody User binding a client-supplied role or balance field — use DTOs with exactly the fields the action needs.

XSS, CSRF, SSRF

  • XSS (A03): any path where user input reaches HTML unescaped, innerHTML with interpolated data in JS/TS, or th:utext (unescaped!) in Thymeleaf vs th:text. Fix: context-aware output encoding; treat rich text with a sanitizer allowlist.
  • CSRF (A01): state-changing endpoints behind cookie sessions need CSRF tokens; JSON+JWT APIs with no cookie auth are typically exempt — but say which you verified rather than assuming.
  • SSRF (A10): features that fetch a user-supplied URL (webhooks, “import from URL”, avatar-by-URL). Validate scheme/host against an allowlist, block link-local/metadata addresses (169.254.169.254 and friends), disable redirects or re-validate after them.

Secrets, credentials and sensitive data

A committed secret is rotated, not deleted — history keeps it. Related checks: log statements that print tokens, passwords, full card numbers or PII (log.debug("request={}", request) on an object with password fields); stack traces returned to clients; equals()-based password comparison instead of constant-time hashes (BCryptPasswordEncoder.matches in Spring); and crypto choices — MessageDigest MD5 for passwords, Random instead of SecureRandom for tokens, ECB mode, home-rolled ciphers.

Deserialization, file uploads, path traversal

  • Insecure deserialization (A08): ObjectInputStream.readObject on untrusted bytes, or @JsonTypeInfo(use = Id.CLASS) (Jackson polymorphic typing by class name) on public endpoints — both are remote-code-execution classes of risk. Accept only allowlisted types.
  • File uploads: validate content by parsing (magic bytes), not by extension or Content-Type; enforce size limits; store outside the webroot; generate server-side names; scan if the platform offers it.
  • Path traversal: new File(baseDir, userInput) with ../../etc/passwd. Canonicalize, then verify the result starts with the intended base directory; prefer opaque identifiers (store the real path server-side).

Dependency vulnerabilities and error disclosure

  • A06 Vulnerable Components: a new dependency in the diff gets a quick CVE check (Dependabot/OWASP Dependency-Check automate this — see Module 18). Also check: is it maintained, what does it transitively pull in, and is the license compatible (see Module 15)?
  • Improper error disclosure: a 500 response containing a stack trace, SQL, or internal hostnames is free reconnaissance. Log the detail server-side with a correlation id; return a generic error plus that id.
  • Session/authn weaknesses: predictable tokens, missing expiry, logout that doesn’t invalidate server-side state, password reset tokens that are single-use and time-limited (see the case study in Module 19).

Performance & Resource Management Review

Real bottlenecks, resource discipline, and refusing speculative optimization

Two kinds of performance feedback

Structural problems have a known complexity shape (N+1 queries, unbounded result sets, locks held over network calls) and can be identified by reading the code — they belong in review. Micro-optimizations (string concat vs builder, one extra allocation) are usually noise until a profile says otherwise — they don’t. The reviewer’s discipline is knowing which one they’re commenting on, and saying so.

The N+1 query problem

The single most common backend performance defect in review. Symptom in logs: one query for the list, then one query per row.

Review trigger phrases: lazy relations accessed inside loops, findById in a stream map(), hasMany collections iterated after a query. In the logs, enable Hibernate’s hibernate.generate_statistics or p6spy in dev to count statements.

Unbounded work and missing indexes

Compound-index rule of thumb: equality columns first, range/sort columns after; match the query’s shape. Every new WHERE/ORDER BY on large tables deserves an “is there an index?” question (see Module 11).

Resource and concurrency discipline

  • Blocking calls in virtual/request threads: synchronous HTTP or JDBC calls inside event loops or @Async reactive chains starve the whole executor.
  • Thread pool sizing: new Executors.newFixedThreadPool(50) without a reason; pools without named threads (un-nameable in thread dumps = undebuggable in production) or without rejection policies.
  • Memory leaks: static/singleton collections that only grow (caches without eviction, listener registries never unregistered), ThreadLocal never removed in thread pools.
  • Connection management: HTTP clients created per-request instead of pooled/reused; timeouts missing — an unset read timeout is an outage waiting for a slow dependency.
  • Payload discipline: returning entire aggregates where a list view needs five fields; missing pagination on list endpoints; SELECT * equivalent in JPA (fetching entities for projections).

Cache misuse — both directions

And the reverse sin: unnecessary caching. Caching a lookup that takes 400µs adds invalidation bugs, stale reads and operational surface for no measurable gain. The justification for a cache is a measured cost, not a feeling.

Distinguishing real from speculative findings

Comment typeLooks likeVerdict
Structural + load-independent“This endpoint does one query per element in a loop — it’s O(N) round trips at any N”Actionable now
Structural + scale-dependent“findAll() is fine at 10k rows, fatal at 10M — can we paginate now while it’s cheap?”Actionable, with reasoning
Predicted hotspot“This regex might be slow under load” (no measurement, no workload)Speculative — needs a benchmark first
Micro-optimization“Use StringBuilder here” in non-hot codeSkip or NIT

When you flag something scale-dependent, state the threshold where it bites and propose the cheap fix now if the threshold is plausible within months. Numbers you can’t source should be framed as estimates (“order of magnitude”), not facts.

Clients retry: mobile networks drop, users double-tap, queues redeliver. POST endpoints that create resources or move money need idempotency keys.

Test the review question: “what happens if the client sends this request twice?” — for payments, orders, emails and webhooks the answer must be “the same as once”.

  • Self-invocation trap: a this.method() call inside the same bean bypasses the Spring proxy — the @Transactional annotation silently does nothing. A classic “compiles, looks right, isn’t”.
  • Read-only marking: query methods with @Transactional(readOnly = true) help drivers and replication route sensibly.

API documentation review

If the project uses OpenAPI/Swagger, the contract file is part of the diff: new fields documented, examples updated, deprecated fields marked with sunset guidance. Documentation that drifts from the code is worse than none — reviewers are the drift alarm.

Concurrency & Distributed Systems Review

Why a five-line change can take down production at 3 a.m.

Distributed defects hide because every component passes its own tests. The failure needs two things at once: a redelivered message, a slow dependency, a rebalance, a retry. Review is the only stage where the interaction is visible before production writes the test for you.

Thread safety fundamentals

  • Check-then-act races: the gap between testing a condition and acting on it. Fix by making the test-and-act atomic (conditional SQL update, ConcurrentHashMap.compute, lock, or optimistic version).
  • Shared mutable state in singleton beans (Spring default!): any mutable field on a @Service is shared across all requests. Mutable request state belongs in method scope or in a store.
  • Double-checked locking without volatile is broken; prefer holder idiom or eager init. Flag hand-rolled singletons in a Spring app entirely.
  • Thread pools: sized with a reason, threads named, rejection policy chosen (see Module 09); @Async methods returning void swallow exceptions by default — check the configured handler.

The atomic conditional update (the workhorse fix)

The database serializes the check and the write in one statement; no Java-side lock, no race window. This pattern resolves a large share of real-world race-condition review findings.

The idempotent consumer is the pattern that makes at-least-once safe: a processed-message table keyed by (topic/queue, message id) or a natural business key (orderId), checked before processing, written in the same transaction as the business effect.

Dual writes and the transactional outbox

Review trigger: any code that writes to a database and publishes/sends within one request, without an outbox or an equivalent (saga compensation, event store). Ask: what does the system look like if exactly one of these two writes succeeds?

Retries, timeouts, circuit breakers

  • Timeouts everywhere: every outbound HTTP/JDBC/Redis/broker call. An unset timeout converts a slow dependency into a thread-pool outage.
  • Retries with backoff + jitter, and only for operations that are idempotent or carry idempotency keys; cap attempts; distinguish retryable (timeout, 503) from fatal (400, 401) errors.
  • Circuit breakers (Resilience4j) for dependencies that fail repeatedly: fail fast, recover gradually. Review the thresholds and the fallback — a fallback that silently returns empty data can be worse than an error.
  • Eventual consistency surfaced: if the system now answers “created” before downstream state exists, do clients and UI handle the lag? APIs should expose status rather than promise synchronous completion.

Sagas and distributed transactions

When a flow spans services (order → payment → inventory → shipping), review the compensation story for every step: what reverses it, how partial failures surface, and whether the saga’s state is queryable (“where is my order stuck?”). A saga without compensations isn’t a saga, it’s a gambit.

!Why small changes break big systems
A one-line change from “auto-commit offsets” to “commit before processing” silently drops messages on crash. Moving a kafka.send two lines earlier or later creates or destroys a dual-write bug. Adding a second consumer to a queue breaks an ordering assumption. In distributed code, position, ordering and failure-timing are the semantics — review them like logic, not style.

Testing & Test Quality Review

Evaluating the tests a PR brings — and catching tests that pass without proving anything

Tests in a PR are the author’s evidence. Review them as evidence: do they fail if the behavior breaks? That single question exposes most test sins. This module is the review-oriented companion to the Software Testing Patterns guide.

Tests that pass without verifying

The reviewer’s test for tests: mutate the production code mentally (break the rounding, invert the condition) and confirm at least one test turns red. Tools like PIT (mutation testing) automate exactly this — recommend it when a critical module’s coverage number looks suspiciously healthy.

What good tests look like

  • Naming states behavior and scenario: goldTierAtThreshold_getsTenPercent, not test1 or testCalc.
  • Structure reads as arrange / act / assert with one logical assertion group.
  • Boundaries get tests on both sides of every threshold (see Module 04).
  • Negative tests exist: bad input, absent records, failing dependencies — most production bugs live in the unhappy paths.
  • Regression tests accompany bug fixes: “fix + test that reproduces the bug” is the package to require; a fix without its test invites the bug back.

Integration / slice (@DataJpaTest, @WebMvcTest)Queries, mappings, validation, JSON contractsPresent for new queries/endpoints — JPA queries notoriously lie in pure unit tests

Flakiness review

A flaky test is worse than no test: it trains the team to ignore red. Flag these on sight:

  • Thread.sleep(...) to wait for async work — use Awaitility or latches/counters with timeout.
  • Wall-clock reads (LocalDate.now()) without an injected Clock — midnight and month-end become lottery days.
  • Order dependence: tests sharing mutable fixtures or relying on execution order.
  • Random data without seeds (RandomStringUtils collisions); parallel runners sharing one database namespace.
  • Assertions on floating-point equality without tolerance; on map/set iteration order; on timestamps without zones.

Mocking practices

  • Mock at architectural boundaries (ports, gateways, clocks), not at every class. Deep mocking chains (mock(A.class) returning mocks returning mocks) signal the code is too coupled to test.
  • verify sparingly — interaction assertions make tests brittle to refactoring. Prefer state/outcome assertions.
  • Never mock what you don’t own when a real test double exists: use WireMock for HTTP, Testcontainers for real brokers/DBs when the test’s value depends on their behavior.
  • Arguing with argument captors is a smell; if you need to inspect that deeply, test the collaborator directly.

Coverage numbers in review

Coverage is a smoke detector, not a goal: 100% with assertion-free tests proves nothing; 70% with sharp behavioral tests is healthy. Use uncovered diff lines as a question generator (“why is the retry path untested?”), never as a merge gate by itself. Mutation score (PIT) is the honest cousin of coverage — it measures whether tests can catch changes.

Error Handling, Logging & Observability Review

Will this change be diagnosable at 3 a.m.?

The observability review question

Every diff changes the set of things that can fail. The review question: when this fails in production, what evidence will exist, and how fast will it point at the cause? If the honest answer is “a user complaint”, the change isn’t done.

Exception design

  • Catch specificity: catch (Exception e) grabs everything including OutOfMemoryError-adjacent surprises and NPEs that indicate bugs. Catch the narrowest useful type.
  • Wrap, don’t erase: rethrowing must keep the cause: new OrderImportException("file " + name, e) — a dropped cause destroys the diagnostic trail.
  • Cause chain at the boundary: log the full chain server-side; return a correlation id to the client (see Module 08).
  • Exceptions are not control flow for expected business outcomes — “item not found” as an exception in a hot loop is slow and noisy; use Optional/result types where idiomatic.

Log levels and content

  • Parameterized logging, never concatenation: log.info("order {} confirmed", orderId) — string building is skipped when the level is off.
  • No secrets or PII in logs (see Module 08): tokens, passwords, card numbers, full addresses. Log ids, not payloads.
  • No log-and-swallow: catch (e) { log.error(...) } then continue as if fine — decide: handle it, propagate it, or degrade explicitly with a comment saying why continuing is safe.
  • Structured logging (JSON with fields: event, orderId, customerId, durationMs) makes logs queryable; string soup does not.

Correlation IDs and tracing

Review checkpoints: new endpoints/menus of execution get the correlation id automatically (MDC via filter/interceptor); outbound calls propagate it (headers on RestTemplate/WebClient/Kafka records); background jobs have their own trace id in logs; MDC.clear() in finally or you’ll cross-contaminate requests on pooled threads.

Metrics, health checks, alerts

  • Business metrics for new flows: counters (orders_created_total), timers (payment_authorize_duration) with outcome labels (status="declined|approved|error") — not just JVM stats.
  • Health checks reflect real dependencies: a new critical dependency (Redis, downstream API) belongs in the readiness probe; but a flaky dependency in a liveness probe causes restart storms — review which probe it joined.
  • Alerting on symptoms with actionability: error rate on the new endpoint, DLQ depth for the new consumer, saturation of the new pool. An alert nobody can act on is noise that hides real pages.
  • Failure diagnosis dry-run: walk through “this feature is broken in prod” — which log line, metric or trace would you check first? If the answer is “none exists”, that’s the finding.

  • Secrets via environment / vault, never in the repo (see Module 08): ${DB_PASSWORD} placeholders with defaults only for local dev that are obviously fake (localdev-only).
  • Every environment difference explicit: the PR that adds a config key must show values for dev/staging/prod or state that defaults apply everywhere. “Works on my machine” config is a deploy-day discovery.
  • Fail fast on bad config: startup validation (@ConfigurationProperties + @Validated) instead of a cryptic NPE at 2 a.m. when the value is missing.
  • Feature flags: new risky behavior behind a flag with a stated default; flags have owners and removal dates (a flag older than two quarters is permanent config pretending to be temporary); the PR shows the flag’s off-state is safe.
  • Time zones and locales: new config that assumes server-local time (TimeZone.getDefault()) vs UTC; cron expressions with zones stated.

Build reproducibility

  • Pinned action/plugin versions in CI (not @v-floating or latest), so Tuesday’s build equals Monday’s.
  • Dependency verification or lockfiles committed — the diff that touches dependencies must touch the lockfile in the same commit.
  • No network at test time for hermetic builds (or consciously accepted and documented).

Reviewing docs effectively (in order of value)

  1. Accuracy first: do the documented endpoint, flag, default and example match the code in this diff? Drift between docs and code is worse than absence — it’s confidently wrong.
  2. Runnable second: can a new joiner copy-paste the setup steps and succeed? A README with unstated prerequisites (Java 21, Docker, a running Postgres) fails on the first try.
  3. Findability third: is the doc where people will look (linked from the code / README index), not in a forgotten wiki page?
  4. Style last: typos and phrasing are NITs; don’t spend review capital on them unless they create ambiguity.

Javadoc that earns its lines

Review rule: Javadoc is required on public library/domain APIs where behavior isn’t obvious from names — contracts, units, nullability, thread-safety, exceptions. Private helpers with clear names don’t need ceremonies.

ADRs: decisions with a paper trail

When a PR makes a decision people will ask “why?” about in a year — technology choice, pattern adoption, boundary change — the ADR is the artifact to request. It’s five minutes now versus archaeology later.

Changelog and migration guides

  • Changelog entries written for users, not committers: what changed for them, in the format the project uses (Keep a Changelog style: Added / Changed / Fixed / Removed). Conventional commits can generate this mechanically.
  • Migration guides for breaking changes: exact steps, code snippets before/after, and the version boundary. If the PR breaks an integration, the guide is the difference between an upgrade and an outage.
  • Doc-only PRs are real PRs: review for accuracy like code, and thank the author — doc work is chronically under-credited.

Reviewing Legacy Code & Large Changes

Strategies for 3,000-line diffs, old systems, and risky refactors

First, a decision: review it, split it, or pair on it

Review quality decays with diff size — past a few hundred lines, defect detection drops sharply. Faced with a giant PR, a reviewer has three honest moves, and picking one explicitly is the job:

  1. Split request (default): most large PRs are separable — by layer, by module, or into “mechanical prep” + “behavior change”. Offer to help find the seams; “I think this is three PRs” lands better than “too big”.
  2. Structured review (when truly atomic): review in passes — pass 1 commits and shape, pass 2 architecture, pass 3 line-by-line — and say you did, so the author knows the coverage.
  3. Pair/sync review (highest risk: money, auth, migration): a shared screen beats a wall of diff comments for both speed and quality.

Refactor PRs: behavior preservation is the claim under test

  • One kind of change per PR: refactoring mixed with behavior changes makes both unreviewable — the reviewer can’t tell an intentional difference from a mistake. Require the split even when it’s inconvenient (git makes it cheap: stage by hunk).
  • Ask for characterization tests first: before touching fuzzy legacy logic, add tests that pin current behavior (even if current behavior is weird — especially then). The refactor then becomes verifiable: same tests, green, different code.
  • Mechanical vs. semantic: IDE-driven renames/moves are reviewable by spot-checking; hand-written logic changes need full attention. Label which is which in the description so reviewers can calibrate.
  • Strangler pattern for big migrations: new path alongside old, traffic switched gradually (flag or routing), old path removed only after a soak period. The PR should show the switch and name the removal milestone.

High-risk changes: the extra review pass

Risk typeExtra checks to demand
Database migrationsRollback statement, lock analysis, batch sizes, rehearsed on prod-size data (see Module 11)
Auth/payments/inventorySecond reviewer with domain ownership; adversarial test cases; audit trail for the decisions
Public contract changeContract tests, consumer sign-off, versioning/transition plan (see Module 10)
Infra/configDry-run output pasted in PR, blast radius stated, one-change-at-a-time deploys
Concurrency changesStress/load test evidence, invariant explanation (see Module 12)

Reviewing unfamiliar systems

  1. Read the tests first — they document intended behavior better than any README.
  2. Use git archaeology: git log -p <file> and git blame answer “why is it like this?” and reveal which constraints are load-bearing. Code that looks wrong but has a defensive history deserves a question, not a verdict.
  3. Ask the adjacent owner — every legacy module has someone who last bled on it; CC them rather than guessing.
  4. Scope your approval: “LGTM on the new logic; I could not verify the interaction with the settlement batch job — @settlement-team please sanity-check” is a professional, honest review. Rubber-stamping what you didn’t read is worse than admitting limits.

Improving legacy code without demanding rewrites

The “rewrite it all” review comment is how reviewers burn trust and PRs stall forever. The sustainable posture is campsite rules: every change leaves the touched area a little cleaner (extract one method, delete one dead branch, add one characterization test), tracked so it compounds. Request rewrite-scale proposals as RFCs/design docs — a separate conversation with different stakes than this PR.

iRollback is a first-class review topic
For any risky PR, the reviewer should be able to answer: how do we turn this off? Feature flag, config, redeploy of previous image, migration reversal? If nobody in the review conversation knows, that’s a finding before any code comment.

Advanced Review Judgment & Engineering Culture

Making good calls when there is no universally correct answer

Bugs, preferences, and the space between

Every review comment falls somewhere on a spectrum: defect (breaks correctness, security, or a stated requirement), risk (works today, likely to fail under change or load), improvement (clearly better, not urgent), preference (taste). The senior skill is knowing which one you’re holding before you speak, because the merge posture flows from the category: defects block; risks block on critical paths and get tickets elsewhere; improvements and preferences are non-blocking by default. Mislabeling a preference as a defect is how reviewers acquire reputations; mislabeling a defect as a preference is how systems acquire outages.

The nitpicking discipline

  • Prefix optional points with “nit:” or “non-blocking:” and mean it — an “optional” comment the author feels compelled to satisfy isn’t optional.
  • Batch nits: one comment listing five small points reads as helpful; five separate comment threads reads as an audit.
  • Ask what a comment costs: if the author spends 30 minutes to satisfy it, what does the codebase gain? If you can’t answer, delete the comment.
  • Praise precisely. “Nice catch on the boundary case here” teaches the team what good looks like — generic “LGTM” teaches nothing.

Perfection vs. delivery: the risk/reversibility frame

Google’s engineering guidance frames it well: a CL (change list) is approvable when it improves the codebase’s health — not when it’s flawless. Combine two dials:

Reversible (feature-flagged, small, easy rollback)Irreversible (migrations, public contracts, money)
Low blast radiusApprove with follow-ups; velocity winsApprove after targeted checks; note residual risk
High blast radiusOne focused pass on the risky paths, then ship with monitoringSecond reviewer, adversarial tests, staged rollout — hold the line

“It’s not perfect” is a reason to comment; it is rarely a reason to block. “It’s not safe” always is. Keeping that distinction crisp is most of the judgment.

Technical disagreements: escalation without casualties

  1. Ground it in something checkable: a spec, a measurement, a reproducer, a style guide rule. “I think X is faster” becomes “here’s a JMH run”.
  2. State the stakes and the reversibility: “I’ll defer on naming; I won’t defer on the transaction boundary because it’s a money path.”
  3. Take it out of the PR: long threads move to a design doc / meeting / RFC with written conclusions, then a short pointer lands in the PR.
  4. Designate an arbiter (tech lead / architect) before frustration sets in — and disagree with the arbiter’s call by writing the concern down, then committing. Disagree and commit keeps velocity without silencing anyone.
  5. Never relitigate silently: accepting feedback while planning to revert it after merge is a trust-destroyer; say “I’ll do this now and propose X next sprint” instead.

Reviewing up, reviewing out

  • Senior authors: apply the same bar, softer tone isn’t required — respect is. Senior engineers get rusty code too, and unreviewed senior code is how “genius systems” that nobody else can change get built.
  • Unfamiliar tech: review what transfers (invariants, boundaries, error paths, test honesty), ask genuine questions, and label your confidence. “I can’t assess the Rust borrow-checker subtleties, but the retry logic has no backoff” is a complete, useful review.
  • Receiving feedback: the author’s skills mirror the reviewer’s — assume the comment is about the code, not you; answer every thread; push back with reasons when the comment is wrong (reviewers are wrong regularly, and good ones like being corrected); thank people for finding what you missed.

Psychological safety and review culture

Review is where engineering culture is most visible, because it’s structured criticism under time pressure. The norms that keep it healthy:

  • Critique code, never people: “this method has three responsibilities” not “you always write god classes”. Even jokingly, the second changes what people bring to review.
  • Assume competence and good intent: the question “what am I missing that made this seem right?” converts gotchas into learning, and regularly finds the reviewer was missing context.
  • Turnaround is respect: a same-day first response (even “queued for tomorrow morning”) is the single biggest driver of healthy PR flow. Teams that let PRs sit for days teach authors to batch giant PRs to avoid the wait — a doom loop.
  • Reviewer accountability: your approval is your signature; “I skimmed it” approvals are worse than slow reviews because they fake the safety the process promises.
  • Blameless postmortems close the loop: when a reviewed change still fails in production, the question is “what would have caught this, and where should that check live?” — a test, a gate, a checklist item — not “who approved it?”

Building the culture: the compounding assets

  1. A written review standard (what blocks, what doesn’t; turnaround expectations) — argument-ending and onboarding-accelerating.
  2. Style automation so humans never argue about commas again.
  3. Small-PR norms celebrated in practice, not just in slides.
  4. Review rotations so knowledge spreads beyond the two people who “know that service”.
  5. Retrospectives on the review process itself twice a year — the checklist that made sense at 10 engineers is strangling at 40.

Professional Review Methodology

A repeatable nine-step workflow from opening the PR to making the call

Consistency is what makes reviews repeatable across reviewers and calm under deadline pressure. The workflow below front-loads understanding, works from global properties to local detail, and ends with a deliberate decision. Steps 1–3 come from Module 03; the rest sequence the deep review.

  1. Understand the change. Title, description, linked issue, acceptance criteria, affected components. If you can’t state the problem being solved in one sentence, stop and ask.
  2. Evaluate scope. Files added/removed/modified; unrelated changes present; dependencies introduced; PR appropriately sized or splittable. Request splits now, before deep review.
  3. Review correctness. Business rules validated against the requirement; edge and failure cases; state transitions; incorrect assumptions. Trace at least one execution path end to end (Module 04).
  4. Review design and maintainability. Naming, responsibilities, abstractions, duplication, dependency direction, technical debt introduced (Modules 05–07).
  5. Review security and performance. Access control on new surfaces, input validation, sensitive data handling; N+1s, unbounded reads, resource management (Modules 08–09).
  6. Review testing. Tests exist, assert real behavior, cover positive/negative/boundary cases, aren’t flaky by construction; bug fixes carry reproducing tests (Module 13).
  7. Review documentation and compatibility. Contracts, migrations, config changes, docs updated; deployment and rollback story coherent (Modules 10–11, 15–16).
  8. Write constructive feedback. Identify the issue, explain the impact, suggest a solution; separate must-fix from optional; keep the tone about the code (Comment Workshop).
  9. Make the decision. Approve / approve with non-blocking suggestions / request changes / comment only / escalate / ask for clarification — chosen deliberately, not by exhaustion.

Comment Classification System

Seven severity labels that keep reviews honest about risk

A shared severity vocabulary does three jobs: it tells the author what must change before merge, tells the team what the review found without reading every thread, and keeps the reviewer honest — labels force you to commit to how bad a finding actually is. Severity reflects risk and impact, never personal preference or how much the style annoys you.

BLOCKERCannot merge

Critical issue that makes merging unsafe: exploitable vulnerability, data loss, auth bypass, broken build in a path CI can’t see, or a migration that can’t be rolled back.

Example comment: “[BLOCKER] This endpoint has no ownership check — any authenticated user can read any order by id (verified: GET /api/orders/1042 with a different account returns the full record). We need findByIdAndCustomerId (or equivalent) before this merges. Happy to pair on the fix.”

HIGHMust fix in this PR

Serious correctness, security or reliability issue that will produce production failures: N+1 on a hot path, missing timeouts on a critical integration, race on shared state, swallowed exceptions on a money path.

Example comment: “[HIGH] The charge is inside the try, but the catch only logs — the order continues as paid even when the gateway declines. Can we rethrow and transition to PAYMENT_FAILED instead? As written, every gateway outage becomes free merchandise.”

MEDIUMShould fix — this PR or a linked ticket

Meaningful maintainability or functionality concern: duplicated logic that will diverge, missing validation on an internal endpoint, error responses without correlation ids, tests that assert nothing.

Example comment: “[MEDIUM] These two blocks re-implement tier lookup — the second copy has already drifted (no BRONZE case). Could we extract TierDiscount::forCustomer? If it’s too much for this PR, a follow-up ticket works, but the duplication shouldn’t multiply.”

LOWWorth considering, not required

Minor improvement: a clearer name, a missing Javadoc contract on a public method, a magic number that deserves a constant, an index that would help an existing query.

Example comment: “[LOW] process2() is doing the refund path now — processRefund() would read better at the call sites. Totally your call.”

NITCosmetic, optional, zero pressure

Style polish: line length, import order, a typo in a message. Batch them, mark them clearly, expect nothing.

Example comment: “nit: trailing whitespace on lines 40–42. The formatter would catch this — maybe we enable spotlessCheck in CI? (separate PR if you like)”

QUESTIONUnderstanding before judging

Clarification requests: intentionality of a behavior, missing context, a constraint you can’t see. Questions are findings — “I couldn’t verify X” is legitimate review output.

Example comment: “[QUESTION] The retry loop skips index 0 on the first pass — intentional (first attempt is the original call) or off-by-one? If intentional, a comment here would save the next reader.”

PRAISEReinforce what good looks like

Highlighting excellent decisions: a boundary test nobody asked for, a clever simplification, a dangerous edge case handled. Precise praise teaches the team more than generic LGTMs.

Example comment: “[PRAISE] Covering both sides of the tier threshold is exactly the test this module needed — the last two bugs here were boundary misses. Thank you.”

Mapping labels to merge posture

Finding mix in the PRDecision
Any BLOCKERRequest changes — full stop, whatever else is present
HIGH findingsRequest changes, scoped to the fixes needed
MEDIUM onlyJudgment call: fix now if cheap; approve with linked tickets when the change is urgent and the risk is bounded
LOW / NIT / QUESTION onlyApprove with suggestions; questions answered inline before merge
PRAISE-worthy work, clean otherwiseApprove fast — and say what was good

Must fix · should fix · could improve

For teams that prefer plain language: must fix = BLOCKER + HIGH (no merge without them); should fix = MEDIUM (merge reluctantly acceptable with a ticket); could improve = LOW + NIT (never blocks); informational = QUESTION + PRAISE (context, no action). Use whichever vocabulary your team standardizes — use it consistently. The system that works is the one everyone can predict.

!Calibration failures to avoid
  • Severity inflation: marking a naming gripe HIGH because you feel strongly. Inflated labels make real HIGHs invisible — crying wolf with metadata.
  • Severity deflation: downgrading a real vulnerability because the author is senior or the deadline is close. Deadlines don’t negotiate with attackers.
  • Everything-is-a-blocker reviewing: if all comments are mandatory, authors stop trusting the labels and start negotiating every thread.
  • Unlabeled severity: making the author guess which comments matter. Label everything; let the labels mean things.

You reviewed only part of the changeComment only, naming what you covered and what you didn’t
Stakes exceed your confident judgmentEscalate to a domain owner, while still giving your partial review
Purpose/scope still unclear after readingAsk for clarification before the deep pass — cheap now, expensive later

Common review mistakes (and their antidotes)

  1. Opening the diff before the description → Module 03 workflow.
  2. Rubber-stamping under time pressure → say “queued for tomorrow 9am” instead of faking approval.
  3. Nitpick avalanches → batch nits, label severities, praise precisely.
  4. Reviewing the code you would have written → review the code that’s there against its actual requirements.
  5. Vague comments (“this is bad”) → issue + impact + suggestion, always.
  6. Blocking on taste → defect/risk/improvement/preference categories from Module 20.
  7. Ignoring tests in the PR → tests are evidence; audit their assertions.
  8. Silent partial reviews → scope your approval honestly.
  9. Winning arguments instead of improving code → evidence, arbiter, disagree-and-commit.
  10. Forgetting the rollback question → “how do we turn this off?” on every risky PR.
