Introduction to Rust

Philosophy, design goals, and an honest map of where Rust fits

What Rust is

Rust is a systems programming language that guarantees memory safety and thread safety without a garbage collector, while compiling to native machine code with performance in the same class as C and C++. It began as a personal project of Graydon Hoare at Mozilla around 2006, was sponsored by Mozilla, and reached its 1.0 release in 2015 after several years of deliberate language redesign. Today it is maintained by the Rust Foundation and used in production by infrastructure teams across the industry — operating system components, browsers, cloud platforms, databases, command-line tooling and embedded firmware.

The defining idea: instead of checking memory safety at runtime (garbage collection, reference counting everywhere, or blind trust in the programmer), Rust checks it at compile time through the ownership model. Programs that could dereference freed memory, iterate a collection while mutating it, or share data across threads unsafely are rejected before they ever run.

“Zero-cost abstraction” is Bjarne Stroustrup’s phrasing that Rust adopts: what you don’t use, you don’t pay for; what you do use, you couldn’t hand-code any better. A chain of iterator adapters in Rust compiles to a tight loop — no closures allocated, no dynamic dispatch, no iterator objects at runtime (Module 20 shows you how to verify this yourself).

Where Rust is used — and when to choose it

Strong fits: command-line tools (fast startup, single static binary); systems components and OS kernels where C would historically be required; performance-sensitive library code invoked from other languages; network services where tail latency and predictable memory matter; embedded targets without room for a GC; WebAssembly modules; security-critical parsing of untrusted input.

Weak fits: rapid prototypes where iteration speed beats correctness; thin glue scripts (a shell or Python script wins); teams with no systems experience and hard deadlines before training; domains dominated by mature ecosystems in another language where rewriting buys little. Choosing Rust for a weekend internal tool can be excellent practice and poor economics — know which goal you are serving.

iAdoption snapshot
Rust has been used in production by Mozilla (Firefox components), Microsoft (Windows kernel components), AWS (Firecracker), Cloudflare, Discord (rewrote a Go service for latency stability), Dropbox (storage sync engine), and the Linux kernel (accepting Rust drivers since 6.1). The pattern is consistent: Rust is chosen where memory-related defects, latency variance or CPU cost of the previous implementation hurt enough to justify a rewrite.

Strengths and limitations, honestly

  • Limitations: compile times on large projects; the ownership learning curve; some domains (GUI, some ML) still maturing; unsafe still needed for some low-level work; async ecosystem, while strong, carries historical complexity (Module 15–16 prepare you for exactly this).

Complete Linux setup walkthrough

  1. Install rustup and the stable toolchain. Fetch and run the official installer, then start a fresh shell so ~/.cargo/bin is on your PATH: curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh (the script explains every step; the default profile is correct for most developers).
  2. Verify the install with the version commands below — all three must print versions, not “command not found”.
  3. Install your editor support: VS Code with the rust-analyzer extension, or IntelliJ IDEA with the Rust plugin. Both give inline compiler diagnostics, which you will want while learning the borrow checker.
  4. Create and run a first project: cargo new hello_rust && cd hello_rust && cargo run — you should see Hello, world! and a target/ directory of build artifacts.
  5. Add clippy and rustfmt if the installer did not (they ship by default): rustup component add clippy rustfmt.

Prerequisites: a C linker (cc, from build-essential on Debian/Ubuntu or gcc/clang elsewhere) is required to link binaries; git is strongly recommended since Cargo fetches dependencies over git as well as the crates registry.

Rust Syntax and Language Fundamentals

Types, mutability, control flow — and the expression-oriented mindset

Variables, mutability, shadowing

Immutability-by-default is a design decision, not boilerplate: if a value cannot change, the compiler (and every reader) can rely on it. Shadowing is a new let in the same scope — distinct from mutation, and legal with a different type, which makes transform-and-rebind chains idiomatic. Constants are evaluated at compile time and must have an explicit type.

Primitive types

FamilyTypesNotes
Signed integersi8 i16 i32 i64 i128 isizei32 is the default; isize is pointer-sized
Unsigned integersu8 u16 u32 u64 u128 usizeIndexing uses usize; overflow panics in debug, wraps in release
Floatsf32 f64f64 default; IEEE 754
Other scalarsbool, charchar is a 4-byte Unicode scalar value, not a byte
Compoundtuples, arraysTuple: heterogeneous, fixed length. Array: homogeneous, length in the type ([i32; 3])

A slice is a reference to a contiguous sequence — a fat pointer (start + length) that borrows rather than owns. Slices appear constantly in function signatures because they accept arrays, vectors, and string slices alike.

Strings: two types, deliberately

String owns heap memory; &str borrows UTF-8 text that lives somewhere else (a binary’s static data, a String, a file buffer). Functions should take &str and return String when they must produce new text. Module 09 explains why indexing s[1] does not exist and how iteration actually works.

Expressions vs statements — the Rust mindset

A block evaluates to its final expression when that expression has no trailing semicolon. This single rule explains half of the “expected, found” syntax errors beginners meet, and it makes match arms into value producers — the foundation of Rust’s data-oriented style.

Functions

Control flow

  • if requires a real bool — no truthiness, no if x for integers.
  • for x in iterator is the default loop; index-based loops are the exception.
  • Ranges: 0..5 is exclusive, 0..=5 inclusive.
  • break can return a value from loop — the “do until” pattern without flags.

Comments and documentation

Documentation comments support Markdown and executable examples; Module 19 turns them into tests. Sections like # Panics, # Errors and # Safety are community conventions readers expect (Rust API Guidelines, linked in Resources).

Exercises

  1. Write a function fn fizz(n: u32) -> String using only expressions (a match on (n % 3, n % 5) is the elegant solution).
  2. Convert a Celsius/Fahrenheit converter to use shadowing instead of intermediate mut variables — note which version reads better.
  3. Use loop with a break value to implement “smallest power of two above n”.

Ownership: The Core of Rust

Moves, copies, clones, the heap, and the drop — the model everything else follows from

!Take this module slowly
Ownership is the concept that makes Rust Rust. Every later topic — borrowing, lifetimes, smart pointers, Send/Sync, async cancellation — is ownership applied to a new situation. If you invest deeply in one module, make it this one. Practice each idea immediately in the Ownership Lab.

Why ownership exists

Manual memory management (C/C++) makes three classic errors possible: use-after-free, double free, and memory leaks. Garbage collection eliminates the first two at runtime by periodically tracing reachability — at the cost of a runtime, pauses, and unpredictability. Rust’s answer is a third path: make every allocation have exactly one unambiguous owner, make transferring/inspecting that ownership a compile-time question, and free memory exactly when the owner disappears. No collector, no runtime, no dangling pointers in safe code.

Stack vs heap — the physical background

Stack — automatic, LIFO, fast
n: 42 (i32, 4 bytes, known size)
flag: true (1 byte)
coords: [10, 20, 30] (12 bytes, size in type)

Allocated/freed by function calls themselves. Values must have sizes known at compile time.

Heap — requested, dynamic, indirect
"Hello" as UTF-8 bytes (String::from — size can grow)
Vec elements [3, 1, 4] (capacity may exceed length)

Requested at runtime through a pointer. Who frees it, and when? That question is ownership.

A String is the canonical two-part value: on the stack sit a pointer to heap bytes, the length and the capacity; on the heap sit the actual UTF-8 bytes. Copying three machine words is cheap; duplicating the heap buffer is not. This asymmetry is exactly why Rust distinguishes moving from copying and makes you say clone() out loud when you mean the expensive thing.

The three rules

  1. Each value has an owner. Some binding, struct field, collection slot or smart pointer is responsible for it.
  2. There is exactly one owner at a time. Assignment and function-call boundaries transfer (move) ownership rather than aliasing it.
  3. When the owner goes out of scope, the value is dropped. Destruction is deterministic — the Drop trait runs at the closing brace.

Ownership across function boundaries

Every function signature is an ownership contract: parameters say what the function takes, and the return type says what it gives back. No hidden aliases, no surprise frees. When a function only needs to look at data, taking ownership is wasteful and awkward — that is precisely the problem borrowing solves (Module 05).

Ownership in collections, structs, enums

Ownership composes: a Vec<Customer> owns its buffer, which owns each Customer, each of which owns its String fields. Dropping the Vec recursively drops everything — the whole tree, deterministically, at one closing brace.

The drop, observed

Deterministic, reverse-declaration destruction is Rust’s RAII: resource release (files, locks, sockets — Module 21) is tied to scope, not to a collector’s mood or a manual close() call you might forget.

Borrowing and References

&T and &mut T — access without ownership, under the exclusivity rules

Why borrowing exists

If every function that merely read a string had to take ownership of it, Rust would be unusable — you would clone() constantly. A reference lets you refer to a value without owning it: &T (shared, read-only) and &mut T (exclusive, read-write). Creating a reference is called borrowing, because the value will be returned — the borrower never owns, never frees, and must give it back.

Dereferencing is usually implicit (text.len() auto-derefs); explicit *ref appears when assigning through a mutable reference: *text = String::from("new").

The two borrowing rules

iThe rules the compiler enforces
1. Any number of shared references &T may coexist — reading is safe to parallelize. 2. A mutable reference &mut T must be the ONLY reference for the duration of its use — no other &T, no other &mut T. Plus the safety invariant both rest on: references must never outlive the data they point to (Module 06).

Rule 2 is where beginners feel friction, and it is exactly the rule that kills data races and iterator invalidation at compile time: if nobody else can even look while you write, “changed under your feet” is structurally impossible.

Valid and invalid — the canonical four

● Many readers
● Aliasing + mutation
● One writer at a time
● Two writers

Non-Lexical Lifetimes (NLL) — scopes that end at last use

Rust does not track borrows by braces; it tracks them by use. A borrow is live from creation to its last dereference, not to the closing brace. This is NLL, and it is why the “One writer at a time” example above compiles even though r1 is still in scope. When you get a borrow error, ask: where is each borrow’s last use? — not where does its scope end?

Two-phase borrows refine the same idea for method calls: vec.push(vec.len()) compiles because the mutable borrow reserves first but activates only when the call actually needs writing — the shared evaluation of the argument happens in between. You rarely need to reason about this explicitly; knowing borrows end at last use covers 95% of real code.

Dangling references are structurally prevented

The compiler refuses to compute a program where a reference could point at freed memory. “Who does this borrow point at, and do they outlive me?” is a type-level question — the machinery for answering it in general is lifetimes, next module.

Borrowing in practice

  • Parameter choice: take &str/&[T]/&T to read, &mut T to write, T by value only when you must consume or the type is Copy.
  • Field-level splitting: the exclusivity rule applies to places, so disjoint fields can be borrowed simultaneously — this is why Rust code naturally decomposes into small structs.
  • Iterator invalidation: let r = &v[0]; v.push(x); fails because push may reallocate — the rule that prevents use-after-free also prevents the classic C++ bug.

How these rules prevent data races

A data race requires: two accesses to the same location, at least one a write, unsynchronized. Rule 1+2 make write access exclusive against everything in a single thread; the Send/Sync system (Module 14) extends the same exclusivity across threads by controlling which types may cross thread boundaries at all. “Fearless concurrency” is not marketing — it is this rule applied twice.

Lifetimes

What ’a really means — and what it absolutely does not

What a lifetime is

A lifetime is the region of a program during which a reference is guaranteed valid — from the borrow’s creation to the owner’s death, whichever ends first. Every reference has one; the interesting question is only whether the compiler can see it. Inside a function body it always can. Across a function boundary it cannot: given fn f(x: &str, y: &str) -> &str, is the result borrowing from x or y? The caller’s validity depends on the answer. Lifetime annotations are how signatures state the relationship so the compiler can check every caller.

!What ’a does NOT mean
A lifetime annotation does not create, extend or shorten any value’s life. It changes no runtime behavior whatsoever — it is purely a compile-time relationship statement, like a type. Writing ’a never rescues a dangling reference; it only describes constraints the compiler then verifies. If the constraint is false, you get E0597, not a working program.

The canonical example, read precisely

Read it as a contract, not as code: “there is some region ’a such that both inputs are valid for it, and whatever I return will be valid for exactly that region.” The compiler picks ’a at each call site as the intersection of the two arguments’ lifetimes — the only region where both promises hold and therefore the only region the return value can promise. Elision — why you rarely write these

The compiler applies three rules so most functions need no annotations:

  1. Each elided reference parameter gets its own fresh lifetime parameter.
  2. If there is exactly one input lifetime, it is assigned to all elided output lifetimes (fn f(s: &str) -> &str means output borrows from s).
  3. For methods, &self/&mut self wins: elided outputs borrow from self.

longest needs an annotation because it has two inputs and rule 2/3 cannot pick. When the compiler says “missing lifetime specifier”, it means the elision rules were insufficient — you must state the relationship yourself.

Structs that store references

Structs holding references are borrow-checker-visible: instantiate Excerpt with data that dies first and E0597 names the field. Most production structs own their data (String, not &str) and need no parameters at all — borrowing structs shine for zero-copy views: parsers, iterators, protocol decoders.

Multiple parameters, bounds, ’static

Common misunderstanding #1: “’static means a global variable” — no, it means valid for every region, which owned data and literals satisfy. #2: “adding ’a fixed my error” — annotations never fix; they only let the compiler explain precisely which relationship fails. #3: confusing lexical scope with lifetime — since NLL, lifetimes end at last use (Module 05).

Error Handling

Errors as values: panic, Result, ?, From-conversion, thiserror vs anyhow

Two kinds of failure

Rust splits failures the way mature systems actually fail. Unrecoverable states — broken invariants, impossible values, bugs — use panic!: print a message and backtrace, unwind, abort. Recoverable states — file missing, timeout, bad input — are values of type Result<T, E>, returned, propagated and handled like any other data. The type system makes “this can fail” impossible to overlook: there is no checked-exception opt-out and no silent throw.

The ? operator — propagation without ceremony

? desugars to: if Ok, unwrap the value; if Err, return From::from(err) converted into this function’s error type. The From hook is the composition point — it lets one domain error type absorb io::Error, serde_json::Error and friends with #[from].

When is unwrap()/expect() reasonable? In tests, in examples, in main of a throwaway tool, and — with expect("why this cannot fail") — at sites where you can prove the invariant (a lock just acquired, a parse you just validated). What is inappropriate is unwrap as the default error strategy of production code paths.

Smart Pointers and Memory Management

Box, Rc, Arc, RefCell, Weak — choosing the right ownership topology

Why they exist

References borrow (Module 05) — they never own. Sometimes you need ownership shapes references cannot express: a value on the heap of unknown size, a value with several owners, mutation behind a shared handle, or shared access across threads. Smart pointers are owning wrapper types; each one relaxes one specific ownership constraint, and says so in the type.

Interior mutability: mutation behind an immutable face

RefCell does not remove the exclusivity rule — it moves enforcement from compile time to runtime, panicking on violations. You pay for situations the compiler cannot see through (shared graphs, callbacks, test doubles). Mutex/RwLock are the thread-aware cousins: same idea, blocking instead of panicking.

Concurrency and Parallelism

Threads, channels, locks, atomics — and how the type system makes races compile errors

Concurrency vs parallelism

Concurrency is about structure: dealing with many things at once (tasks that overlap in time). Parallelism is about execution: doing many things literally simultaneously (needs multiple cores). A web server is concurrent; a number cruncher across 8 cores is parallel. Rust’s threads give you parallelism; channels and async (Module 15) give you concurrency structures; the safety story covers both.

Threads: spawn, move, join

Why move is mandatory here: a spawned thread may outlive the caller’s stack frame, so borrowing local data would dangle. 'static + Send bounds on the closure are the compiler enforcing that reasoning.

Message passing: channels

Message passing transfers ownership of each message — once sent, the sender cannot touch it, so no lock is needed. That is the Go-tagline insight (“share memory by communicating”), but with the compiler proving no one else still holds the value.

Shared state: Mutex and RwLock

The genius is structural: the data lives inside the lock, and the only way to reach it is through a guard — forgetting to lock is a type error, not a race. Compare with Java, where the lock is a convention beside the field.

Deadlocks, races, and the honest limits

  • Data race (two accesses, one write, unsynchronized): impossible in safe Rust — the exclusivity rules of Module 05 extended across threads via Send/Sync.
  • Race condition (logic-level ordering, e.g. check-then-act across a lock boundary): still your responsibility — hold one lock across the whole invariant, or restructure around channels.
  • Deadlock (circular lock waiting): possible — discipline fixes it: acquire locks in a fixed global order, or better, never hold two; scope guards tightly; prefer message passing for ownership transfer.
  • Lock poisoning: a panic while holding a Mutex marks it poisoned — .lock() returns Err, forcing the next thread to decide (recover with into_inner or propagate).
  • Thread pools & parallel computation: for data-parallel work, the rayon crate turns sequential iterators into parallel ones (par_iter()) with a work-stealing pool — the idiomatic first tool for CPU-bound maps/reduces.

Async Rust and Futures

The mental model, the runtime’s job, and practical Tokio engineering

The problem async solves

One OS thread costs megabytes of stack and scheduling overhead. A service handling 10,000 mostly-idle connections cannot afford 10,000 threads — but it can afford 10,000 state machines that each wake only when their I/O is ready. That is async: concurrency without a thread per task. Note carefully what it is not: async does not create OS threads, does not run your CPU code in parallel by itself, and does not make anything faster — it makes waiting cheap.

Futures, polling, and the runtime’s job

Key mental model: calling an async function creates a future; .await is where you hand control back until it completes. Between awaits, the task occupies a thread; at an await on a not-yet-ready operation, the thread is released to run other tasks. The runtime (executor) owns the threads, the waker plumbing and the I/O driver — your code declares the data dependencies.

Pinning and Advanced Async Internals

Pin, Unpin, self-referential futures — why the machinery exists

The problem: self-referential data

Most Rust values can move freely — a String’s stack header can relocate because the heap bytes stay put. But an async fn becomes a generated struct holding its locals across awaits, and those locals can include values that point into the same struct (a stack-allocated future borrowing a local buffer). If that struct moved, the internal pointers would dangle. The borrow checker cannot reason about a value pointing into itself — that is not expressible in safe Rust’s model — so the async transformation generates such structs only under a strict condition: once polled, the future must never move again.

Polling, wakers, cancellation — the running system

  • Waker: when poll returns Pending, the future has stored a Waker (a handle back to the executor). The I/O driver calls wake() on readiness; the executor re-queues the task. Nothing busy-waits.
  • Cancellation: dropping the future destroys the state machine and runs Drop on everything held — sockets close, guards release. But partial progress is not rolled back: a loop of select! over an operation that half-completed (sent a request, not read the reply) must either be retry-safe or restructured — that is cancellation safety. Prefer naturally resumable primitives (loops around recv, idempotent requests, checkpointed work).
  • Holding resources across .await: a MutexGuard held across an await is a deadlock risk (Module 15) and a clippy lint; a RefCell guard held across an await inside a spawned task can panic on the next poll if re-borrowed — scope guards before awaiting.
  • Send futures: tokio::spawn requires the whole state machine be Send — holding a non-Send value (e.g. Rc) across an await makes the future non-Send, rejected at the spawn site (see the Error Arena’s Send diagnostics).

Unsafe Rust and Memory Safety

What unsafe really gives you, and the obligations it hands back

!Calibrate first
unsafe is not a sandbox switch and does not turn off the borrow checker globally. It grants exactly five additional powers inside an explicitly marked block or function, and in exchange you become responsible for upholding the invariants the compiler can no longer prove. Production advice, unironically: measure twice, write zero unsafe. When you must, encapsulate it (below) and review it with the checklist at the end of this module.

What unsafe actually grants

  1. Dereference raw pointers (*const T, *mut T)
  2. Call unsafe functions and methods (including FFI/extern)
  3. Access or modify mutable statics
  4. Implement unsafe traits
  5. Access fields of unions

Everything else — moves, borrows, lifetimes, drops — keeps applying exactly as before, including inside unsafe blocks.

Raw pointers and the soundness bar

Undefined behavior is the dragon: dereferencing dangling/misaligned pointers, reading uninitialized memory, data races, breaking aliasing rules, or producing an invalid value (e.g. bool = 2). UB is not a crash you can catch — the optimizer assumes it never happens and may delete surrounding code. That is why every unsafe block is a proof obligation, not a permission slip.

FFI: talking to C

Also in this family: unions (C-compatible overlapping storage — reading a union field is unsafe because you must guarantee the active variant), static mut (mutable global state — nearly always a data race in waiting; use a Mutex or atomics instead), and layout control via #[repr(C)]/repr(align/packed) when interfacing with hardware or C structs.

Sound abstractions: the professional pattern

The goal is never “unsafe program” — it is a safe API whose implementation uses unsafe internally. Library code (Vec, HashMap, tokio’s epoll glue, every GPU binding) is built this way: one audited unsafe core, a public interface whose types make misuse impossible.

Error boundaries and public API design

  • Error layering: domain errors (meaningful variants, no I/O types) → application errors (adds orchestration failures, #[from] conversions) → edge mapping (HTTP/CLI/JSON rendering). Module 08’s types at each boundary, never leaking sqlx::Error past the store crate.
  • API design: follow the Rust API Guidelines (linked in Resources) — new as constructor, builders over long parameter lists, as_/to_/into_ conversion naming, #[must_use] on results, comprehensive but not exhaustive pub.
  • Versioning: semver applies to your public API — pre-1.0 signals instability; additive changes (new methods, new trait impls) are minor; anything a caller could observe changing is major. cargo semver-checks automates the audit.
  • Feature flags: additive, independently combinable, never on the critical path of correctness (Module 12).
  • Extensibility: accept traits, expose small composable pieces, prefer output flexibility (impls you provide) over input generics everywhere — the std library itself is the case study.
