Browser Fundamentals & Web Platform Architecture

What a browser actually is — and what it is not

What a web browser is

A web browser is an application that fetches, interprets, executes and presents web resources according to a set of open standards. That single sentence hides an enormous amount of work: the browser is simultaneously an operating-system-like runtime (scheduling tasks, managing memory, enforcing permissions), a document engine (parsing and rendering HTML/CSS), a virtual machine host (executing JavaScript and WebAssembly), a network client (DNS, TCP, QUIC, TLS, HTTP), and a security enforcement system (same-origin policy, sandboxing, process isolation). When engineers say “the browser” they are usually referring to this entire stack, not to a single program.

Its responsibilities include: navigating to URLs and managing session history; downloading subresources; parsing HTML into the DOM; parsing CSS into the CSSOM; executing scripts; calculating styles and layout; painting and compositing pixels; dispatching user input as events; storing data locally; and mediating all of it through a security model that assumes any page may be hostile.

iTerminology used throughout this guide
Rendering engine (Blink, Gecko, WebKit) turns HTML/CSS/JS into pixels. JavaScript engine (V8, SpiderMonkey, JavaScriptCore) executes ECMAScript. The browser is the whole product around them. “Chrome” is a browser built on the Blink rendering engine and V8; Firefox uses Gecko and SpiderMonkey; Safari uses WebKit and JavaScriptCore. The distinction matters because behavior specified by standards is shared, while everything else is an implementation choice.

Browser versus rendering engine versus JavaScript engine versus OS

These four layers are frequently confused. The rendering engine implements the DOM, CSSOM, rendering pipeline and, in most engines, its own event-loop scheduling hooks. The JavaScript engine implements the ECMAScript language: parsing, bytecode, JIT compilation, garbage collection. ECMAScript itself specifies no DOM, no setTimeout, no fetch — those are host APIs provided by the platform. The operating system provides processes, threads, sockets, files and the display compositor; the browser is a client of the OS, not a replacement for it. JavaScript’s single-threaded execution inside a renderer is a property of the browser host environment, not of the ECMAScript language, which describes an agent with its own event loop in the abstract.

Web standards and interoperability

The web’s defining feature is that a page written once renders everywhere. This is achieved through standards: WHATWG maintains the HTML Living Standard, DOM Standard, Fetch Standard, URL Standard and others as continuously updated “living” documents; W3C maintains most CSS specifications; Ecma TC39 maintains ECMAScript; IETF maintains HTTP (RFC 9110–9114) and TLS (RFC 8446). Browsers implement these independently, and where behavior is unspecified, engines diverge — a recurring theme in this guide. A useful mental model: standards define observable contracts (parsing results, event order, security boundaries), while internal architecture is left to each implementer.

The browser’s subsystems at a glance

Every modern browser contains the following subsystems, whatever the product: a UI layer (chrome, tabs, address bar); a navigate/dispatch core deciding what loads where; a network stack (caches, connections, protocol handling); a parsing pipeline (HTML, CSS, JS); a rendering pipeline (style → layout → paint → composite); an event and input system; a storage layer (cookies, localStorage, IndexedDB, cache storage); and a security model binding it all together. Multi-process versus single-process

Historically browsers were single-process: one program did everything, and a crash or security breach anywhere was fatal everywhere. Modern browsers split work across multiple OS processes: a browser (UI) process, per-site renderer processes, a GPU process, and service processes. This buys crash isolation (one tab crashing does not kill the browser), security (renderers run sandboxed with minimal OS privileges), and performance (parallelism across cores), at the cost of memory and IPC complexity. The trade-off is engine-specific: the split, the process count limits, and what runs where differ between Chromium, Firefox and WebKit — Module 02 uses Chromium as the detailed case study and marks clearly what is not universal.

Why internals matter to engineers

Every practical frontend question bottoms out in browser mechanics. “Why is my page blank for two seconds?” is a question about parsing, render-blocking resources and the event loop. “Why does this animation jank?” is a question about the main thread, paint and compositor layers. “Why does this fetch fail?” is a question about CORS and connection state. Engineers who understand the machine stop guessing and start measuring — and they read performance traces as naturally as they read stack traces. Backend engineers benefit equally: knowing what the client actually does with your headers, caches and streaming responses changes how you build APIs.

Browser Architecture: Processes, Threads & IPC

A Chromium case study — with the browser-specific parts clearly marked

This module describes Chromium’s architecture as a detailed, realistic example. Process names, thread counts and IPC mechanisms are implementation details — Firefox and WebKit divide responsibilities differently. Nothing on this page is required by any web standard; what standards do require (isolation guarantees, storage partitioning) is marked.

The cast of processes

Browser process — the privileged coordinator. It owns the UI (tabs, address bar, bookmarks), session history, permission prompts and network policy. It is the only process that talks to all renderers and to the OS with full rights. Renderer processes — each hosts web content: parsing, DOM, style, layout, script execution. Renderers are sandboxed: minimal file access, no direct network access to the OS (they ask the browser process), and restricted system calls. GPU process — the single process that talks to GPU drivers, accepting draw commands from renderers (tiles, layers) and compositing them into the final frame. Centralizing GPU access isolates driver crashes and enforces one context per machine. Network service — a utility process owning sockets, DNS, TLS and the HTTP cache (historically threads inside the browser process; now split out for stability). Utility processes — short-lived workers for isolated tasks such as audio service, data decoding or profiling.

DIAGRAM 02Chromium process & thread relationships (implementation example)

Simplified: a real Chromium run also spawns utility processes (audio, profiling) and may merge renderers for same-site tabs under memory pressure. The essential shape — privileged browser process, sandboxed renderers, one GPU process — is what matters.

Threads inside a renderer

The main thread is where nearly everything you think of as “the page” happens: HTML parsing, DOM mutation, style calculation, layout, paint record generation, and JavaScript execution. When developers say “the main thread is blocked”, they mean one long task is monopolizing this thread, delaying parsing, input handling and rendering. The compositor thread handles scrolling and frame presentation with input from the main thread’s layer tree; when a page scrolls, this thread often produces frames without the main thread at all. Raster worker threads turn paint records into textures, on CPU or GPU. Worker threads host Web Workers and service workers. Dedicated audio and I/O threads exist in some configurations. The JavaScript execution thread is the main thread — JavaScript in a page runs there unless explicitly moved to a worker.

Site isolation and process allocation

Which sites share a renderer is a security decision. Chromium’s site isolation places documents from different sites (scheme + registrable domain, e.g. example.com including its subdomains) into different processes. The motivation is defense in depth: even if a renderer is compromised by a memory-safety exploit, it holds content from only one site, and cross-site documents cannot be read from inside the process. Same-site tabs and iframes may share a process; cross-site iframes get their own. Under memory pressure or in constrained environments (Android historically, low-end devices) browsers relax this and trade isolation for memory. standard the guarantees attackers must not read cross-site data (same-origin policy) are standard; implementation achieving them with per-site processes is Chromium’s choice.

Inter-process communication

Processes communicate through IPC. In Chromium this is the Mojo framework: typed message pipes with interface definitions, plus shared-memory buffers for bulk data (tiles, bitmaps) and GPU command buffers that let renderers record GPU work for the GPU process to replay. Every cross-process call is asynchronous by nature — a renderer asking the network service to fetch a URL sends a message and gets a callback, it never blocks a thread on a syscall. This asynchrony is why so many browser APIs are callback- or Promise-based: the API surface mirrors the architecture.

Sandboxing and crash isolation

A sandboxed renderer runs with an OS-level reduced token (Windows) or seatbelt profile (macOS) or seccomp filter (Linux): no direct file writes, no direct socket creation, no arbitrary syscalls. All privileged operations are brokered through the browser process, which validates each request. Crash isolation follows from process boundaries: a renderer crash kills its tabs only, and the browser process offers to reload them. GPU driver hangs can be survived because the GPU process can be restarted. The security payoff is real but bounded — sandboxes reduce what an exploited process can do, they do not prevent the exploit itself.

Resource management

Multi-process browsers are aggressive memory managers: they suspend background renderers (freezing timers and rAF), discard tabs entirely under pressure (reload on revisit), cap the total number of live processes, and merge same-site renderers. Every one of these behaviors is an implementation trade-off between memory, battery, isolation and responsiveness — and every browser draws the line differently. For engineers the practical consequence: your page may be frozen or discarded at any time, and the Page Lifecycle events (freeze/resume, discard) exist so well-behaved applications can react.

Navigation: What Happens When You Enter a URL?

The seventeen-step journey — and where its steps overlap

The idealized sequence

Every “what happens when you type a URL” explanation walks a sequence like this. It is the right place to start — and the wrong place to stop, because real browsers overlap these steps aggressively: DNS may resolve while the process is still spinning up, speculative connections may already be open, and parsing begins before the response body finishes downloading. Learn the sequence, then learn the overlaps.

  1. User enters a URL — typed, pasted, clicked or suggested by omnibox autocomplete.
  2. URL parsing and validation — the browser process parses per the URL Standard; the omnibox may interpret bare words as search queries.
  3. Navigation begins — the browser process asks the target renderer (or a new one) to prepare.
  4. State and policy checks — permissions, download intent, safe-browsing, scheme handlers, form resubmission warnings.
  5. Cache and service-worker checks — a controlling service worker may answer before any network work; the HTTP cache may avoid the request.
  6. DNS resolution — host name to IP, via caches, system resolver or DoH (Module 17).
  7. Connection establishment — TCP three-way handshake or QUIC version negotiation, possibly to an already-speculatively-open connection.
  8. TLS negotiation — certificate validation and key exchange for https (Module 17).
  9. HTTP request sent — method GET, headers, cookies (Module 18).
  10. Response arrives — status line and headers first; the browser inspects Content-Type, CSP and redirect status.
  11. Redirects may occur — 301/302/303/307/308 or HTML/CSS/JS-driven; the loop restarts at the appropriate step with the new URL (browsers cap redirect chains).
  12. Response processing begins — mime sniffing fallbacks, download detection, security header enforcement, commit.
  13. HTML parsing begins — incremental, from the first bytes (Module 05).
  14. Subresources discovered and requested — parser discovers CSS, scripts, images; the preload scanner races ahead of the parser (Module 19).
  15. DOM and CSSOM construction proceed — in parallel with each other and with script execution (Modules 05–07).
  16. Rendering and presentation — style, layout, paint, composite (Module 11); first paint can occur while the document is still parsing.
  17. The page becomes interactive — according to its loaded resources and execution state: parser-blocking scripts done, main thread free of long tasks, hydration complete.

Same-document versus cross-document navigation

A cross-document navigation replaces the document: a new renderer (or a reused one) loads a fresh response, and the old document is destroyed. A same-document navigation — fragment change, history.pushState(), replaceState() via the History API — keeps the document alive: no network round trip for the document itself, scripts and state survive, and the browser updates the address bar and history. Same-document changes skip nearly the entire sequence above, which is why single-page applications navigate instantly — and why their URL semantics are the application’s responsibility. The newer Navigation API gives same-document transitions first-class events (navigate, navigatesuccess) instead of the older popstate/hashchange pair.

Reload, hard reload, and redirect handling

A reload re-requests the main resource, usually with revalidation (the cache may answer 304 “Not Modified”), while subresources follow their own freshness rules. A hard reload (Ctrl/Cmd+Shift+R) bypasses the HTTP cache for the document and often for subresources, forcing conditional or full requests. Server redirects are followed transparently up to a cap (about 20 in Chromium — an implementation detail): 301/308 preserve method and body semantics for permanent moves, 302/303 historically rewrite POST to GET, 307/308 preserve the method strictly. Meta-refresh and location assignments are JS/HTML-initiated navigations, handled after the current task completes.

Back/forward cache and page lifecycle

When you navigate away, the browser may not destroy the page. The back/forward cache (BFCache) keeps a fully alive renderer in memory so that pressing Back is instant — no network, no parse, no rehydration. Pages are evicted or never stored for observable reasons: open WebSocket/WebRTC connections in some engines, unload handlers in some configurations, pending payments. The Page Lifecycle gives scripts visibility: pageshow/pagehide with persisted flags, and the newer freeze/resume events when a page is frozen to save resources. Well-engineered applications treat “the page was gone and came back” as a normal state, not an exception.

Speculation: preconnect, prefetch, prerender

Browsers constantly guess. While you read, they may preconnect (DNS + TCP + TLS) to hosts you are likely to visit next — driven by resource hints like <link rel="preconnect">, by navigation predictors, or by typing a partial URL. They may prefetch a likely next document into the HTTP cache, or fully prerender it in a hidden renderer so the navigation is instant. Speculation spends bandwidth, memory and battery on guesses; getting it wrong costs resources, getting it right removes hundreds of milliseconds of latency. Module 19 covers the resource-hint mechanics; here the point is architectural: the “sequence” above is frequently shortened because steps 6–8 already happened before you navigated.

Measuring navigation

The Navigation Timing API exposes every milestone of this module as timestamps: startTime, domainLookupStart/End, connectStart/End, secureConnectionStart, requestStart, responseStart, domInteractive, domContentLoadedEventStart/End, loadEventStart/End. Read them via performance.getEntriesByType('navigation'). These are real measurements, not estimates — and they are the ground truth when investigating “why is my site slow” (Module 25 builds workflows on them).

URL anatomy

A URL is a structured string, not a blob. The URL Standard defines its components and their exact parsing — including how malformed URLs fail:

Relative URL resolution is the algorithm that turns ../img/logo.png into an absolute URL against a base URL. It is why moving an HTML file can break image paths, and why <base> exists. Percent-encoding escapes reserved characters (%20 for space, %2F for an embedded slash in a query value); forgetting it is a classic source of broken URLs and injection bugs — always build query strings with URLSearchParams.

Special schemes

blob: URLs reference in-memory Blob data and carry an inner origin from the creating context — a blob URL created by https://a.example inherits that origin. data: URLs embed content directly; they are treated as opaque origins in modern browsers (historically null), and fetching cross-origin data: URLs is restricted. file: URLs have no host and origin behavior varies by engine — one reason file: pages cannot reliably use privileged APIs. An opaque origin serializes to null and compares unequal to everything, including itself — the mechanism behind sandboxed iframes.

Origin, site, and the same-origin policy

An origin is the tuple (scheme, host, port). Two URLs are same-origin only if all three match exactly: http://a.example and https://a.example differ (scheme), a.example and dev.a.example differ (host), a.example:8080 and a.example differ (port, when non-default). The same-origin policy (SOP) is the web’s core security invariant: script from one origin cannot read data from another without explicit opt-in (CORS headers, postMessage). A site is coarser: scheme + registrable domain (the public suffix plus one label — example.co.uk, where co.uk is a public suffix from the Public Suffix List). Same-site comparisons use it for cookies (SameSite), prefetch behavior and process-isolation decisions. Origin protects data; site shapes policy. Cross-origin is not the same as cross-site.

HTML Parsing & DOM Construction

A stateful tokenizer and tree builder — not a string-to-tree converter

From bytes to tree

HTML parsing is specified in the WHATWG HTML Standard as a pipeline of stages with explicit state machines: bytes are decoded (encoding sniffing from BOM, <meta charset> or defaults), become a character stream, feed the tokenizer, whose tokens feed the tree construction stage, which builds the DOM under the guidance of insertion modes. The parser is incremental: it processes chunks as they arrive over the network, and the DOM grows while the response is still downloading. It is also resumable and error-correcting: malformed markup does not abort the parse; the specification defines exactly how to recover.

DIAGRAM 04Tokenization and tree construction

The tokenizer

The tokenizer recognizes: DOCTYPE, start tags (with attributes), end tags, character data, comments, and CDATA-ish constructs. It is a state machine with states like “tag open”, “attribute value double-quoted”; a stray < in text moves it to a new state, and whether it produces a tag or a literal character depends on what follows. Attributes are lower-cased (for HTML elements), duplicates are dropped (first wins), and values are unescaped (&amp; → &).

Tree construction and insertion modes

The tree builder receives tokens and decides, per its current insertion mode, where each element goes. It maintains a stack of open elements and the list of active formatting elements. This machinery is what produces “implied” elements: <li> implicitly closes a previous <li>; a <td> outside any table context is dropped or re-parented; <table> fosters offending content out of the table. The famous example: <p>div</p> — the parser closes the paragraph before the div, because <div> cannot exist inside <p>. None of this is leniency by accident; the recovery algorithm is specified token by token, which is why different browsers build the same DOM from the same broken HTML.

Shadow DOM attaches a scoped subtree to an element: host.attachShadow({mode:'open'}) returns a shadow root whose children are invisible to querySelector from the outside document. It is the encapsulation primitive behind Web Components — styles do not leak in or out by default, and event targets are retargeted at the host boundary. A light DOM query cannot reach inside a closed shadow root at all. Frameworks and design systems use it to ship widgets whose internals cannot collide with page CSS or scripts. We return to it in Modules 07 (styling boundaries) and 26 (components).

CSS Parsing, CSSOM & Style Calculation

How rules are parsed, matched, cascaded and turned into computed values

From bytes to rules

CSS is parsed into the CSSOM — a tree of objects mirroring the stylesheet structure: stylesheets contain rules; rules contain preprocessed selectors and declarations. Unlike HTML parsing, CSS parsing is not incremental in the same way: because a rule’s meaning can depend on what follows (later rules override earlier ones, @media blocks wrap later context), engines historically waited for a stylesheet to finish before using it — which is exactly why an external stylesheet is render-blocking: the browser will not render until the CSSOM is complete, because rendering with half the CSS would show wrong styles and then flash to correct ones. Invalid constructs are dropped silently: a bad selector kills its whole rule; a bad declaration is skipped individually; recovery resumes at the next ; or block end.

DIAGRAM 06DOM + CSSOM → computed style

Selector matching

Engines match right to left: for selector ul li span.badge, the engine first finds elements matching span.badge, then walks up the ancestors checking for an li, then a ul. This is why descendant selectors with a common rightmost part (.wrap *) are expensive: the right side matches huge numbers of elements. Browsers heavily optimize matching with bloom-filter-like ancestor checks and style-sharing between similar siblings, but selector hygiene still matters: prefer classes, keep depth shallow, avoid needless universal or tag rightmost parts.

Specificity and the cascade

When several rules match one element, the cascade decides. In order: (1) origin and importance — user-agent < user < author < author !important < user important < UA important, plus transition/animation origins; (2) specificity; (3) source order — last wins. Specificity counts, per selector, (a) IDs, (b) classes/attributes/pseudo-classes, (c) types/pseudo-elements: #nav .item:hover is (1,2,0). Pseudo-classes count in column b; :is()/:where() take the specificity of their most specific argument (or zero, for :where()); inline style beats any selector except !important.

Computed, used and resolved values

The cascade produces a specified value for every property. The computed value resolves it to something layout-ready: relative units resolved where possible (em → px against the element’s font), URLs absolutized, var() substitutions performed. The used value is what layout finally assigns after the box’s geometry is known (a width: auto becomes a concrete pixel width; a percentage becomes px). The resolved value is what getComputedStyle() returns — usually the computed value, but the used value for geometry-dependent properties like width and top. Custom properties, queries, pseudo-elements

Custom properties (--brand: cyan;, used as color: var(--brand)) participate in the cascade and inherit; they are tokens resolved at computed-value time, which makes them theming primitives that preprocessor variables are not. Media queries apply rules by viewport/feature (@media (min-width: 48rem)); container queries (@container (min-width: 400px) with a container-type: inline-size ancestor) respond to a container’s size rather than the viewport — components finally respond to their own context. Pseudo-classes select states (:hover, :focus-visible, :nth-child()); pseudo-elements style fragments (::before, ::selection, ::part() for shadow-DOM piercing).

Invalidation and recalculation

When the DOM or a stylesheet changes, the engine must decide which elements’ computed styles are stale. This is style invalidation. Class changes invalidate the element and, depending on selectors involved, descendants or siblings. Appending a subtree computes styles for it. A <style> content change can invalidate broadly. Engines bucket invalidation work by selector features to avoid recalculating the whole document; nevertheless, :has() and broad attribute selectors can widen the blast radius. Style recalculation then recomputes matching rules for dirty elements — a main-thread pipeline stage that appears in traces as “Recalculate Style” with a count of elements affected (Module 25 shows where to look). Changing only a custom property can be cheaper than changing structural selectors, but none of this is guaranteed across engines — measure your case.

Stylesheet delivery realities

External stylesheets block first render until downloaded and parsed; @import chains serialize discovery (the outer CSS must load before the inner one is even seen) — use <link rel="stylesheet"> tags in parallel, or bundle. Critical CSS inlines above-the-fold rules into the document and loads the rest asynchronously, trading maintainability for first paint. Dynamically added stylesheets trigger recalculation when they apply. Print styles, alternate stylesheets and disabled sheets are parsed but skipped at match time. Shadow DOM style boundaries: selectors from the outside do not match inside a shadow tree (except inheritable properties cascading in, and explicit ::part() opt-ins).

JavaScript Engine & Runtime Architecture

Parse, bytecode, tiers, deopt — and where the engine ends and the host begins

What the engine does

A JavaScript engine implements ECMAScript: it parses source into an AST, compiles that to bytecode, executes the bytecode in an interpreter, profiles hot functions, and re-compiles them with an optimizing JIT compiler producing machine code. It also owns the garbage-collected heap, the call stack of execution contexts, and the language’s built-in objects (Object, Array, Promise, Math…). What the engine does not own: document, setTimeout, fetch, console, the event loop itself. Those are host APIs provided by the browser (or Node.js, or any other embedding). The distinction is not pedantic: it explains why setTimeout timing differs between browsers, why window is not in the ECMAScript spec, and why the event loop is specified by the HTML Standard, not by ECMA-262.

DIAGRAM 07Engine execution model (V8-shaped, tier names are implementation)

Interpreters, tiers and deoptimization

Why two (or more) execution tiers? Because compiling everything optimally is slow to start, and interpreting everything is slow to run. Engines start every function in the interpreter, collecting feedback: what shapes objects had, what types flowed through operations, which branches ran. After enough invocations, the optimizing compiler speculates — “this addition always saw numbers” — and emits fast machine code with guards. If a later call violates the speculation (a string arrives), the engine deoptimizes: it throws away the optimized code, resumes in the interpreter, and may re-optimize with broader assumptions. The practical consequences for engineers: stable types and shapes beat cleverness — monomorphic call sites and consistent object layouts run dramatically faster than polymorphic ones; and a function whose types flip frequently pays deopt costs repeatedly. implementation Tier names, thresholds and heuristics differ per engine and change across versions; the shape of the pipeline is the durable knowledge.

Heap, stack, and execution contexts

The stack holds execution contexts — function frames with locals and bookkeeping — and is cheap and automatically reclaimed on return. The heap holds objects whose lifetime is not tied to a call: objects, closures, arrays, DOM wrappers (the DOM node itself lives in the renderer’s C++ world; JS sees a wrapper). Garbage collection (Module 24) reclaims unreachable heap objects. Execution contexts carry the lexical environment (where bindings live) and the this binding; module contexts, function contexts and the global context share the same machinery. Closures are functions plus their captured lexical environment — the reason inner functions can outlive their outer call while keeping its variables alive (and a classic leak vector when captured unintentionally).

Modules and built-ins

ECMAScript modules are engine-level: parsing, linking and evaluation of import/export are specified by ECMA-262, while fetching modules is the host’s job (the HTML Standard, for browsers). A module has its own module scope (not global), strict-ish semantics, and top-level this === undefined. Built-in objects the engine provides (JSON, Reflect, Proxy) are portable across embeddings; host-provided globals differ per environment — feature-detect rather than assume.

iEngine versus runtime — the summary
V8 is not “Chrome’s JavaScript” only: it also powers Node.js and Deno. The engine answers “how does this code execute?”; the runtime answers “what can this code do?” — DOM in browsers, fs in Node. When behavior differs between browser and Node (timer precision, microtask timing details, available globals), you are almost always looking at a host difference, not an engine difference.

Execution contexts and the call stack

Every time JavaScript runs, at least one execution context exists: the global context created when the realm starts. Each function call pushes a function context onto the call stack; each return (or thrown error) pops it. A context holds: the current lexical environment (bindings visible here, chained to outer environments), the this value, and evaluation state. The stack is last-in-first-out, which is why stack traces read top-down from the crash site to the entry point.

Scope, hoisting, and the temporal dead zone

Lexical scope is decided by where code is written, not where it runs: a function defined inside another sees that outer function’s bindings forever. Hoisting is the two-phase execution model: declarations are processed when the context is created (functions fully; var as undefined), statements execute after. let/const are also hoisted — but stay uninitialized in the temporal dead zone until their declaration executes; touching them earlier throws ReferenceError. Closures and retained environments

A closure is a function value plus a reference to the lexical environment it was created in. The environment (and everything it binds) stays reachable as long as the closure is reachable — even after the outer function returned. That is the feature (private state, factories, memoization) and the liability (capturing a large object in a long-lived callback keeps it alive; Module 24 hunts exactly this leak class).

Recursion and stack overflow

Each nested call grows the stack; engines cap it (thousands of frames, engine- and frame-size-dependent implementation). Exceeding the cap throws RangeError: Maximum call stack size exceeded. Deep data is better walked iteratively with an explicit stack; infinitely recursing mutual functions are a logic bug, not a stack-size problem. Promises do not grow the stack across ticks — each callback starts with a fresh stack, which is also why errors inside .then chains appear with short, confusing traces (async stack traces in DevTools stitch these back together).

Exceptions and propagation

A throw unwinds frames one by one, running finally blocks and popping contexts, until a matching catch — or the host reports the uncaught error. Synchronous unwinding is stack-based; but a rejection is not an exception on the stack: it is a state transition on a Promise, observed by microtasks later (Module 10). Mixing the two — throwing inside a setTimeout callback — starts a fresh stack with no caller to catch; the host logs it. try/catch around an async call without await catches nothing: the throw happens in a later task.

Browser Event Loop & Task Scheduling signature

The WHATWG model — task sources, microtask checkpoints, rendering opportunities

The model, precisely

The event loop is specified in the WHATWG HTML Standard, not in ECMAScript. Each agent (a window’s main thread, a worker) has one event loop. An event loop has: one or more task queues, each holding tasks from a particular task source; a microtask queue (a single queue, not per-source); and, for window event loops, the notion of rendering opportunities. The loop spins forever:

  1. Pick a task from one of the task queues. Which queue to prefer when several are non-empty is deliberately left to the implementation — browsers prioritize (user interaction usually beats, say, a timer firing) — so “the event loop is a FIFO” is wrong at the queue level: it is FIFO within a queue, but selection among queues is an implementation decision.
  2. Run the task to completion — a task is one callback: one timer callback, one click dispatch, one fetched-resource continuation. The loop cannot run anything else mid-task; only the current code can yield via finishing or awaiting.
  3. Microtask checkpoint — drain the entire microtask queue: Promise reaction jobs, queueMicrotask callbacks, MutationObserver callbacks. Every callback queued by a microtask runs in the same checkpoint, before anything else happens. A checkpoint occurs whenever the JavaScript execution context stack empties — in practice after every task callback and after the initial script evaluation.
  4. Maybe render — a window event loop gets a rendering opportunity only when it aligns with the display’s refresh (VSync). When it does: run requestAnimationFrame callbacks, then update the rendering (style, layout, paint, composite — Module 11). When it does not: straight back to step 1. This is why a busy task delays paint by whole frame multiples, and why not every task produces a paint.
  5. When idle and supported, requestIdleCallback callbacks may run with a deadline and remaining-time budget.

Timers under the hood

setTimeout(fn, 0) does not mean “immediately”: it means “enqueue a task after at least 0 ms.” The delay is a minimum: the task fires only when the loop reaches the timer queue and the deadline passed. Nested timers (5+ levels deep) get clamped to a ~4 ms minimum per HTML Standard to discourage busy-polling; background tabs get much harsher throttling (often ≥1 s, engine-specific), and Chrome’s intensive throttling can delay chained timers much further. setInterval enqueues a task per interval tick, with the same minimum-delay semantics and drift behavior; it does not run a callback while a previous one is still queued in some engines — timers are coarse tools for pacing. For scheduling work relative to rendering use requestAnimationFrame; for yielding to the event loop from a long computation, a MessageChannel or setTimeout(0) split beats naive chunking, and scheduler.yield() (where available) preserves priority better.

Starvation, long tasks, and responsiveness

A long task (by convention > 50 ms of main-thread time) blocks input processing, timers and rendering for its whole duration — users perceive this as lag. Tasks cannot be preempted: cooperative scheduling means your code must split itself. Microtask starvation is nastier: a microtask that re-queues itself forever (function loop() { Promise.resolve().then(loop); }) never yields — no task, no render, no input, tab effectively frozen — because the checkpoint drains until empty and the queue never empties. DOM events are tasks: a click handler that runs for 200 ms delays the paint of the visual response, hurting Interaction to Next Paint (Module 25).

!Three misconceptions to retire
(1) “The event loop is one FIFO queue” — it is several task queues with implementation-defined prioritization plus a separate microtask queue. (2) “Every task renders a frame” — rendering happens only at rendering opportunities; many loop iterations skip it, and busy loops may skip several. (3) “setTimeout(fn,0) runs before paint” — microtasks and usually the rAF/paint phase run first; timers are tasks.

Workers and other event loops

Workers have their own event loops — same WHATWG machinery, no rendering steps (there is nothing to paint), and slightly different available task sources. A service worker’s loop can be spun up on demand and terminated when idle (Module 22). Node.js implements a different but familiar loop (libuv): timers phase, poll for I/O, check phase (setImmediate), with the microtask queue drained between phases and process.nextTick running before Promise microtasks. The concepts transfer; the phase boundaries do not — do not quote Node’s phases as if they were browser behavior.

Layout, Reflow & Geometry

What layout computes — and how read-after-write forces it synchronously

What layout actually computes

Layout (historically “reflow” in Gecko-era terminology) turns the style-resolved tree into a tree of boxes with geometry: for every rendered element it computes position and size, resolves auto dimensions, places text lines, and establishes scroll regions. Inputs: computed styles (Module 07) and the containing geometry; outputs: used values — concrete pixel positions and sizes (the values getBoundingClientRect() reports). Layout runs per formatting context: block flow stacks boxes vertically; inline flow wraps text within lines; flex layout distributes space along main/cross axes from flex-direction, flex-grow/shrink, align-*/justify-*; grid layout resolves tracks (explicit sizes, fr fractions, auto tracks with min/max content contributions) then places items into cells. Intrinsic sizing is content-driven measurement — min-content (longest unbreakable unit), max-content (no wrapping), fit-content — and it is what makes tables, floats and width: auto expensive: measuring text requires font metrics.

Two structural concepts do a lot of work. The containing block is the reference a box positions and sizes itself against — normally the nearest block ancestor’s content box, but absolutely-positioned elements use the nearest positioned ancestor, and fixed elements the viewport. The viewport is the visible window; scroll containers are boxes with overflow creating a scrollable region — the scrollport. Coordinate systems layer on top: page coordinates (document origin), client/viewport coordinates (what mouse events report), and offsets relative to the containing block — plus device pixel ratio (DPR): CSS pixels × DPR = physical pixels; a 2× display renders each CSS pixel with a 2×2 physical grid, which is why rasterization costs grow quadratically with DPR.

Layout invalidation and dirty bits

Layout is incremental. Marking an element’s width changed sets dirty bits up and down the tree as needed; the next layout pass processes only dirty subtrees. But dirt spreads: a width change dirties descendants (their containing block changed) and may dirty siblings (content reflowed); a height change at the top of a document can dirty nearly everything below it. Some changes are cheap and localized (a leaf’s background color causes no layout at all); others are structurally expensive (flex/grid redistribution, table column resizing, position flips). Browsers also batch: multiple DOM writes before a forced read coalesce into one layout pass.

Forced synchronous layout

Here is the trap. Layout is normally deferred until needed (right before paint). But several APIs require up-to-date geometry to answer: getBoundingClientRect(), offsetWidth/Height, clientWidth/Height, scrollWidth/Height, getComputedStyle() on geometry-dependent properties, scrollIntoView(), window.innerHeight in some cases. If the DOM is dirty when you call one, the browser must run layout synchronously, right now, inside your JavaScript. That is a forced synchronous layout. It is not incorrect — sometimes you genuinely need the measurement — it is a cost. The pathology is calling these APIs in a loop with writes in between:

● THRASHING — read ↔ write loop
items.forEach(item => {
  // read (forces layout: DOM was
  // dirtied by the previous write)
  const h = item.offsetHeight;
  // write (dirties layout again)
  item.style.height = (h * 1.1) + 'px';
});
// N items → up to N forced layouts
● BATCHED — reads then writes
// phase 1: all reads (one layout,
// still clean from the last paint)
const heights = items.map(i => i.offsetHeight);

// phase 2: all writes (one invalidation)
items.forEach((item, i) => {
  item.style.height = (heights[i] * 1.1) + 'px';
});
// 2 layout passes total: 1 read + 1 write

This alternating pattern is layout thrashing. The fix is always the same: batch reads and writes — read everything you need first, then write everything. When interleaving is unavoidable, frameworks use double-buffering (write to a detached clone or virtual representation, measure there, apply once). FastDOM is a classic library implementing read/write phase scheduling; modern frameworks batch DOM updates for the same reason. ResizeObserver is the structural replacement for resize polling: it fires callbacks with the new size after layout commits, without you forcing it — and it batches all elements per frame.

iGeometry API cheat sheet
getBoundingClientRect() — viewport-relative box (x, y, width, height, plus cumulative right/bottom). offsetWidth/Height — layout size including border+padding (integer-rounded). clientWidth/Height — padding box minus scrollbars. scrollWidth/Height — full scrollable content size. offsetTop/Left — offset from offsetParent. All of them may force layout when the DOM is dirty; use them deliberately.

Paint, Rasterization & Compositing

Display lists, tiles, GPU layers — and why more layers is not more better

Stage names and threading in this module describe the Blink-style pipeline (paint records → tiles → compositor). Gecko and WebKit implement the same concepts with different names and splits. What is universal: paint order, stacking contexts, and the trade-offs of layer promotion.

Paint records and display lists

Paint does not touch pixels directly. It generates an ordered list of drawing operations — conceptually “draw rect here, then this text run, then this image” — called paint records, collectively a display list. The order is specified: CSS painting order walks stacking contexts back-to-front, and within them backgrounds, borders, descendants, then positioned elements. This indirection is what makes painting cheap to skip: unchanged records are not regenerated, and the same records can be replayed for rasterization at any scale (zoom, DPR) or re-tiled for a scroll.

Paint invalidation marks the region or items that must be regenerated. A color change invalidates one element’s paint; a size change that also moved siblings invalidates more. The smaller and more local the invalidation rect, the cheaper the frame — the classic reason a fixed full-screen overlay repaint can be catastrophic (it dirties the whole viewport) while animating a small promoted element is nearly free.

Rasterization and tiles

Rasterization executes paint records into pixels. The work is divided into tiles (a grid of e.g. 256×256 px areas) so that only affected tiles re-rasterize, tiles near the scroll direction are pre-painted ahead of time, and the work parallelizes across raster worker threads and the GPU. Output: textures in GPU memory. At DPR 2, each tile costs 4× the pixels; at 3×, 9× — texture memory and fill cost scale quadratically. Content that re-rasterizes every frame (animated gradients as backgrounds, filter noise, giant blurred shadows) is the paint-heavy class of jank.

The compositor (in Blink: the renderer’s compositor thread plus the GPU process’s display compositor) assembles layer textures into the final frame, applying transforms and opacity. Elements get their own compositor layers for reasons including: 3D or active transform/opacity animations, will-change: transform/opacity, accelerated video/canvas, position:fixed/sticky in some configurations, and overflow scrolling areas. Stacking contexts are not layers: a stacking context is a CSS paint-order concept (z-index, opacity < 1, transforms all create one); a compositor layer is an implementation-level texture. Every promoted element creates a stacking context, but most stacking contexts never become layers.

will-change: power tool, footgun

will-change: transform tells the engine “a transform is coming; promote me now.” Used precisely — on the handful of elements that will animate, ideally toggled on before and off after — it removes the first-frame promotion jank. Sprinkled everywhere, it multiplies texture memory (each layer a full-resolution bitmap × DPR), increases compositing cost per frame, can break the browser’s own heuristics, and on memory-constrained devices causes eviction churn. Layer promotion and demotion are engine decisions: layers are created on demand and dropped when the reason disappears; treat hints, not your mental model of layer counts, as the API.

!Transform/opacity, honestly
“Animate only transform and opacity” is the right default because these properties can be applied by the compositor to an existing texture — no relayout, no repaint, no re-raster. It is a capability, not a guarantee: the element still needs to be layer-eligible, the animation must be one the engine runs on the compositor thread (CSS transitions/animations of transform/opacity, and rAF-driven changes usually qualify), and layout-affecting properties (width, top, font-size) never do. Overdraw is the sibling cost: overlapping translucent layers make the GPU paint pixels it will immediately cover — the Layers/Rendering panels expose it.

Events, Propagation & Browser Input

Capture, target, bubble — passive listeners, hit testing, input latency

The propagation model

When an event occurs, the browser computes its target (via hit testing: walking the painted, transformed geometry to find the topmost element under the pointer) and then dispatches through three phases: capture from the window down to the target’s parent, target (listeners on the target itself, in registration order — capture/bubble distinction collapses here for legacy listeners), and bubble back up to the window. Not every event bubbles (focus/blur don’t; focusin/focusout are the bubbling equivalents); capture works for all events, which is why library authors reach for it.

DIAGRAM 13Propagation path for a click on a button inside a card

stopPropagation() halts further propagation to other elements; stopImmediatePropagation() also cancels remaining listeners on this element. preventDefault() is orthogonal: it cancels the browser’s default action (following a link, submitting a form, starting a scroll) without stopping propagation. Defaults run after dispatch completes, and only if no listener prevented them.

Pointer, mouse, touch, keyboard, wheel, focus, input

Pointer events (pointerdown/move/up) unify mouse, touch and pen with pointerType; they are the default choice for custom interactions, with pointer capture (setPointerCapture) keeping events flowing to an element even when the pointer leaves it — the clean fix for drag-outside glitches. Mouse, touch and wheel events remain for compatibility and specific semantics. touch-action declares which gestures the page handles itself, letting the browser handle the rest without waiting for JS. Keyboard events (keydown/keyup) precede the corresponding input/beforeinput events on editable targets; the input event is the one that reflects the value after the edit. Focus events pair with :focus-visible styling so keyboard users get outlines while pointer users do not. beforeinput enables interception of edits; composition events (compositionstart/update/end) matter for IME input — treating IME text as final during composition is a classic editor bug.

Passive listeners and scroll performance

To scroll smoothly, the compositor thread cannot wait for a JS touchstart/wheel listener that might call preventDefault(). A passive listener (addEventListener(type, fn, { passive: true })) promises never to prevent the default, so scrolling starts immediately on the compositor. Since Chrome 56 touchstart/touchmove/wheel listeners on window/document are passive by default — calling preventDefault() in them is ignored with a console warning. The pattern this forces: listen passively for gestures you merely observe; listen non-passively only for the narrow cases where you truly cancel a default, and keep those handlers fast.

Event dispatch and the event loop

Dispatching an event to its listeners is itself work on the main thread: the input task runs hit testing, propagation and your handlers, then — if a rendering opportunity follows — style/layout/paint for the visual response. Input latency (the delay from physical event to painted response) therefore decomposes into: input delivery, your handler time, and the wait for the next rendering opportunity. This chain is exactly what INP measures (Module 25): a 200 ms handler paints its feedback 200+ ms after the tap. Moving heavy work off the interaction (optimistic UI first, real work after), splitting long handlers with scheduler.yield() or chunking, and keeping animations compositor-driven are the structural fixes.

Animation, Scrolling & Frame Scheduling

CSS vs JS animation, rAF, observers, reduced motion, long animation frames

Three ways to animate

CSS transitions interpolate a property when its value changes, with a declared duration/easing — ideal for state changes (hover, open/closed). CSS animations run keyframe timelines without triggers, loop, pause and reverse declaratively. Both, for transform/opacity on eligible elements, are executed by the compositor thread: the browser records start/end states once, then produces frames even while the main thread is busy — this is why a spinner animated with CSS keeps spinning while JS blocks, and janks instantly if animated with top/left in JS. JavaScript animations driven by requestAnimationFrame compute values per frame on the main thread: necessary for physics, gesture-driven or chained logic, but hostage to main-thread congestion. Prefer CSS for presentation, rAF for logic, and never animate layout properties when a transform expresses the same motion.

Frame scheduling rules of thumb: one rAF chain, not several competing ones (or a thin scheduler atop them); compute from the callback’s timestamp, never from wall-clock assumptions (120 Hz displays halve your dt); stop chains when hidden — rAF pauses in background tabs anyway (timers do not, which wastes battery); and keep each callback under a few milliseconds, since style/layout/paint still have to fit in the budget.

Scrolling and scroll-linked effects

Scrolling is the compositor’s crown jewel: with layer-ized content, scrolling moves textures on the compositor thread at display speed. JS-driven scroll effects (parallax, sticky headers, scroll shadows) historically ran on scroll events — a task per scroll, jank-prone. Modern tools move the work: scroll-driven animations (animation-timeline: scroll() / view()) let the compositor scrub CSS animations from scroll position with zero JS; IntersectionObserver reports visibility transitions asynchronously (lazy loading, reveal effects) without scroll listeners; position: sticky replaces JS-pinned headers outright. Smooth scrolling (scroll-behavior: smooth, scrollIntoView({behavior:'smooth'})) is engine-interpolated — never re-implement it with a timer loop.

Observers: the async observation pattern

IntersectionObserver (visibility thresholds), ResizeObserver (size changes, batched after layout), MutationObserver (DOM changes, microtask-batched) and PerformanceObserver (metric entries) share one design: register interest, let the browser do the watching natively, receive batched callbacks. They replace polling loops and event storms with engine-side observation — the right default whenever the question is “tell me when X changes”.

Reduced motion and long animation frames

prefers-reduced-motion is a media query (and a matching media feature for JS): users who have asked the OS to minimize motion should get fades instead of slides, no parallax, no autoplaying movement — respect it as an accessibility requirement, not a nice-to-have. For diagnostics, the LoAF API (PerformanceObserver with type 'long-animation-frame') reports frames whose total duration exceeded 50 ms, including the scripts, styles and layout that composed them — the frame-level complement to long tasks, and the natural place to start when an animation “stutters sometimes.”

iAnimation performance checklist
Animate transform/opacity, not geometry · prefer CSS/compositor animations for presentation · one rAF chain, delta-time based · stop chains when idle or hidden · scroll effects via scroll-driven CSS or observers, not scroll listeners · honor prefers-reduced-motion · verify in the Performance panel: a healthy animation shows green compositor frames and empty main-thread lanes.

Browser Networking Fundamentals

The stack from the browser’s point of view — latency, proxies, CDNs, limits

The browser’s network stack

Everything a page loads travels a layered stack. The application layer is HTTP (Module 18) over transport (TCP or QUIC-over-UDP) over the internet layer (IP addressing and routing), with TLS inserted between HTTP and transport for https. The browser’s network service wraps this with policy: a connection pool per proxy/origin, a prioritization scheme for pending requests, the HTTP cache (Module 20), cookie attachment, and request throttling for background tabs. Above it all, DNS turns names into addresses before any packet can flow (Module 17).

Each hop adds latency and can add caching, compression or rewriting. In production incidents, knowing which hop misbehaved is half the diagnosis — which is what request Initiator, cache status and timing breakdowns in the Network panel reveal.

Latency, bandwidth, throughput

Bandwidth is capacity (bits per second); throughput is what you actually achieve; latency is the delay of a single round trip — and for the web, latency dominates. A typical request pays: DNS lookup + connection establishment (1 RTT for TCP, plus 1–2 for TLS) + request transmission + server time + response transmission. A 100 ms RTT link pays 300+ ms before the first byte of a fresh HTTPS navigation, regardless of bandwidth. Packet loss compounds this: TCP treats loss as congestion (Module 17), retransmits, and backs off its sending rate. The engineering consequences are the whole of Module 19: reduce round trips (preconnect, HTTP/3 0-RTT, H2 multiplexing), reduce bytes (compression, responsive images), and move data closer (CDNs).

Connections and pooling

The browser reuses connections: keep-alive (HTTP/1.1 default) leaves a TCP connection open for subsequent requests to the same origin. HTTP/1.1 parallelism comes from multiple connections — browsers allow about 6 per origin (an implementation convention, not a standard). HTTP/2 multiplexes many streams over one connection per origin (Module 18), changing the calculus: fewer handshakes, but head-of-line possibilities at the TCP layer. Proxies sit in the middle (forward proxies for enterprises, reverse proxies like nginx/HAProxy at the edge); a proxy terminates one connection and opens another, and can cache, route or transform. Connection limits and pool behavior differ per engine — measure yours rather than assuming a number.

That is why “just add a font from a third-party domain” can cost an extra 120 ms of setup — and why preconnect exists to pay it early and in parallel.

DNS, TCP, QUIC & TLS

How names resolve, connections open, and encryption starts

DNS: resolving a name

DIAGRAM 14Recursive DNS resolution (cache miss)

The browser asks its resolver (OS-configured, or its own DoH endpoint). On a cache miss, the resolver walks root → TLD → authoritative, caching each answer for its TTL. Answers are A (IPv4) or AAAA (IPv6) records; CNAME aliases chain to a canonical name first (each hop can cost another lookup — why deep CNAME chains slow first loads). Failures surface in the browser as ERR_NAME_NOT_RESOLVED: expired delegations, DNSSEC validation issues, or split-horizon names that only resolve inside a corporate network. DNS over HTTPS (DoH) and DNS over TLS (DoT) encrypt the client-resolver leg, changing who can observe (and spoof) lookups — and sometimes changing which answers you get, a classic “works on VPN, fails at home” cause.

TCP: the reliable workhorse

Connection established: 1 round trip before the first HTTP byte can leave. Termination is a 4-way FIN/ACK exchange; abandoned connections time out.

TCP provides reliability over an unreliable network: sequence numbers and acknowledgments order bytes and detect loss; retransmission resends unacknowledged segments; flow control (the receive window) keeps a fast sender from drowning a slow receiver; congestion control (slow start, then congestion avoidance/BBR-style probing — algorithm choice is OS/endpoint-specific) throttles senders to protect the network, meaning throughput ramps up over several RTTs rather than jumping to line speed. The structural weakness for the web: head-of-line blocking at the transport — one lost segment stalls all data behind it, even data for other HTTP requests multiplexed over the same connection. Connection reuse (keep-alive) avoids repeated handshakes, and TLS session resumption shortens the crypto part, but the HOL problem is inherent to a single ordered byte stream.

QUIC: transport rebuilt for HTTP

QUIC (RFC 9000) is a reliable, secure transport built on UDP. Each QUIC connection carries independent streams: stream 5 losing a packet stalls stream 5 only — no transport head-of-line blocking across streams, the key fix HTTP/2 needed. QUIC integrates TLS 1.3 (the handshake is the connection establishment), collapsing connect+crypto into about 1 RTT, with 0-RTT resumption for repeat visits. Connection migration lets a connection survive network changes (Wi-Fi → cellular) because it is identified by connection IDs, not by the 4-tuple. HTTP/3 (RFC 9114) is HTTP semantics over QUIC — methods, headers and status codes are the same; the transport underneath differs, and QPACK replaces HPACK header compression with awareness of stream reordering. QUIC lives in user space (browsers ship their own implementations), which speeds evolution but costs CPU relative to kernel TCP on some workloads — a real, measured trade-off.

The handshake combines asymmetric cryptography (key exchange — agreeing on a shared secret without ever transmitting it; certificate signatures proving identity) with symmetric encryption (bulk data, fast, keys derived from the shared secret). Certificates bind a public key to a hostname, issued and signed by certificate authorities the OS/browser already trusts; validation walks the chain to a trusted root and checks hostname, validity window and (in modern practice) revocation via stapled OCSP or CRLite-class mechanisms. ALPN negotiates the application protocol (h2 vs http/1.1 vs h3) during the same round trip. What TLS gives you: confidentiality, integrity, and server authentication. What it does not: anonymity of the destination (DNS + SNI leak it), protection of a malicious server, or anything about content the page itself loads insecurely (mixed content — Module 23).

HTTP Protocols & Browser Request Lifecycle

Messages, H2/H3 mechanics, Fetch, CORS — the request’s whole life

Messages: request and response

An HTTP request is a method, a target, a version, headers, and an optional body. A response is a status code, headers, and an optional body. Methods carry semantics: GET (safe, cacheable), HEAD (headers only), POST (submits, not idempotent), PUT/DELETE (idempotent by contract), PATCH, OPTIONS (used by CORS preflights). Status classes: 1xx informational, 2xx success (200, 204 no content, 206 partial content for ranges), 3xx redirects (301/308 permanent, 302/307 temporary, 304 not modified — the cache revalidation response with no body), 4xx client errors (400, 401, 403, 404, 429), 5xx server errors.

Compression applies to text responses (gzip/Brotli/Zstandard via Accept-Encoding) and shrinks transfer size dramatically; it is why bundles minify+compress well and why images (already compressed) must not be re-compressed. Content negotiation (Accept, Accept-Language) lets the client express preferences the server may honor via Vary — and Vary is also the cache’s keying instruction (Module 20). Range requests (Range: bytes=1000- → 206) enable media seeking and resumable downloads.

HTTP/2: multiplexing on one connection

HTTP/2 (RFC 9113) reframes HTTP as binary frames over streams: many requests and responses interleave on a single TCP connection. Headers are compressed with HPACK (shared, indexed tables; QPACK is the QUIC-aware successor that tolerates reordering). Stream prioritization lets clients signal dependencies and weights — concepts browsers implement differently (and which evolved from the original dependency tree to extensible priorities); treat priorities as hints the server may honor. Multiplexing removes the HTTP/1.1 request queue, but not TCP’s byte-stream head-of-line blocking: one lost packet stalls every stream sharing the connection — which is exactly the problem HTTP/3 exists to solve (Module 17). Server push existed in H2 and was removed from browsers as a missed bet: hints (Module 19) do the job better.

Fetch: the browser’s request pipeline

fetch() is the API over the Fetch Standard’s pipeline: build a Request (method, URL, headers, body, mode, credentials, cache hint), run it through service-worker interception (Module 22), HTTP cache lookup (Module 20), and the network stack; get a Promise<Response> with status, headers, and body accessors. XMLHttpRequest is the legacy predecessor — still functional, no longer the right default (no streaming request bodies, clunkier response handling). Two features matter constantly:

CORS: when the browser says no

The same-origin policy (Module 04) blocks reading cross-origin responses. CORS is the opt-out mechanism: the server declares, in response headers, which origins may read what. “Simple” requests (GET/HEAD/POST with safe headers) go straight through, and the browser exposes the response only if Access-Control-Allow-Origin matches. Requests that are “not simple” — other methods, custom headers like Authorization or Content-Type: application/json — trigger a preflight: the browser first sends OPTIONS with Access-Control-Request-* headers, and only proceeds if the server approves method, headers and origin. Preflight responses are cacheable (Access-Control-Max-Age) — otherwise every call pays an extra round trip. With credentials: 'include', cookies cross origins only if the server sets Access-Control-Allow-Credentials: true and an explicit origin (never *). The #1 debugging rule: CORS failures are browser-enforced, server-configured — the fix is on the server; the browser is just the messenger (and Postman, having no origin, never triggers it).

Resource loading priorities

The browser assigns every request a priority (Chromium exposes it in the Network panel; the scheme evolved from H2 dependency trees to the Priority Hints fetchpriority attribute). CSS is high (render-blocking), visible images medium, scripts depend on placement and attributes, fonts race text rendering. You influence priorities with placement, async/defer, fetchpriority="high" on the LCP image, and preload hints — the mechanics Module 19 covers in depth.

Resource Loading, Preloading & the Critical Rendering Path

Discovery, priority, hints — and the chain that gates first paint

Discovery: the preload scanner

The HTML parser is linear, but the browser does not wait for it to find your resources one by one. A preload scanner (Chromium name; every engine has an equivalent implementation) races ahead over the raw markup, discovering src/href references before the DOM reaches them, and starts those downloads early — even ones the parser has not reached yet, including those blocked by a parser-blocking script ahead of them. This is why “put scripts at the bottom” matters less than it used to (the scanner still sees images early), and why resources only discoverable by JavaScript (a URL built in a string, an image decided by a framework) load late: no scanner can see them.

Render-blocking versus parser-blocking

Two different blockers, often conflated. Render-blocking: CSS (and sync scripts, transitively) prevents painting — the browser refuses to show unstyled content. Parser-blocking: a classic <script> halts DOM construction until fetched and executed. defer removes parser blocking while preserving order and pre-DOMContentLoaded execution; async removes both but forfeits order. Stylesheets additionally block script execution that follows them (a sync script after a pending stylesheet waits, because the script might query computed styles) — the reason “CSS before JS” ordering matters.

Browser Caching & Offline Capabilities

Freshness, validators, revalidation, partitioning — and who owns which cache

Four caches, four owners

When engineers say “the browser cache” they may mean any of four different stores. The HTTP cache (memory and disk) is browser-managed: it follows HTTP headers, is shared across navigations, and survives restarts (the disk part). The memory cache inside a renderer (or the browser process) holds short-lived entries for the current session (decoded images, small resources). The Cache Storage is application-managed: your service worker decides what goes in, what is served and when it is updated. CDN caches are server-side and outside the browser entirely. Confusing these four is the root of most “why do users see old content” debugging failures — each has a different invalidation lever.

DIAGRAM 18Request paths: service worker, HTTP cache, network

Freshness and Cache-Control

A cached response is fresh until its age exceeds its lifetime, derived from Cache-Control: max-age=N (relative, robust) or Expires (absolute, clock-sensitive). Directives compose: public (any cache may store) vs private (browser only — CDN must not keep it), no-cache (store, but revalidate every use — the name is misleading: it does not forbid storing), no-store (never store at all — sensitive data), immutable (the resource will never change during freshness — safe with content-hashed URLs), s-maxage (shared-cache lifetime), must-revalidate (stale entries may not be served without a successful revalidation). A response with neither validators nor freshness directives falls into heuristic caching — browsers guess from Last-Modified — which is why “unpredictable caching” usually means “unspecified caching”.

Validators and revalidation

When a stored response is stale (or no-cache), the browser sends a conditional request: If-None-Match: "abc123" (the stored ETag — an opaque validator the server generates, commonly a content hash) or If-Modified-Since: <date> (the stored Last-Modified). If nothing changed, the server answers 304 Not Modified with headers only — no body — and the cached copy’s freshness is renewed. ETags are stronger (byte-precision); weak validators (W/"...") allow semantically-equivalent responses. Cache invalidation in practice is therefore: version your URLs with content hashes (app.a17f.js) + max-age=31536000, immutable for assets, and short/no caching (no-cache with ETag) for HTML — so the HTML references new hashes and drags the world forward. The classic failure, “stale HTML served for days”, is a max-age too long on the document.

Partitioning and third parties

Modern browsers partition the HTTP cache (and other storage) by top-level site: the same image loaded by site A and site B is cached twice. Partitioning dismantles cross-site tracking via cache timing and changes third-party caching economics (a shared CDN asset is no longer shared across sites). standard storage partitioning is now the interoperable direction; details of keying vary. The developer-facing rule: never assume your third-party resources are “already cached” from another site.

Offline with service workers

Cache Storage (caches.open('v2'), cache.put/match/delete) is programmable storage for requests/responses, used by service workers (Module 22) to build offline behavior: cache-first, network-first, stale-while-revalidate strategies implemented in your own fetch handler. It is not an HTTP cache: it obeys no headers, never revalidates, and serves exactly what you stored until your code decides otherwise — which is both its power (deterministic offline) and its trap (serving outdated app versions, Module 28’s case study 13). IndexedDB backs dynamic data offline (Module 21). Cache poisoning considerations: a compromised or buggy service worker can persist bad responses; mitigate with strict update flows, versioned cache names and cleanup on activate.

Cookies in detail

A cookie is set by Set-Cookie (or document.cookie, when not HttpOnly) with attributes: Domain (defaults to the exact host; setting a parent domain shares it across subdomains), Path (scoping within the origin’s paths — a coarse filter, not a security boundary), Expires/Max-Age (absent → session cookie), Secure, HttpOnly, and SameSite: Strict (never sent on cross-site navigation), Lax (top-level safe navigations only — the modern default), None (cross-site too, but requires Secure). SameSite reshaped CSRF defense (Module 23): cross-site POSTs from forms no longer carry session cookies by default. Quotas, eviction, persistence

Storage is quota-based per origin (and partitioned per top-level site for third-party contexts). Under pressure, browsers evict best-effort storage: whole origins’ data can vanish. Calling navigator.storage.persist() requests persistent storage — the browser may grant it (installed PWAs, user engagement) and then commits to not evicting without consent. navigator.storage.estimate() reports usage and quota. Design rule: treat all client storage as a cache that can disappear — keep the source of truth server-side, and make cold-start (empty storage) a fast, normal path.

Cross-tab coordination

Same origin across tabs is shared storage territory: storage events (window.addEventListener('storage')) fire in other tabs when localStorage changes — a built-in pub/sub for simple cases. BroadcastChannel is the cleaner message bus (postMessage-style, no storage abuse). The Web Locks API provides async mutexes across tabs — the correct tool for “only one tab runs the migration / sync at a time”, replacing fragile localStorage lock hacks. SharedWorker can centralize state for some engines (Safari removed it; prefer the above).

Service Workers, Web Workers & Background Processing

Moving work off the main thread — and intercepting the network

Why workers exist

The main thread is a single lane shared by parsing, style, layout, paint, input and JavaScript (Modules 10–14). Workers give you additional threads, each with its own event loop, for work that should not block the page: parsing gigabytes of CSV, heavy crypto, image processing, background sync. Workers cannot touch the DOM — not because of a technicality, but because concurrent DOM mutation from multiple threads would break every rendering invariant the engine maintains. Communication is message-based, with data copied (structured clone) or transferred (transferables).

DIAGRAM 19Worker architectures: dedicated, service, shared

Messaging: clone, transfer, share

postMessage(data) serializes data with the structured clone algorithm — deep copy of most JS values, but not functions, DOM nodes or prototypes (plain data only, plus some typed objects). Transferable objects (ArrayBuffer, MessagePort, OffscreenCanvas) move ownership zero-copy: the sender’s reference is neutered, the receiver gets the buffer — the pattern for shipping large binary data without copying. SharedArrayBuffer allows genuine shared memory, but requires cross-origin isolation (COOP+COEP headers, Module 23) because of Spectre-class side channels; Atomics provide the synchronization. MessageChannel gives direct port-to-port messaging (also the basis of MessageChannel-based yielding, Module 10).

Service worker lifecycle

Registration (navigator.serviceWorker.register('/sw.js')) starts an async install. Install: pre-cache the offline shell; failure rejects registration. Waiting: a newly installed worker waits while an older one controls pages (avoid skipWaiting unless you also reload, or you serve a mix of versions — Module 28 case study). Activation: old caches deleted (clients.claim() takes over existing pages). Control: fetches from controlled pages fire fetch events in the worker, which can answer from Cache Storage, pass to the network, or synthesize. Termination: the browser stops the worker when idle and restarts on events — a service worker must be stateless across events, keeping durable state in Cache Storage/IndexedDB. Background Sync defers work until connectivity; the Push API wakes the worker on server push (both permission-gated). Update checking happens on navigation and periodically: byte-difference in the script file triggers the install/wait/activate cycle again.

!Comparing the three worker kinds
Web Worker = compute offload for this page (dies with it). Service Worker = network proxy + lifecycle controller for an origin (no DOM, no synchronous APIs, may be killed between events). Worklet = engine extension point (audio/paint/animation) with strict per-frame execution rules. Choosing wrong shows up as: trying to touch document in a worker (throws), storing state in a service-worker global (lost on termination), or expecting push without permissions.

Browser Security Architecture

SOP to CSP to COOP/COEP — who enforces what, and where the boundaries are

The model in one picture

Browser security is layered defense: the same-origin policy isolates data by origin; process isolation (site isolation) puts that isolation into OS process boundaries; sandboxing limits what a compromised process can do; transport security (TLS) protects data in flight; context security (secure contexts, permissions) gates powerful APIs; and content security policies constrain what injected script could do even if everything else failed. Each layer assumes the previous one might break.

CSP: the policy language

Content Security Policy is a response header (Content-Security-Policy) declaring allowed sources per directive: script-src, style-src, img-src, connect-src, frame-src, object-src 'none', frame-ancestors, base-uri, and report-uri/report-to for violation reporting. The modern pattern: strict default-src plus per-directive exceptions with nonces (script-src 'nonce-r4ndom') or hashes, avoiding unsafe-inline/unsafe-eval. Deploy via Content-Security-Policy-Report-Only first, watch reports, then enforce — a broken CSP breaks the whole site, which is why staged rollout is standard practice. Permissions Policy (Permissions-Policy: geolocation=(self)) complements CSP by disabling platform features per frame; Referrer Policy controls how much URL leaks in Referer.

COOP, COEP, CORP: the isolation headers

Three response headers cooperate for cross-origin isolation. COOP (Cross-Origin-Opener-Policy: same-origin) cuts the window.opener relationship with cross-site openers. COEP (Cross-Origin-Embedder-Policy: require-corp) makes the page refuse subresources that do not opt in via CORP (Cross-Origin-Resource-Policy) or CORS. Together they put the document in a crossOriginIsolated state — the precondition for SharedArrayBuffer and precise timers, and the mitigation context for Spectre-style attacks. The practical cost: every embedded third-party resource must explicitly opt in, which is why enabling COEP breaks naive embeds (Module 28 case study 19).

Secure contexts and permissions

Powerful APIs (geolocation, camera, notifications, service workers, Web Crypto’s subtle crypto) require a secure context: https, localhost, or file: in some configurations. On top of that, many require an explicit permission grant — the browser mediates a user prompt, remembers the decision, and exposes status via navigator.permissions.query(). Feature detection must therefore be two-phase: “does the API exist here?” and “is using it permitted here?” A page that calls navigator.geolocation over plain http gets nothing on modern browsers — not a prompt.

iframe security

iframes are mini-browsers with their own origin, event loop and document. The sandbox attribute strips privileges (scripts, forms, popups, same-origin access) unless re-enabled per-token; a sandboxed frame gets an opaque origin. Cross-origin frames cannot be scripted from the parent (SOP); same-origin frames can, which is the classic “third-party widget turned out to be same-origin” audit finding. Embedders restrict what frames may do with Permissions Policy; embedees refuse framing with frame-ancestors. The postMessage protocol — with targetOrigin checks and origin validation on receive — is the sanctioned channel across the boundary.

Browser Memory Management & Garbage Collection

Reachability, generational collection, detached nodes — and finding real leaks

GC specifics below describe V8’s design as the worked example (Orinoco-class pipeline: scavenger for young objects, mark-sweep-compact for old, incremental + concurrent marking). SpiderMonkey and JavaScriptCore solve the same problems with different collectors. The leak patterns, however, are engine-independent.

Allocation, stack and heap

Primitives and references live in stack frames and die with them (Module 09). Objects live on the heap: allocation is fast (bump-pointer in the young generation), but lifetime is unbounded, so reclamation is the collector’s job. Reachability is the core concept: an object is live if it can be reached from a root — the global object, the current call stack’s locals, active handles — by following references. Everything unreachable is garbage, even if it references other live objects: cycles are collected fine by tracing collectors (the old “IE needed cycle-breaking” folklore is about reference counting, not modern tracing GC).

DIAGRAM 21Reachability: what survives a collection

Generations and pause behavior

Most objects die young (intermediate arrays, wrapper objects, per-request state). V8 exploits this: the young generation is collected by a scavenger (semi-space copy: live objects copied out, everything else vanishes with the from-space) — fast, frequent, tiny pauses. Objects surviving two scavenges are promoted to the old generation, collected by mark-sweep-compact: mark traces reachability from roots; sweep frees unmarked memory; compact slides survivors to fight fragmentation. Major GCs are expensive, so marking is incremental (interleaved with JS) and concurrent (on background threads), shrinking main-thread pauses to (usually) low milliseconds — but a page that churns gigabytes through the old generation still feels GC pauses as jank. Practical guidance: reuse buffers, avoid per-frame allocation storms in animations (pool objects or use typed arrays), and watch the Memory panel’s sawtooth — deepening sawteeth with a rising baseline is the leak signature.

The leak patterns

A memory leak in a GC world is never “the collector missed it” — it is an unintended retainer: a live path from a root to memory you consider dead. The five canonical patterns:

Weak references are the language-level tools for cache-keyed-by-object patterns: WeakMap/WeakSet hold entries that vanish when the key object does (no enumeration, no iteration). WeakRef keeps a weak hold on an object itself; FinalizationRegistry schedules a callback after collection — a last-resort cleanup hook for external resources, explicitly not a destructor (timing is non-deterministic, callbacks may never run).

Profiling and tab memory

The Memory panel’s tools map directly to this module: heap snapshots (compare two snapshots; the delta with a retainer chain through your data structure is the leak), allocation instrumentation on timeline (see allocation sites as they happen), and detached DOM tree groupings in snapshots (the smoking gun for pattern 1). Tab-level memory behavior — suspension, freezing, discard under pressure (Module 02) — is the OS-facing complement: memory pressure in the browser process evicts or freezes renderers, which is why a memory-hungry tab gets sluggish or discarded on mobile even without “leaking” in the JS sense.

Strategies: detection, enhancement, degradation

Feature detection asks the platform directly: if ('IntersectionObserver' in window), CSS.supports('container-type: inline-size'), typeof obj.method === 'function'. It beats UA sniffing because the UA string lies (historically and structurally). Progressive enhancement builds a functional baseline and layers richer behavior where the platform allows; graceful degradation builds the full experience and stubs the gaps. The first survives new browsers automatically; the second tends to break them. Polyfills implement missing APIs in JS (cheap for logic, dangerous for syntax — a polyfill cannot add new language syntax, which is transpilation’s job: → arrows, class fields, etc., compiled to older syntax). Vendor prefixes (-webkit-…) were the old experimental mechanism; they linger as compatibility debt — always write the standard property alongside.

Testing across the matrix

Cross-browser testing covers engines, not brands: Chromium, Gecko, WebKit (Safari — and its iOS-mandated WebKit rule). Prioritize by your analytics, but never ship a feature whose failure mode is catastrophic on your #2 engine. Responsive testing uses DevTools device emulation (viewport, DPR, touch) — with honest limits: emulation is not a phone (CPU/GPU class, memory pressure, network stack quirks, OS behaviors all differ). Real-device labs and cloud device farms exist because emulation lies at the edges. Automate the matrix where possible: Playwright-class drivers run real engines in CI; visual regression catches the “works but shifted 3px” class.

Console: expressions, console.table for data, console.trace, live expressions, log levels, and filters. Sources: breakpoints (line, conditional, DOM-change, event-listener, XHR/fetch), step controls, scope inspection, async stack traces, and source maps into your original TypeScript/framework sources. The five-question triage: does it reproduce in another engine? does it reproduce without your framework? what does the spec say the behavior is? does it reproduce in a fresh profile (extensions off)? is there an existing engine issue with your minimal repro? DevTools & Hands-On Investigation Guide

Eight panels — what each solves, what to inspect, and the false conclusions to avoid

!DevTools changes with every release
Panel names, sub-tabs and settings move between Chrome versions. This guide teaches workflows and evidence, not pixel-locations — when a label here does not match your build, look for the same capability (the command menu Ctrl/Cmd+Shift+P searches features directly). Firefox and Safari have strong equivalents for nearly every workflow below.

The universal investigation loop, whichever panel you open: reproduce the problem on purpose (throttling, cache state, interaction pattern) → capture the evidence (trace, snapshot, network log) → attribute (which item in the evidence explains the symptom?) → change one thing → re-capture and compare. The sections below apply the loop per panel, ending with the two things that waste the most time: false conclusions and unverified fixes.

Elements panel — the DOM and styles as they are

Solves“What is actually in the DOM? Which rules style this element? What geometry does it have? Who listens on it?”
Open & inspectRight-click → Inspect, or Ctrl/Cmd+Shift+C. DOM tree, Styles/Computed panes, Layout box model, Event Listeners, DOM breakpoints (subtree modifications, attribute changes, node removal), Accessibility pane.
Interpreting evidenceThe Styles pane shows the cascade in order: overridden rules struck through, inheritance marked, specificity visible in the order; the Computed pane shows the final value per property and which rule won. ::before/shadow roots are expandable; pseudo-classes can be forced (:hover, :focus) for debugging restyling without interacting.
False conclusionsA struck-through rule is not “wrong” — it lost the cascade (Module 07); check specificity/origin before blaming order. Elements panel edits do not persist — it is a live scratchpad. “No listeners shown” may mean the listener lives on an ancestor (delegation) or was added with capture on a parent.
Verifying a fixRe-inspect after the fix: winning rule correct, computed value as intended, box model matches design. For layout mysteries, combine with the Rendering panel’s paint flashing and Layout Shift Regions.

Console — expressions, errors, quick experiments

Solves“What is the value of X right now? What threw? Does this expression do what I think?”
Open & inspectF12 → Console. console.table for arrays, console.dir for objects, console.trace for callers, groups, timers, live expressions pinned to the top; filters by level/text/url; Preserve log across navigations.
Interpreting evidenceError objects carry real stack traces; click through to sources with source maps. Cross-origin errors without CORS headers may arrive sanitized (“script error”) — that itself is evidence (missing Access-Control-Allow-Origin on the script). Warnings about passive listeners, deprecated APIs and CSP violations point to specific lines.
False conclusionsLogging the same object twice shows its final state (live reference) — snapshot with structuredClone or JSON when you need the value at log time. console.log in a hot loop distorts timing measurements (Module 25: measure with performance.mark, not logs). Console runs in the page’s context (or the top/frame context you select) — the wrong context selector explains “my variable is undefined”.
Verifying a fixThe same expression that showed the bad value shows the good one — and the error no longer logs with the exact repro steps.

Sources panel — breakpoints and the running program

Solves“Why does the code take this path? What are the real values in scope? Where does this event lead?”
Open & inspectLine breakpoints, conditional breakpoints (logpoints), DOM-change and event-listener breakpoints (break when any listener of a type fires), XHR/fetch breakpoints, step in/out/over, the call stack and scope panes, watch expressions, async stack traces; source maps back to original sources; local overrides for iterating on built assets.
Interpreting evidencePause gives you the true program state: scope chains (Module 09) materialize in the Scope pane — closures visible as their environments. The call stack reads top-down from the pause; async stacks stitch the task boundary with a “(async)” marker — enabling them is the difference between a 3-frame and a 30-frame story.
False conclusionsPaused code is frozen: timers, rAF and events queue up and then all fire on resume — the resumed timeline is not a natural one. Optimized functions may show variables as “unavailable” (deoptimized inspection limits). A breakpoint that never hits usually means the code path runs in a different context (iframe, worker) or was tree-shaken from the bundle.
Verifying a fixRe-run the repro with the same breakpoint: the branch taken, scope values and stack should now match the intended design.

Network panel — every request, its timing, its cache fate

Solves“What loaded, in what order, at what cost, from where — and did it come from cache or network?”
Open & inspectRequest table (sort/filter/group), waterfall column, Headers/Payload/Response/Initiator/Timing tabs per request, Priority column, the Size column’s cache decomposition, throttling profiles, blocking, preserve log, replay XHR, copy as fetch/curl.
Interpreting evidenceThe Timing tab is Modules 16–20 as data: queueing (priority), DNS, initial connection, TLS, request/waiting (server), content download. Size shows “(memory cache)/(disk cache)” vs transferred bytes; Initiator chains reveal who triggered each request (the preload scanner vs a script). The waterfall’s shape exposes stalls: long flat gaps mean serialized discovery or blocking dependencies.
False conclusionsDevTools open disables some optimizations (bfcache, and historically some prerender/speculation) and its cache column can differ from a user’s run. “Status 200” with “(from cache)” is a cache hit — do not count it as network time. “from disk cache” may still cost decode time. CORS errors appear as failed requests with a security note — the response body is often genuinely there, just unreadable by JS (Module 18).
Verifying a fixRe-run with the same throttling and cache state: same rows, different timing/path. Screenshot the before/after waterfall; compare LCP resource discovery time specifically.

Performance panel — the rendering pipeline on tape

Solves“What did the main thread do all this time? Why was this frame late? What does the user actually experience?”
Open & inspectRecord a profile (with/without screenshots), then: the frame lane (green/red bars per frame vs the 60 Hz budget line), the main-thread flame chart (tasks colored by stage: scripting, rendering=style+layout, painting), long-task flags, the Bottom-Up/Call Tree/Event Log views, and the Interactions track for input timing. CPU and network throttling to reproduce field conditions.
Interpreting evidenceRead it as Modules 10–15: a long yellow task before a red frame is main-thread jank (split it); “Recalculate Style > 2000 elements” is a selector/invalidation problem (Module 07); “Layout” repeatedly inside a script loop is forced synchronous layout (Module 12); paint-heavy frames with simple scripting point to raster/layer issues (Module 13). The Interactions track decomposes INP: input delay (queue wait) + processing + presentation.
False conclusionsA trace is one sample of one machine: the absence of jank in your trace does not prove its absence on users’ devices (Module 25: field data is the arbiter). Long white gaps can be idle, throttling or process suspension — check the screenshots lane before assuming a hang. Flame chart widths include sampling overhead; rely on task-level durations, not micro-blocks.
Verifying a fixRecord the same repro after the change: frame bars turn green, the long task splits or moves off-thread, interaction timing drops. Keep both traces and compare side by side.

Memory panel — heaps, retainers, leaks

Solves“Is memory growing? What is retained, and by whom? Where do allocations come from?”
Open & inspectHeap snapshots (three over time beats two), allocation instrumentation on timeline, allocation sampling; in snapshots: sizes (shallow vs retained), constructors, the Detached DOM tree filter, and the Retainers pane showing the path from roots (Module 24’s chains, verbatim).
Interpreting evidenceThe leak workflow: snapshot → repro → snapshot → diff, sort by retained size delta, open the retainer chain of the biggest grower. If the chain ends in your data structure (a Map, an array, a listener’s closure), that is the leak — GC is never “broken”. Sawtooth JS heap with a flat baseline is healthy GC churn; a rising baseline across repros is a leak.
False conclusionsMemory not dropping after your action does not prove a leak — GC runs when it chooses; force GC from the panel first. Detached nodes in a snapshot are only a leak if something retains them (check the chain). DOM/memory numbers include renderer overhead — compare relative growth, not absolute totals.
Verifying a fixThe repro loop’s delta between snapshots shrinks to noise; the retainer chain of the previous grower no longer exists. Re-run the repro 10×: healthy memory oscillates, leaked memory climbs.

Application panel — storage, service workers, permissions

Solves“What has this origin stored? Which service worker is controlling the page? What permissions are granted?”
Open & inspectFrames tree; per-frame storage: cookies (with all attributes, editable), localStorage/sessionStorage, IndexedDB databases (browse object stores), Cache Storage (list cached request/response pairs), service workers (status: installing/waiting/active, update/skipWaiting controls, offline simulation, push emulation), storage quotas (usage & quota), manifests, and Clear storage actions.
Interpreting evidenceA “waiting” service worker while users report stale content is Module 22’s version-mismatch story visible in UI: the old worker still controls, the new one waits. Cookies here show exactly what requests carry: SameSite/Secure/HttpOnly attributes decide auth mysteries. Cache Storage contents reveal exactly what a cache-first SW will serve.
False conclusions“Unregister” the SW in DevTools fixes your browser only — users need the update flow. Cache Storage entries are not the HTTP cache: clearing one does not clear the other (Module 20). IndexedDB data belongs to the origin; testing in a different profile/origin shows empty stores, not lost data.
Verifying a fixReload under the panel: the active worker version is the new one, cache keys match the release manifest, cookies carry the intended attributes. Then verify in a fresh profile — a first-visit user sees no stale anything.

Lighthouse & Performance Insights — audits and opportunity lists

Solves“Give me a prioritized, reproducible assessment of this page right now.”
Open & inspectLighthouse tab (categories: Performance, Accessibility, Best Practices, SEO; device profile, throttling applied) or the Performance panel’ Insights lane. Opportunities (render-blocking resources, unused JS/CSS, image sizing, modern formats), Diagnostics (main-thread work, bootup time, DOM size), Core Web Vitals with their lab values.
Interpreting evidenceLighthouse numbers are lab data (Module 25): deterministic environment, simulated throttling in some modes. Use them to compare builds and find categories of problems; use field data (CrUX/RUM) to rank what users experience. Insights add trace-backed annotations (“LCP image was lazy-loaded”) with the offending element linked.
False conclusionsA 100 Lighthouse score does not mean fast for users (different devices, networks, cache states). The lab LCP can be wildly better or worse than field LCP; that is expected. Opportunities are estimates of potential savings, not promises — verify each fix in the Performance panel and in the field.
Verifying a fixRe-run the same audit category, same device profile, before/after in the same session — and confirm the user-facing metric actually moved in RUM over the rollout.

Internals Concept Comparison

Fourteen frequently confused pairs, side by side

The fastest way to stop confusing two concepts is to see them side by side with the one distinction that matters. Each card below gives the two definitions, then the key difference in one sentence — the sentence to remember in an interview.

DOM vs CSSOM
DOMStructure of the document: nodes parsed from HTML; mutable via script; owned by the tree builder (M05–06).
CSSOMStructure of the stylesheets: rules and selectors parsed from CSS; consumed during style calculation (M07).
Key: two different trees from two different languages — DOM says what exists, CSSOM says how it should look; style calculation joins them.
DOM vs render tree
DOMThe full parsed document, including head, scripts, and display:none elements.
Render treeA conceptual model of what will actually be painted: DOM minus non-rendered nodes, plus computed styles; modern engines build layout objects directly (M11).
Key: the render tree (model) is derived and paint-oriented; the DOM is authoritative and complete — an element can exist in the DOM while contributing nothing to output.
JavaScript engine vs browser runtime
EngineImplements ECMAScript: parse, bytecode, JIT, GC, built-ins like Array and Promise (M08).
RuntimeThe embedding: DOM, timers, fetch, event loop, workers — the host APIs around the engine (M08, M10).
Key: the engine answers “how does this code execute”; the runtime answers “what can this code do” — V8 runs identically in Chrome and Node, the runtimes differ.
Call stack vs task queue
Call stackFrames of the currently executing context chain; synchronous; LIFO; empties when the callback returns (M09).
Task queuePending callbacks waiting for the event loop to pick them up; asynchronous; FIFO within a source (M10).
Key: the stack is now, the queue is next — a callback on the queue cannot run until the stack is empty; a full stack blocks the queue.
Task vs microtask
TaskOne callback from a task source (timer, input, network); next loop iteration; can be deferred by busy main thread.
MicrotaskPromise reactions, queueMicrotask, MutationObserver; drained fully after every callback, before any task or render.
Key: microtasks run at the end of the current callback, tasks run in a future loop iteration — which is why an infinite microtask chain freezes the page completely.
Layout vs paint
LayoutComputes geometry: positions and sizes of boxes, from styles + content (M12).
PaintGenerates drawing operations in stacking order: which pixels colors go where — display lists, not pixels yet (M13).
Key: layout answers “where and how big”, paint answers “what gets drawn, in what order” — you can repaint without relayout (color change) and relayout almost always implies repaint.
Paint vs rasterization
PaintMain-thread record generation: an ordered list of draw operations (display list).
RasterizationExecuting those records into actual pixels, tiled, on raster workers/GPU (M13).
Key: paint is the plan, raster is the execution — the same paint records can be re-rasterized at another scale or DPR without repainting.
Rasterization vs compositing
RasterizationFills textures with pixels per layer/tile, once per content change.
CompositingAssembles layer textures into the final frame applying transforms — on the compositor thread, potentially every frame (M13).
Key: raster turns one layer into pixels; compositing combines layers — a transform animation re-composites an existing texture without re-rasterizing it.
TCP vs QUIC
TCPKernel transport: reliable ordered byte stream; one stream per connection; HOL blocking across everything on it (M17).
QUICUser-space transport over UDP: independent streams in one connection, integrated TLS 1.3, connection migration.
Key: both are reliable transports, but TCP delivers one ordered stream (loss stalls everything) while QUIC delivers many independent streams (loss stalls one).
HTTP cache vs Cache Storage
HTTP cacheBrowser-managed; obeys response headers; freshness + revalidation (M20).
Cache StorageApp-managed via the Cache API; your service worker decides everything; no header semantics (M20, M22).
Key: the HTTP cache follows rules you set in headers; Cache Storage follows code you write — deterministic offline vs automatic freshness.
Web Worker vs Service Worker
Web WorkerCompute thread for one page; created by it, dies with it; messaging only (M22).
Service WorkerOrigin-wide proxy; outlives tabs; intercepts fetches; started/stopped by the browser on demand (M22).
Key: a worker runs work for a page; a service worker runs policy for an origin — one is a thread, the other is a programmable proxy with a lifecycle.
Origin vs site
Origin(scheme, host, port) — exact tuple; same-origin policy unit (M04).
SiteScheme + registrable domain (public suffix + 1); cookie SameSite and process-isolation unit (M04, M02).
Key: subdomains are same-site but cross-origin — which is why your API at api.example.com needs CORS despite being “the same site”.
Cookie vs localStorage
Cookie~4 KB; sent automatically with matching requests; server-readable; HttpOnly/Secure/SameSite attributes (M21).
localStorage~5–10 MB; never sent automatically; client-only; synchronous API (M21).
Key: cookies are a request transport (server state per request), localStorage is a client store (state for your JS) — putting auth tokens in localStorage hands them to any XSS.
Rendering vs browser painting
RenderingThe whole update-the-output pipeline: style, layout, paint, raster, composite, present — including thread-off stages (M11).
PaintingOne stage inside it: generating the draw-operation records (M13).
Key: painting is a subset — a page can re-render (scroll: composite only) without repainting, and can repaint without relayout; never use the words interchangeably in an interview.
