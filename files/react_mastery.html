Introduction to React

What React is, what problem it solves, and what it deliberately is not

What React is

React is a JavaScript library for building user interfaces, created at Facebook (now Meta) and released open-source in 2013. You describe what the UI should look like for any given state of your data, and React takes responsibility for updating the browser DOM efficiently when that state changes. That description is not a string template — it is regular JavaScript functions returning elements, a lightweight description of the UI. React assembles those elements into a tree, compares new descriptions against old ones, and applies the minimum DOM operations required.

Three ideas define React’s identity. Declarative: you state the result, not the steps. Component-based: the UI is a tree of small, composable, testable units that each own a slice of rendering and behavior. Unidirectional: data flows one way — down the tree through props — which makes change propagation predictable and debuggable (see Module 05).

iReact core vs the ecosystem
React itself is small: a component model, a rendering pipeline, and a set of built-in hooks. Routing, data fetching, form management, testing utilities and full-stack capabilities all live in separate packages — some maintained by Meta (React DevTools), most by the community (React Router, TanStack Query, Vitest). A React application needs exactly one ecosystem library to start: none. This guide labels every API as either React core or Ecosystem so the boundary never blurs.

Why React exists: the problem it solves

Before component frameworks, interactive UIs were written as a pile of DOM updates scattered through event handlers. Every state change required you to find every piece of the page affected by that state and update it by hand. The code that changed the UI and the code that read the state drifted apart; missed updates produced the classic bugs — a counter badge showing 3 while the cart holds 5 items. Facebook’s internal motivation was exactly this: an increasingly unmaintainable cascade of manual DOM synchronization in a codebase with enormous state interdependencies.

React’s answer was to invert control. Instead of you mutating the DOM on every change, React re-derives the UI from state after every change. Your job shifts from “keep the DOM in sync” — bug-prone bookkeeping — to “model state correctly” — a design problem. The framework does the bookkeeping, deterministically and at machine speed.

Declarative versus imperative UI programming

Imperative code tells the browser how to mutate, step by step: find this node, change that text, add this class. Declarative code tells React what the UI should be for the current state; React computes the how. The same counter, both ways:

● IMPERATIVE — vanilla JS: you are the DOM manager
● DECLARATIVE — React: describe the UI for any count

Notice what disappears in the React version: there is no code that updates anything. Add a third place the count appears, and the vanilla version needs another manual update line (and another bug surface), while the React version needs only another {'{count}'} in the markup. The cost is a mental model you must learn — rendering, state, reconciliation — which is precisely what Modules 12–14 teach.

Component-based architecture

A React application is a tree of components. Each component is a function that accepts inputs (props) and returns UI. Components nest: a ProductPage renders a SearchBar, a ProductList of ProductCards, and a CartBadge. Boundaries follow responsibility — each component owns its markup, its local behavior, and (ideally) nothing else. The tree shape gives you reasoning superpowers: state changes re-render subtrees, not spreadsheets of DOM selectors; components are unit-testable in isolation; and design systems map directly onto component libraries. Composition details live in Module 04.

Library versus full-stack framework

React the library renders your UI and stops there. Meta’s framework Next.js (and Remix, Gatsby and others) builds on React to add routing, server rendering, data loading conventions and bundler integration — these are Ecosystem frameworks, not React itself. A React app can be a single <div> progressively enhancing a server-rendered page, or an entire client-side application where React owns the document. Nothing in React’s core requires a framework, and nothing requires Redux, a router, or any specific library — a persistent misconception this guide explicitly retires. When a framework becomes worthwhile (server components, streaming, file-based routing), Module 24 covers the decision.

The “Virtual DOM”: what the term means — and what it does not

“Virtual DOM” is the historical name for React’s internal bookkeeping: after a render, React holds a tree of plain JavaScript objects describing the UI it wants, and compares the new tree against the previous one to compute the minimal set of DOM mutations (this comparison is reconciliation — Module 13). What the term does not mean:

  • It is not a guarantee of automatic speed. Diffing costs CPU; React is fast because the model enables batching and skipping work, not because diffing is free. Naive React code can absolutely be slower than hand-written DOM code.
  • It is not a full diff of the entire app on every update. React starts from the components whose state changed and walks down their subtrees; sibling subtrees that were not affected are skipped.
  • It is not the architecture. Modern React (since 16’s Fiber rewrite) is more accurately described as a scheduler plus a renderer: work is split into units that can be prioritized and interrupted — the foundation of concurrent features (Module 24). The docs now say “React maintains a virtual representation of the UI” rather than leaning on the marketing term.

Design philosophy

  • UI as a pure function of state — same state in, same UI out. Side effects are quarantined in effects and event handlers, not sprinkled through render logic.
  • Explicit data flow — props flow down; events flow up through callbacks. Two-way binding magic is deliberately absent.
  • Escape hatches over rigid rules — refs, flushSync and manual DOM access exist when the model genuinely does not fit; they are marked as such.
  • Stability and gradual adoption — APIs survive for years; legacy patterns keep working while the ecosystem migrates (class components still render; hooks did not delete them).
  • Schedule work, then commit it — rendering is separated from committing so urgent updates (typing) can preempt expensive ones (filtering 10,000 rows).

Where React fits in modern frontend engineering

React powers a huge share of new SPAs, hybrid server-rendered sites (Next.js/Remix), cross-platform apps (React Native renders native widgets, not HTML), design-system component libraries, and embedded widgets inside larger non-React pages. In a typical team, React defines the frontend contract: designers deliver against component APIs, backend teams consume JSON/REST or GraphQL contracts that the frontend calls, and tooling (TypeScript, Vitest, Playwright) integrates around the component model. React sits between the browser platform and your product logic — it does not replace either.

When teams choose React — use cases

Strong React fits: highly interactive stateful UIs (dashboards, editors, configurators), product surfaces with deep client state (e-commerce carts and filters, social feeds), design systems shared across teams, apps targeting web and native with shared skills, and pages needing progressive enhancement of server-rendered HTML. Weak fits: mostly-static content sites (a templating/static-site generator wins on simplicity and speed), tiny interactive islands where 20 lines of vanilla JS suffice, and hard real-time canvas/WebGL scenes where you drive rendering yourself (React can wrap them, but the render loop is yours). Choosing honestly is a senior skill.

Environment, Tooling & Project Setup

Node, package managers, Vite, linting, DevTools — a professional baseline

Node.js and npm fundamentals you actually need

React development runs on Node.js: the dev server, bundler, test runner and lint tooling are all Node programs. You need Node installed (use the Active LTS line — check node -v), plus npm, which ships with it. Day-to-day you use four npm ideas: dependencies (runtime code), devDependencies (tooling), semantic versioning ranges in package.json (^19.0.0 = compatible minor/patch), and the scripts block that aliases commands. A React app needs astonishingly few runtime dependencies — typically just react and react-dom.

npm, pnpm and Yarn

ManagerInstall layoutNotable property
npmLocal node_modules per projectDefault, zero setup, lockfile package-lock.json
pnpmGlobal content-addressable store + hard linksFast, strict, saves disk across many projects
Yarn (Berry)Plug’n’Play or node_modulesWorkspaces-first monorepo ergonomics

All three read the same package.json. Pick one per project, commit its lockfile (package-lock.json, pnpm-lock.yaml, yarn.lock), and never mix managers inside one repository. Lockfiles pin the exact dependency graph so every machine and your CI install byte-identical trees — committing them is non-negotiable on a team.

Creating a project with Vite

Vite is the current default for new React applications. (Create React App is deprecated and must not be used for new projects.) Vite serves your code over native ES modules in development — near-instant startup, hot module replacement — and bundles with Rollup for production.

index.html is a real HTML file — the only one. Vite injects your entry script; React takes over the <div id="root"> from there. The mount itself is three lines:

import { StrictMode } from "react";

  <StrictMode>
    <App />
  </StrictMode>
);

Development server and production build

Dev (npm run dev): unbundled native ESM, hot module replacement preserves component state while you edit, source maps map everything back to your files. Build (npm run build): minification, tree-shaking, content-hashed filenames for long-term caching, code-split chunks, CSS extraction, asset inlining. Preview (npm run preview) serves dist/ the way a static host would — always smoke-test the build here before deploying; the dev server is more forgiving than production in ways that hide bugs.

Inspect what you ship: open dist/, check chunk sizes, and use the browser Network panel on preview. A React 19 hello-world app bundles to roughly 140–160 kB minified (≈45–48 kB gzipped) — knowing your baseline makes regressions visible early.

Environment variables and safe configuration

Vite exposes environment variables only when prefixed with VITE_, via import.meta.env:

# .env                — committed defaults
VITE_API_BASE_URL=/api/v1
# .env.local          — NOT committed; machine-specific overrides
# .env.production     — used by `npm run build`

const BASE = import.meta.env.VITE_API_BASE_URL ?? "/api/v1";
export async function getJSON(path) {
  const res = await fetch(BASE + path);
  if (!res.ok) throw new Error("GET " + path + " failed: " + res.status);
  return res.json();
}
!Anything bundled is public
import.meta.env.VITE_* is inlined into the JavaScript you ship. Never put API secrets, private keys or database credentials there — there is no such thing as a hidden frontend secret. Real secrets belong behind a backend you call; the frontend only ever holds public configuration (API base URLs, feature flags, analytics keys). Full treatment in Module 23.

ESLint and formatting

Linting is not cosmetic — for React it is a correctness tool. eslint-plugin-react-hooks statically catches hook-rule violations and missing effect dependencies; its rules are the closest thing React has to a compiler pass. Modern setups use flat config:

import js from "@eslint/js";
import reactHooks from "eslint-plugin-react-hooks";

export default [
  js.configs.recommended,
  {
    files: ["src/**/*.{js,jsx}"],
    plugins: { "react-hooks": reactHooks },
    rules: {
      "react-hooks/rules-of-hooks": "error",    // hooks called correctly
      "react-hooks/exhaustive-deps": "warn"     // effect deps complete
    }
  }
];

Run npm run lint in CI on every pull request. Add Prettier (or Biome) for formatting so humans review logic, not whitespace.

React Developer Tools

Install the React DevTools browser extension (Chrome/Firefox; also a standalone app). It adds two tabs: Components (live tree of rendered components — inspect props, state, hooks, context per node, edit values, “flash” on re-render) and Profiler (record interactions and see which components rendered, why, and for how long — the tool behind Module 14). The Components tab also reveals source file names with “click to open in editor” when the dev server is running. This is the single highest-ROI tool in React development; install it before writing your second component.

Browser debugging workflow

  • Sources panel: set breakpoints in .jsx files directly (source maps); debugger; statements work in dev.
  • Console: React logs component stack traces with warnings; read them — they name the offending component.
  • Network panel: watch fetch/XHR, headers, payloads; throttle to “Slow 3G” to see your loading states honestly.
  • Performance panel + DevTools Profiler: distinguish script time from rendering/paint time.
  • React 19 DevTools show “why did this render?” reasons per component when profiling — first stop for re-render mysteries.

Strict Mode

<StrictMode> is a development-only component that runs extra checks around your components. In React 18+ it double-invokes component bodies, effects and passed state updater functions in development to surface impurity and missing cleanup. This is the behavior that makes your effect run “twice on mount” during development — by design, to prove your effect can mount, clean up, and mount again (which is what happens in real production scenarios like Fast Refresh and route remounts). Strict Mode adds no production overhead and never affects production behavior. If double effects expose a bug, that bug existed anyway — fix the effect (Module 08), do not remove Strict Mode.

Basic Git workflow for React projects

  • Commit package.json and the lockfile together; commit dist/ never (CI builds it).
  • .gitignore: node_modules, dist, .env.local, coverage, editor folders.
  • Branch per feature; keep lint + tests green on main so bisecting real regressions stays possible.
  • Component-level commits (“add CartBadge component”) keep history reviewable; format/renames go in separate commits.

Deeper Git craft lives in this library’s dedicated Git guide (see Related Guides).

JSX & JavaScript Foundations for React

JSX is JavaScript — semantics, expressions, lists, fragments and the JS you use every day

What JSX is

JSX is a syntax extension to JavaScript that looks like HTML but is compiled into ordinary function calls before it ever reaches the browser. This tag-based syntax:

function Greeting({ name }) {
  return <h1 className="title">Hello, {name}!</h1>;
}

compiles (via Babel or the platform compiler in your build tool) to this plain JavaScript:

function Greeting({ name }) {
  return React.createElement("h1", { className: "title" }, "Hello, ", name, "!");
}

React.createElement returns a plain object — a React element: { type: "h1", props: { className: "title", children: [...] } }. That is all JSX ever produces: descriptions, not DOM nodes. Understanding this dissolves the biggest beginner confusion: JSX is not a template language with magic directives — it is JavaScript expressions, with full language power and full JavaScript debugging, and every rule of JavaScript (scope, truthiness, expression vs statement) applies inside it.

JavaScript expressions inside JSX

Anything inside { } is a single JavaScript expression evaluated at render time and rendered as text (or as elements/arrays of elements). Statements do not belong there — if, for, while are statements, so you use expression equivalents:

const user = { name: "Ada", role: "admin", unread: 3 };

function NavBadge({ user }) {
  return (
    <header>
      {/* expression: property access */}
      <span>{user.name}</span>

      {/* expression: ternary — the JSX "if" */}
      {user.role === "admin" ? <AdminPanel /> : null}

      {/* expression: logical AND — render only when meaningful */}
      {user.unread > 0 && <span className="badge">{user.unread}</span>}

      {/* expression: template literal */}
      <img src={"/avatars/" + user.name.toLowerCase() + ".png"} alt="" />

      {/* expression: function call */}
      <time>{formatDate(new Date())}</time>
    </header>
  );
}
!The && leak — the classic JSX bug
{count && <Badge />} renders the number 0 visibly when count === 0, because && returns its left operand when it is falsy-but-renderable. Guard explicitly: {count > 0 && <Badge />}. Numbers and strings are the only falsy values JSX will render; false, null, undefined and true render nothing.

Conditional rendering — the full toolbox

function Panel({ state, items }) {

  if (state === "error") return <ErrorBox retry={retry} />;

Lists and keys

Rendering collections uses Array.map to produce an array of elements; React renders arrays inline. Every element in a list needs a key — a stable identity string React uses to track items between renders:

function ProductList({ products }) {
  return (
    <ul>
      {products.map((product) => (
        <li key={product.id}>              {/* stable id: correct */}
          {product.name} — {product.price}
        </li>
      ))}
    </ul>
  );
}

Keys are not cosmetic: they are how React decides whether a list item is “the same” across renders — which decides whether its local state survives. The rules: use stable domain IDs; never Math.random() (a new key every render remounts everything); avoid the array index when the list can reorder, insert or delete (state silently attaches to the wrong item — the full analysis, with the bug demonstrated live, is Module 13 and Lab 10). Key only matters among siblings; it need not be globally unique.

Fragments

A component must return one root, but sometimes the extra wrapper div would break layout (CSS grid children, <tr> in a table, definition lists). Fragments group children without adding a DOM node:

import { Fragment } from "react";

function TableRow({ cells }) {
  return (
    <Fragment>
      <td>{cells.a}</td>
      <td>{cells.b}</td>
    </Fragment>
  );
}

Attributes, event handlers, and dynamic values

  • Event handlers are functions passed as props named onEvent: <button onClick={handleSave}>. Pass the function, do not call it — onClick={handleSave()} calls during render and passes the result (a bug that fires immediately, not on click). To pass arguments, wrap: onClick={() => remove(item.id)}.
  • Dynamic attribute values use expression braces: src={user.avatarUrl}, disabled={!form.valid}.
  • Booleans like disabled accept real booleans: disabled={isSaving}; required, checked, hidden behave likewise.
  • Spreading props forwards collections: <input {...register("email")} /> — powerful with forms; use deliberately, since invisible props reduce explicitness.

Escaping: why JSX is safe by default

Everything rendered inside braces is escaped by React before insertion — a value of <script>alert(1)</script> renders as visible text, never as markup. There is no way to inject HTML through data with plain JSX; the only escape hatch is dangerouslySetInnerHTML, which does exactly what its name says and requires sanitization when fed anything user-derived (Module 23). This default is a major security property of React and one you get for free — do not work around it with HTML string concatenation.

Nesting rules and component return values

JSX is parsed as nested expressions, so tags must nest properly and close; adjacent sibling roots are a syntax error (use fragments). A component returns: an element, an array of elements, a fragment, a string/number, or null (renders nothing but keeps the component mounted — different from false... which also renders nothing, but from conditions). Returning undefined is an error; return null deliberately.

Components & Composition

The unit of React engineering — building blocks, boundaries and the composition mindset

What a component is

A component is a reusable, independent piece of UI: a JavaScript function that accepts a props object and returns React elements describing what should be on screen. The same input always produces the same output, which makes components predictable, testable and composable. React calls your function whenever it needs to render that piece of UI — first at mount, then after relevant state changes.

function VideoCard({ title, duration, thumbnailUrl }) {
  return (
    <article className="video-card">
      <img src={thumbnailUrl} alt="" />
      <h3>{title}</h3>
      <span className="duration">{formatDuration(duration)}</span>
    </article>
  );
}

// Usage — components compose like HTML tags:
<VideoCard title="Rendering Deep Dive" duration={754} thumbnailUrl="/t/42.png" />

Naming conventions are load-bearing: components are PascalCase (JSX treats lowercase tags as host DOM elements — <videoCard /> renders an unknown HTML tag, not your component), one component per file, file named after the component. Props read like an API: nouns for data (items), on-prefixed handler names for callbacks (onSelect), is/has for booleans.

Component responsibilities and boundaries

A good component has one job and a clear contract: props in, UI (and optionally events) out. Symptoms of a boundary drawn wrong: a component that fetches data and lays out cards and formats dates and owns filter state — four responsibilities, four reasons to change. The fix is not moral purity; it is that every responsibility you split out becomes independently readable, testable and reusable. Boundaries also define render boundaries (where re-renders stop — Module 14) and error boundaries (where failures stop — Module 17).

The component tree

Nesting components produces a tree: <App /> renders <Layout />, which renders <Navbar /> and <Main />, and so on down to host elements like <div> and <button>. The tree is the mental map for everything that follows: data flows down it (Module 05), renders cascade down it (Module 12), identity and state live on its nodes (Module 13), and context broadcasts across it (Module 10). Open Lab 01 to inspect a live tree, and see Visual Model 1.

Props, destructuring, defaults

function Button({
  variant = "primary",        // default via destructuring — preferred
  size = "md",
  icon,
  children,
  ...rest                     // collect the rest for forwarding
}) {
  return (
    <button
      className={`btn btn--${variant} btn--${size}`}
      {...rest}               // forwards onClick, type, disabled, aria-* ...
    >
      {icon && <span className="btn-icon" aria-hidden="true">{icon}</span>}
      {children}
    </button>
  );
}

Props are read-only: a component must never modify its props object. Mutating a prop you received is mutating your parent’s data — the bug appears somewhere else. Treat every prop as frozen; if you need to change it, own state instead (Module 06). The ...rest forwarding pattern above is how well-designed primitives stay compatible with the platform: consumers can still pass onClick, disabled or aria-label without the Button enumerating them.

children — composition’s workhorse

children is a special prop containing whatever the caller nested between your tags. It is the mechanism that turns components from rigid templates into flexible slots:

function Card({ title, actions, children }) {
  return (
    <section className="card">
      <header className="card-head">
        <h2>{title}</h2>
        <div className="card-actions">{actions}</div>
      </header>
      <div className="card-body">{children}</div>

}

</Card>

Note actions={<Button />}: elements as props (sometimes called “slots”) let callers pass ready-made JSX for named regions. This is composition — the caller supplies structure instead of the component guessing through 15 boolean flags.

Composition over inheritance

React has no component inheritance idiom, and deliberately so. Want a component that is “a Button plus an icon”? Compose it: wrap, don’t extend.

// ❌ The OOP instinct — there is no Button extends in React
// class DangerButton extends Button { ... }

// ✅ The React way — wrap and configure:
function DangerButton(props) {
  return <Button variant="danger" {...props} />;
}

// ✅ Wrap for behavior: logging, guards, layout — same shape
function Modal({ title, onClose, children }) {
  return (
    <div className="modal-backdrop" onClick={onClose}>
      <div className="modal" role="dialog" aria-modal="true" aria-label={title}>
        <header><h2>{title}</h2><button onClick={onClose}>Close</button></header>
        {children}
      </div>
    </div>
  );
}

Wrapper composition scales linearly with needs; inheritance hierarchies tangle base classes with every new requirement. When you feel the pull of “a base component with overrides”, reach for children, element props, or composition — every time.

Presentational and container-style separation

A useful (older, still relevant as a concept) lens: presentational components render — they take data via props and emit UI; container components coordinate — they own state, fetch data, and pass props down. Modern code rarely names things XxxContainer anymore (custom hooks absorbed most container logic — Module 15), but the separation itself remains the default architecture: your data coordination should be extractable apart from your markup. A ProductList that renders rows is testable with three props; one that also fetches needs network mocking to test at all.

Extraction: when and how

Extract a component when: a JSX block has its own meaningful identity (a SearchBar hiding inside the header); a block repeats; a component exceeds roughly a screen of code; or two components share a shape. The mechanics are mechanical — cut the JSX, paste into a new function, promote referenced values into props:

● BEFORE — one component, three jobs
● AFTER — composed from focused pieces

Avatar is now reusable by the navbar, the comment list and the settings page — extraction paid rent on its first day.

Reuse versus over-abstraction

The counterweight: premature abstraction is worse than duplication. A <GenericField /> with 14 flags that renders every field in your app “flexibly” is harder to read than three honest components. Heuristics that hold up: the rule of three — tolerate two similar blocks, extract at the third; extract for identity, not for line count — a 5-line Price component that owns currency formatting is right, a 5-line Wrapper2 is noise; props are a public API — every flag you add is API you maintain; prefer composition (children, slots) over configuration when callers need variation.

Compound components — advanced composition

When a set of parts only make sense together (a select with trigger and options, a tab set), compound components expose the parts as named properties sharing implicit state — the API reads like HTML, the wiring stays inside:

import { createContext, useContext, useState } from "react";

const TabsCtx = createContext(null);

export default function Tabs({ defaultTab, onChange, children }) {
  const [active, setActive] = useState(defaultTab);
  const value = {
    active,
    select: (id) => { setActive(id); onChange?.(id); }
  };
  return <TabsCtx.Provider value={value}>
    <div className="tabs">{children}</div>
  </TabsCtx.Provider>;
}

function TabList({ children }) {
  return <div role="tablist" className="tablist">{children}</div>;
}
function Tab({ id, children }) {
  const { active, select } = useContext(TabsCtx);
  return (
    <button role="tab" aria-selected={active === id}
      className={active === id ? "tab tab--on" : "tab"}
      onClick={() => select(id)}>
      {children}
    </button>
  );
}
function TabPanels({ children }) { return <div className="tabpanels">{children}</div>; }
function TabPanel({ id, children }) {
  const { active } = useContext(TabsCtx);
  if (active !== id) return null;
  return <div role="tabpanel">{children}</div>;
}

One-way data flow, callbacks, prop drilling, lifting state — the wiring diagram of every React app

One-way data flow

React’s central architectural rule: data flows down, events flow up. A parent passes data to children through props; children never write back directly — they call callback props, and the parent (who owns the data) decides what happens. Every state change has a single, traceable path: event → callback up → owner updates state → new props flow down. This is what makes a React codebase debuggable at 3 a.m.: there is exactly one direction to trace, and the owner of each piece of data is explicit.

Child to parent: callbacks

The child cannot reach up; the parent hands down a function, and the child calls it when something happens:

function QuantityStepper({ value, onChange }) {      // child: reports, decides nothing
  return (
    <div className="stepper">
      <button aria-label="Decrease" onClick={() => onChange(value - 1)}>−</button>
      <span>{value}</span>
      <button aria-label="Increase" onClick={() => onChange(value + 1)}>+</button>

  );
}

function CartLine({ line, onQuantityChange, onRemove }) {   // parent: owns decisions
  return (
    <div className="cart-line">
      <span>{line.name}</span>
      <QuantityStepper
        value={line.qty}
        onChange={(qty) => onQuantityChange(line.id, Math.max(1, qty))}
      />
      <button onClick={() => onRemove(line.id)}>Remove</button>
    </div>
  );
}

Notice the division of labor: the stepper is a dumb input mechanism; the cart line enforces the business rule (Math.max(1, ...)). Rules live with the owner of the data.

Sibling communication through shared parent state

Siblings never talk directly. When two siblings need the same data (a search box and a results list), you lift the shared state into their closest common parent, pass it down as props, and pass callbacks down for changes:

import { useState } from "react";

function CatalogPage({ products }) {
  // ONE source of truth for both siblings lives here:
  const [query, setQuery] = useState("");

  const visible = products.filter((p) =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div className="catalog">
      <SearchBar value={query} onChange={setQuery} />   {/* sibling 1: writes */}
      <ProductList products={visible} />                {/* sibling 2: reads */}
    </div>

}

function SearchBar({ value, onChange }) {
  return (
    <input
      type="search" value={value}
      placeholder="Search products…"
      onChange={(e) => onChange(e.target.value)}
    />

This pattern — state up top, data down, events up — solves 90% of coordination needs without any library. When the closest common parent is many levels away, context (Module 10) or state colocation strategies (Module 20) take over.

Prop drilling

Prop drilling is what happens when data must pass through components that do not use it, only to reach a deep consumer:

<App user={user} />                        {/* App: uses user ✔ */}
  <Layout user={user} />                   {/* Layout: never reads user ✘ */}
    <Sidebar user={user} />                 {/* Sidebar: never reads user ✘ */}
      <UserMenu user={user} />               {/* UserMenu: uses user ✔ */}

Mild drilling (one or two hops) is healthy — it keeps data flow explicit and greppable. It becomes a problem when middle layers churn every time a deep component needs a new value. The alternatives, in order of preference: (1) pass the component down as children or an element prop so intermediate layers never see the data; (2) move state closer to its consumers (component composition fixes most drilling); (3) context for genuinely cross-cutting values (theme, auth, locale — Module 10); (4) an external store when many far-apart components need the same changing data. Reach for (3)/(4) only after (1)/(2) fail — context has its own costs.

Component ownership

For any piece of state, ask: who renders because of it, and who is the closest common ancestor of all of them? That ancestor should own it. State used by one component belongs in that component. State shared by siblings belongs in their parent. State shared across distant branches belongs in a common high-level component — or, if it is truly app-wide identity/configuration, in context. The interactive version of this decision — with trade-offs for each option — is Workshop 3 — State Architecture Decision Assistant.

Prop immutability and callback identity

Props are a loan, not a gift: treat received objects and arrays as frozen. Copy-then-modify on the owning side ({ ...cart, items: nextItems }), never props.items.push(x). The subtler performance topic is identity: a fresh arrow function or object literal created during a parent’s render is a new value every render, so a child comparing props (via React.memo) sees “changes” that are semantically identical. This is the number-one cause of “why is my memoized child re-rendering” — the mechanism and remedies (useCallback, useMemo, moving state down) are Module 14’s main subject, demonstrated in Lab 11.

import { useState } from "react";

function CartPage({ products, user }) {
  const [items, setItems] = useState([]);        // owned HERE: needed by 3 children

  const subtotal = items.reduce(                 // derived — never state
    (sum, i) => sum + i.price * i.qty, 0
  );

  return (
    <div className="cart-page">
      {/* data down ↓  events up ↑ */}
      <ProductGrid
        products={products}
        onAdd={(id) => addItem(setItems, id, products)}
      />
      <CartSummary
        items={items}
        subtotal={subtotal}
        onCheckout={() => submitOrder(user, items)}
        onRemove={(id) => setItems(items.filter((i) => i.id !== id))}
      />
    </div>
  );
}

function addItem(setItems, id, products) {
  const product = products.find((p) => p.id === id);
  setItems((prev) => {                           // functional update: safe from races
    const existing = prev.find((i) => i.id === id);
    return existing
      ? prev.map((i) => i.id === id ? { ...i, qty: i.qty + 1 } : i)
      : [...prev, { id, name: product.name, price: product.price, qty: 1 }];
  });
}
  • Owned state: items — the only mutable truth, lives at the page level.
  • Derived data: subtotal — computed each render, never stored, cannot drift.
  • Down: products, items, subtotal.
  • Up: onAdd, onRemove, onCheckout — children report, page decides.
  • Immutable updates: map/filter/spread only — the mechanics behind this are Module 06.

React State Fundamentals

useState, snapshots, batching, immutability — the semantics most bugs trace back to

What state represents

State is data a component owns that can change over time and that its UI depends on — the current filter text, an open/closed menu, the items in a cart. Everything else is either props (owned above) or constants (owned outside the render entirely). The litmus test for “should this be state?”: does it change over time, and cannot it be computed from other state/props? If it can be computed, it must not be state — it is derived data and belongs in the render.

function FilteredTable({ products }) {
  const [filter, setFilter] = useState("");     // STATE: minimal, changes over time

  const visible = products.filter((p) =>       // DERIVED: computed every render
    p.name.toLowerCase().includes(filter.toLowerCase())
  );
  const count = visible.length;                 // DERIVED: never store a count

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      <table>{/* rows from visible */}</table>
      <p>{count} shown</p>
    </>
  );
}
!Every stored duplicate is a future bug
Storing visibleCount in state means keeping it in sync by hand after every filter change — and every missed update is a stale UI bug. React’s model wants minimal state, maximal derivation: store the facts, compute the views.

useState — the API and its contract

import { useState } from "react";

const [value, setValue] = useState(initialValue);
//  value    — the state FOR THIS RENDER (a snapshot; see below)
//  setValue — requests a re-render with a new value
//  initialValue — used only on the FIRST render (later renders ignore it)

The pair is conventionally named [thing, setThing]. Lazy initialization: when the initial value is expensive to compute (reading localStorage, parsing), pass a function — useState(() => loadFromStorage()) — so it runs once, not on every render.

State snapshots: why the setter does not change the value now

The single most important state fact: a state variable is a snapshot of one render. Calling setValue does not change the variable in the currently running function — it schedules the next render, which will be invoked with the new value. Within this render, the old value remains constant, like a photograph already taken.

function Clicker() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);        // schedules render with 1
    console.log(count);         // logs 0  ← the snapshot, not the new value
    setCount(count + 1);        // 0 + 1 again → still schedules 1
  }
  // Click twice: renders show 1, 2 — but ONE click always lands on 1.
}

Two consequences. First, the classic interview demo: three setCount(count + 1) calls in one handler produce +1 total, not +3 — every call read the same snapshot. Second, asynchronous code keeps its snapshot forever: inside a setTimeout two seconds later, count is still the value from the render that created the closure (this is the stale closure, Module 08). The fix for both is the same:

function handleClick() {
  setCount((c) => c + 1);   // 0 → 1
  setCount((c) => c + 1);   // 1 → 2
  setCount((c) => c + 1);   // 2 → 3  ← each receives the LATEST queued value
}

Use a functional update whenever the next value depends on the previous value. Batched updates run in order, each receiving the result of the last.

Batching

Multiple set calls in one event handler (or one effect) are batched into a single re-render — free since React 18, including inside promises and timeouts. Batching is why three setters in a handler cost one render. The rare need to flush synchronously (measure DOM after a state change) has an escape hatch (flushSync), but treat it as what it is: an escape hatch. Updating objects in state — immutably

Objects and arrays in state follow one law: replace, never mutate. React compares by identity to decide what changed; a mutated object is the same reference, so React may see “no change” and skip the update — and even when it re-renders, anything memoized on that object stays stale.

● WRONG — mutation: silent, broken
● RIGHT — replace: new object, new identity

Deeply nested objects: update level by level with spread — setForm(f => ({...f, address: {...f.address, city: "Berlin"}})). When nesting gets deep enough that this hurts, that is a design signal: flatten the state, or normalize it into a keyed map ({[id]: item}) — Module 11.

State initialization from props — and why it is usually wrong

// ✘ Copying props into state: the copy desyncs when the prop changes
function EditTimer({ initialSeconds }) {
  const [seconds, setSeconds] = useState(initialSeconds);  // frozen on first render
  // parent updates initialSeconds → this component ignores it. Bug.
}

// ✓ Key-based reset when the prop genuinely represents a NEW entity:
<EditTimer key={timerId} initialSeconds={seconds} />
// changing the key remounts with fresh state (identity, Module 13)

// ✓ Controlled child when the parent should stay in charge:
function EditTimer({ seconds, onChange }) {   // stateless, always in sync
  return <input value={seconds} onChange={(e) => onChange(+e.target.value)} />;
}

Copying props into state is legitimate in exactly one narrow case: when the prop is an intentionally captured initial value for an editing session, and the key-based reset above is used. Otherwise pick an owner: either the parent (controlled) or the child (own it fully).

When state is unnecessary

  • Derivable data — counts, filtered lists, formatted values: compute, do not store.
  • Server data mirrors — data you fetched belongs to a cache with a proper loading/error lifecycle (Module 18), not hand-rolled useState + useEffect soup.
  • Values that never trigger rendering — interval IDs, DOM nodes, latest-value trackers: that is useRef territory (Module 09).
  • URL-encoded state — active tab, search query, page number: put it in the URL (Module 19) so links, refresh and history work for free.

Hooks Fundamentals & Rules

Why hooks exist, the two rules, and the reasoning that makes them obvious

What Hooks are

Hooks are functions that let function components “hook into” React features: state (useState), external systems (useEffect), context (useContext), and so on. They are ordinary JavaScript functions with two special powers: they may only be called at the top level of components (or other hooks), and React supplies their behavior based on where in the call order they appear. Names always start with use — both a convention and the signal the linter uses to enforce the rules.

Why Hooks exist

Before hooks (React < 16.8, 2019), stateful logic required class components: state lived on this, lifecycle methods (componentDidMount, componentDidUpdate, componentWillUnmount) split one concern across three methods, and reuse required higher-order components or render props — wrapper pyramids that obscured the component tree. Hooks solved three problems at once:

  • Colocation: the code for “subscribe on mount, unsubscribe on unmount” sits together in one effect, not three lifecycle methods.
  • Reuse without wrappers: stateful logic extracts into a custom hook (Module 15) and is called, not wrapped — no tree distortion, no naming collisions.
  • One component model: functions everywhere; no class binding ceremony (this.handleSubmit = this.handleSubmit.bind(this) is now archaeology).

Classes are not deprecated — they still work and exist in older codebases you may maintain — but all new React code and documentation is functional with hooks.

How hooks preserve state between renders — conceptually

A function component is just a function; where does state survive between calls? Conceptually, React keeps a list of memory cells per component instance, indexed by call order. When your component renders, each useState call walks to the next slot and reads/writes that slot. There is no name lookup — useState(0) does not find “the count slot” — only position. This single implementation detail explains every rule below.

Conceptual model for teaching — the real Fiber implementation is an optimized linked list with the same positional semantics. Interactive drill: Lab 04 — Hooks Rules Detective.

The Rules of Hooks

!Rule 1 — Only call hooks at the top level
Never inside loops, conditions, nested functions, or try/catch. Call them unconditionally, in the same order, every render.
!Rule 2 — Only call hooks from React functions
Component function bodies or custom hooks — never plain JavaScript functions, event handlers outside components, or module top-level code.

Why the rules exist — the reasoning, not the memorization

Because state lookup is positional, a hook call in an if changes which slot each subsequent hook lands in on the next render:

function Profile({ user }) {
  const [tab, setTab] = useState("posts");        // always slot 1

  if (user) {
    const [name, setName] = useState(user.name);  // slot 2 ONLY when user exists
  }

  const [page, setPage] = useState(1);            // slot 2 when user is null
                                                  // slot 3 when user exists!
  // user goes null → this useState reads what useEffect-slot held,
  // or worse: "Rendered fewer hooks than expected" crash.
}

Render 1 (user present): tab→slot 1, name→slot 2, page→slot 3. Render 2 (user null): the if skips the second call, so page lands in slot 2 — it now reads the name cell. React detects the count changed and crashes (“Rendered fewer hooks than expected”) or, worse, silently mismatches state. The rule is not arbitrary style — it is the direct price of positional storage. To call a hook conditionally, make the branching conditional inside a hook that always runs:

function Profile({ user }) {
  const [tab, setTab] = useState("posts");       // slot 1, always
  const [name, setName] = useState("");          // slot 2, always
  const [page, setPage] = useState(1);           // slot 3, always

  useEffect(() => {                              // hook runs unconditionally...
    if (user) setName(user.name);                // ...behavior branches inside
  }, [user]);
}

Hook ordering and stable identity

The same reasoning dictates ordering etiquette: hooks should be called in a fixed order, with any dynamic behavior inside them. Looping over a constant list of fields to call useState per field is technically stable but fragile — one reorder of the fields array reshuffles every slot. When you need state per item, the idiomatic answer is a component per item (each instance gets its own cell list), not a loop of hooks.

Built-in hooks vs custom hooks

React ships a small set of built-ins — useState, useEffect, useRef, useContext, useReducer, useMemo, useCallback, useId, useSyncExternalStore, useTransition, useDeferredValue, useActionState, useOptimistic, use (the last four arrive with React 19 — Module 24). A custom hook is any function starting with use that calls other hooks — a composition unit, not a new React feature:

import { useState, useCallback } from "react";

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle];
}

// In a component — hooks compose like function calls:
function Menu() {
  const [open, toggleMenu] = useToggle();
  return <button aria-expanded={open} onClick={toggleMenu}>Menu</button>;
}

Custom hooks share stateful logic, never state itself: two components calling useToggle each get an independent on. The rules apply identically inside custom hooks — which is exactly why they must be named use*: the linter cannot check a function it does not know is a hook.

Common misconceptions

“useState finds state by variable name”Position only. Renaming variables changes nothing; reordering calls changes everything.

useEffect & Synchronizing with External Systems

Effects are for synchronization — not for derivations, not for events, and not “on mount do stuff”

The mental model: Effects synchronize

An Effect lets a component keep in step with a system outside React: the network, the DOM outside your tree, browser APIs, timers, subscriptions, third-party widgets. React renders your UI; an effect runs after a render commits to push the outside world back into alignment with what you just rendered. The framing that prevents 90% of misuse:

iThe one-sentence test
If the code responds to a user action (click, submit, keystroke), it belongs in an event handler. If it keeps an external system matched to your state across time, it belongs in an Effect. If it computes something from state/props, it belongs in neither — it is just rendering.

Anatomy: setup, cleanup, dependencies

useEffect(() => {
  // SETUP — runs after the component appears on screen,
  // and again after re-renders where a dependency changed.

  connect(socket);                    // synchronize with the outside world

  return () => {                      // CLEANUP — runs before the next setup
    disconnect(socket);               // (undo the previous synchronization)
  };                                  // and before the component unmounts.
}, [serverUrl]);                       // DEPENDENCIES — reactive values the
                                      // effect reads. Compare by Object.is.
  • No array — runs after every render (almost never what you want; usually a sign of missing deps).
  • Empty array [] — setup once after mount, cleanup on unmount. Correct only for systems that truly do not depend on any reactive value.
  • [a, b] — setup after mount and after any render where a or b changed (compared with Object.is). Cleanup runs before each re-setup and at unmount.

Effects run after the browser paints (post-commit) by default — they never block painting. That ordering — render → commit → effect — is what makes them safe for synchronization: the UI the user sees is already correct before you touch the outside world.

Worked examples, from trivial to real

function ChatRoom({ roomName, unread }) {
  useEffect(() => {
    document.title = unread > 0
      ? `(${unread}) ${roomName}`
      : roomName;
  }, [roomName, unread]);      // re-syncs whenever these render inputs change
  // no cleanup needed — the next setup overwrites the title
}

function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);  // REQUIRED
  }, []);  // [] is correct: the listener reads nothing reactive
          // (setWidth is stable and exempt from deps)
}

function Countdown({ secondsLeft, onDone }) {
  useEffect(() => {
    const id = setInterval(() => {
      setSecondsLeft((s) => s - 1);            // functional update: no stale value
    }, 1000);
    return () => clearInterval(id);            // no orphan intervals, ever
  }, []);                                       // timer cadence never changes

  useEffect(() => {
    if (secondsLeft === 0) onDone();
  }, [secondsLeft, onDone]);
  // ...
}

function useChatSocket(serverUrl, roomId) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    const socket = new WebSocket(`${serverUrl}/rooms/${roomId}`);   // setup

    socket.onmessage = (event) => {
      setMessages((prev) => [...prev, JSON.parse(event.data)]);
    };

    return () => socket.close();               // cleanup: disconnect
  }, [serverUrl, roomId]);                      // re-connect when room changes

  return messages;
}

Watch the room change: cleanup closes the old socket, then setup opens the new one. An effect that can set up must be able to clean up — Strict Mode in development proves it by mounting, unmounting, and remounting every component once (Module 02). If your effect breaks under Strict Mode, it would also break in production under remounts, Fast Refresh, or route changes — the double-run is the test suite you did not know you had.

Data fetching: races, cancellation, stale closures

Fetching in an effect is legitimate synchronization — the external system is the server — and it hides the three classic async bugs. Here is the honest version, guards and all (a full module on the surrounding architecture is Module 18):

function useFetchProducts(query) {
  const [state, setState] = useState({ status: "loading", items: [], error: null });

  useEffect(() => {
    let ignore = false;                       // GUARD 1: stale-response flag
    const controller = new AbortController(); // GUARD 2: real cancellation

    setState({ status: "loading", items: [], error: null });

    fetch(`/api/products?q=${encodeURIComponent(query)}`, {
      signal: controller.signal
    })
      .then((res) => {
        if (!res.ok) throw new Error("HTTP " + res.status);
        return res.json();
      })
      .then((items) => {
        if (!ignore)                          // only the LATEST effect wins
          setState({ status: items.length ? "success" : "empty", items, error: null });
      })
      .catch((err) => {
        if (!ignore && err.name !== "AbortError")
          setState({ status: "error", items: [], error: err });
      });

    return () => {                           // cleanup on dep change / unmount
      ignore = true;
      controller.abort();
    };
  }, [query]);

  return state;
}
  • Race condition: user types “re” then “react”; two fetches fly; the slow first response would land last and overwrite the fresh one with stale results. The ignore flag makes every superseded effect deaf — its results are discarded.
  • Request cancellation: AbortController also frees the network/bandwidth, not just the state — the request actually stops.
  • Stale closure: an effect closes over the query of the render that created it. That is safe here precisely because query is a dependency — a new render with a new query produces a new effect with a fresh closure. Stale-closure bugs appear when reactive values are omitted from deps to “stop the effect re-running” — the effect then keeps seeing an old value forever.

Experience this exact race, deterministically, in Lab 13 — Async UI State Simulator (toggle the guard off and watch stale data win).

Dependency linting — exhaustive-deps is a correctness tool

The react-hooks/exhaustive-deps lint rule flags every reactive value (prop, state, or value derived from them) that an effect reads but does not list. Suppressing the warning is borrowing correctness debt: the omitted value freezes at its mount-time snapshot (stale closure). When the rule complains, you have three legitimate responses:

  1. Add the dependency and make the effect re-runnable (add cleanup if re-setup leaks).
  2. Move the code into an event handler if it actually responds to an interaction.
  3. Restructure: extract the changing piece, or read the latest value from a ref / reducer when re-running is genuinely wrong.

What is never legitimate: // eslint-disable-line as a reflex. The Hook Dependency Inspector workshop drills exactly this judgment.

Avoiding unnecessary Effects

// ✘ 1. Deriving state with an effect (chained setState)
useEffect(() => {
  setFullName(first + " " + last);
}, [first, last]);
// ✓ Render-time derivation:
const fullName = first + " " + last;

// ✘ 2. Resetting state via effect
useEffect(() => {
  if (userId !== prevUserId) setDraft(null);
}, [userId, prevUserId]);
// ✓ Key-based reset — remount with fresh state:
<DraftEditor key={userId} />      // identity, Module 13

// ✘ 3. Responding to user events via effect
useEffect(() => {
  if (submitted) sendAnalytics(...);
}, [submitted]);
// ✓ Event handler — the submit CLICK causes this:
function handleSubmit() { sendAnalytics(...); }

The rule of thumb: if deleting the effect and computing in render (or handling in an event) changes nothing observable, the effect should not exist. The React docs call these “You Might Not Need an Effect” patterns; they account for a large share of real-world effect bugs — extra render passes, infinite loops (setState in effect → re-render → effect → setState…), and event logic firing on mount uninvited.

When an Effect is the wrong solution — summary

  • Derived data → compute during render.
  • Responding to user actions → event handlers.
  • Resetting component state on identity change → key (Module 13).
  • Sharing logic between components → custom hooks / plain functions — an effect is not an extraction mechanism by itself.
  • Expensive initialization that renders nothing → lazy useState initializer or module scope.
  • Coordinating with a store owned elsewhere → useSyncExternalStore (Module 24) instead of manual subscribe effects.

useRef & DOM Interaction

Values that persist without re-rendering — and the DOM handshake

What a ref is

useRef(initialValue) returns a stable mutable box: { current: initialValue }. The object identity never changes across renders, and writing to ref.current does not trigger a re-render. React holds onto the box per component instance, exactly like state cells — but without the render subscription.

import { useRef } from "react";
const box = useRef(0);
box.current;        // read (any time)
box.current = 42;   // write (any time) — NO re-render requested

That single property — persistence without re-render — defines everything a ref is for. The complement diagram:

Does updating it re-render?Yes — that is its purposeNo — ever

Typical residentsFilter text, form values, open/closedTimer IDs, DOM nodes, “previous value”, “latest value”

Interactive side-by-side with live render counts: Lab 06 — useRef vs useState.

Ref rules of conduct

  • Do not read or write refs during rendering (except lazy initializers). Render must be pure — a ref write in render is a side effect that breaks Strict Mode double-rendering. Read/write in event handlers and effects.
  • Do not mirror state in a ref. If the UI needs the value, it is state — a ref copy will desync the moment a render is skipped.
  • When the value changes, you decide when the world learns: update the DOM yourself, force a render via a state change, or just let the next render pick it up.

DOM references — the primary use

import { useRef, useEffect } from "react";

function SearchDialog({ open, onClose }) {
  const inputRef = useRef(null);

  useEffect(() => {
    if (open) inputRef.current?.focus();   // imperative DOM work lives in effects
  }, [open]);

  return (
    <dialog open={open} onClose={onClose}>
      <input ref={inputRef} type="search" />
    </dialog>
  );
}

Pass ref to a host element (<input>, <div>…) and React assigns the DOM node to ref.current after mount (and resets it to null before unmount). Everything you would do with querySelector is available — but scoped to your element, with no global lookups and no stale-selector bugs.

Focus management — a complete pattern

function Modal({ open, onClose, children }) {
  const panelRef = useRef(null);
  const restoreRef = useRef(null);          // who had focus before we opened?

  useEffect(() => {
    if (!open) return;
    restoreRef.current = document.activeElement;      // remember the trigger
    panelRef.current?.querySelector("button")?.focus();

    return () => restoreRef.current?.focus?.();      // give it back on close
  }, [open]);

  return open ? (
    <div className="backdrop" onClick={onClose}>
      <div ref={panelRef} role="dialog" aria-modal="true">{children}</div>
    </div>
  ) : null;
}

Measuring elements

import { useState, useEffect, useRef } from "react";

export function useElementSize() {
  const ref = useRef(null);
  const [size, setSize] = useState({ width: 0, height: 0 });

  useEffect(() => {
    if (!ref.current) return;
    const observer = new ResizeObserver((entries) => {
      const r = entries[0].contentRect;            // external system: layout
      setSize({ width: Math.round(r.width), height: Math.round(r.height) });
    });
    observer.observe(ref.current);
    return () => observer.disconnect();           // cleanup, always
  }, []);

  return [ref, size];   // caller spreads: <div ref={ref} />
}

Scroll positions work the same way: ref.current.scrollTop, scrollIntoView({ behavior: "smooth" }). useLayoutEffect (the layout-timed variant that runs before paint) is the right tool when you must read layout and synchronously adjust it to avoid flicker — rare, and it blocks painting, so justify each use.

Storing timer IDs and other handles

function AutoSave({ markdown }) {
  const timerRef = useRef(null);

  useEffect(() => {                          // debounced save, Module 15 style
    timerRef.current = setTimeout(() => save(markdown), 800);
    return () => clearTimeout(timerRef.current);
  }, [markdown]);
  // The id never needs to re-render anything — a ref is the honest home.
}

usePrevious — the classic ref pattern, with timing caveats

export function usePrevious(value) {
  const ref = useRef(null);
  useEffect(() => {          // runs AFTER commit
    ref.current = value;      // so during THIS render, ref.current is the
  });                         // value from the PREVIOUS committed render
  return ref.current;
}

const prevCount = usePrevious(count);

Timing semantics you must state aloud when using it: the returned value updates after the render commits — on the first render it is null/initial, and a child that reads it during render gets the previous-previous value in rapid chains. Use cases that respect this: logging changes, diffing for animations, “show if increased”. Use cases that do not: anything needing the old value synchronously inside the current render — that requires restructuring or render-time comparison of the last committed output.

Callback refs and React-version differences

Instead of a ref object, pass a function — React calls it with the node (and with null on unmount):

<input ref={(node) => {
  if (node) node.focus();            // node attached
  // return nothing — React 19 treats a returned function as cleanup
}} />

Two version facts. First, React 19 added ref cleanup functions: a callback ref may return a cleanup function, symmetric with effects. Second, React 19 made ref a normal prop for function components — you can accept ref in props directly:

● React 18 and earlier — forwardRef required
● React 19 — ref is just a prop

Library components supporting React 18 still need forwardRef; apps targeting 19 only can drop it. When forwarding to DOM nodes, also forward className and spread ...rest — a wrapper that swallows props breaks consumer expectations.

Ref cleanup considerations

Refs hold no automatic teardown: an interval id stored in a ref still needs clearInterval in an effect cleanup; a DOM node reference in a ref that outlives the element is a leak (React nulls attached element refs automatically, but refs you assign manually are yours to clear). Treat ref.current as a piece of imperative state with no lifecycle manager — you are the lifecycle manager.

!The escape-hatch rule
Every time you write ref.current.<something>, you step outside React’s model — legitimate for focus, measurement, media playback, canvas, third-party widgets and integration seams; a code smell for anything React already does declaratively (visibility via hidden DOM attribute instead of conditional rendering, classes instead of props). If you find yourself “manually updating the DOM to match state”, stop — that is React’s job, and doing it twice creates the desync bugs React exists to prevent.

useContext & the Context API

Distributing values through the tree — without the drilling, with eyes open to the costs

What Context solves

Context is React’s built-in mechanism for passing a value to an entire subtree without threading it through props at every level. A provider declares the value high in the tree; any descendant — ten levels deep if needed — reads it directly with useContext. Components between them never see it. Context is a distribution mechanism, not a state manager: something still has to own the value (usually useState/useReducer in the provider) — context only moves it from owner to consumers.

The three-step API

import { createContext, useContext, useState, useCallback } from "react";

// 1. Create the context (the argument is the DEFAULT value —
//    used when no Provider is above the consumer).
const ThemeContext = createContext(null);

// 2. Provide it — own the state here, expose an intentional API.
export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState(() => localStorage.getItem("theme") ?? "dark");

  const toggle = useCallback(() => {
    setTheme((t) => {
      const next = t === "dark" ? "light" : "dark";
      localStorage.setItem("theme", next);
      return next;
    });
  }, []);

  return (
    <ThemeContext.Provider value={{ theme, toggle }}>
      {children}
    </ThemeContext.Provider>
  );
}

// 3. Consume it — a custom hook is the convention: clearer callsites
//    and ONE place to enforce provider presence.
export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (ctx === null) throw new Error("useTheme must be used inside <ThemeProvider>");
  return ctx;
}

// App.jsx
<ThemeProvider>
  <Layout />          {/* Layout, Sidebar, MenuButton — none see theme props */}
</ThemeProvider>

// MenuButton.jsx — 5 levels deeper, zero intermediate props
function MenuButton() {
  const { theme, toggle } = useTheme();
  return (
    <button className={"btn btn--" + theme} onClick={toggle}>
      Switch to {theme === "dark" ? "light" : "dark"}
    </button>
  );
}

Defaults, providers, and reading rules

  • Default value (the createContext(default) argument) applies only when no provider exists above. For app-wide contexts, pass null and throw in the custom hook — silent defaults create invisible misconfigurations. For optional contexts (feature flags defaulting to “off”), a real default is right.
  • Nearest provider wins: nested providers shadow outer ones — the consumer reads the closest ancestor. This enables region overrides (a light-themed marketing island inside a dark app).
  • Reading is per-component: every component calling useContext(C) subscribes to C individually.
  • Updating context is just calling a function the provider exposed — state flows down like any props, and the whole provider subtree re-renders with the new value.

Authentication context — the second classic

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);           // null = signed out
  const [status, setStatus] = useState("checking"); // checking|signedIn|signedOut

  useEffect(() => {                                 // restore the session once
    let ignore = false;
    fetch("/api/me")
      .then((r) => r.json())
      .then((u) => { if (!ignore) { setUser(u); setStatus("signedIn"); } })
      .catch(() => { if (!ignore) setStatus("signedOut"); });
    return () => { ignore = true; };
  }, []);

  const signIn = useCallback(async (credentials) => {
    const u = await api.signIn(credentials);         // may throw — caller renders errors
    setUser(u); setStatus("signedIn");
  }, []);

  const signOut = useCallback(async () => {
    await api.signOut();
    setUser(null); setStatus("signedOut");
  }, []);

  const value = { user, status, signIn, signOut };
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth requires <AuthProvider>");
  return ctx;
}

The status field is deliberate: “not signed in” and “not checked yet” are different states, and conflating them causes the famous flash-of-wrong-content. Locale/settings contexts follow the same shape.

Context and re-render behavior — the cost model

When a provider’s value changes, every component calling useContext on that context re-renders, along with their subtrees (unless memoized). Two consequences rule context design:

  1. Object identity is the trigger. value={{ theme, toggle }} creates a fresh object every provider render — even with identical contents, every consumer re-renders on any unrelated provider state change. Fix with useMemo: 
    const value = useMemo(() => ({ theme, toggle }), [theme, toggle]);
// consumers now re-render only when theme identity changes
  2. Frequently-changing values spread the blast radius. A context holding mousePosition updated at 60 Hz re-renders every consumer 60 times a second. That is not a context bug — it is the wrong tool: co-locate such state, or move it to an external store consumed surgically (Module 24, useSyncExternalStore).

Context splitting

The standard cure for an over-stuffed context: split by change frequency and by consumer group. A bloated AppContext holding user, theme, locale, cart and toasts forces the entire gang to re-render together. Split it: ThemeContext (rarely changes), AuthContext (rarely), CartContext (changes constantly, consumed by few). Rule: one context per change frequency, per audience. When splitting a context whose value and setter change at different rates, go further — StateContext + DispatchContext (consumers that only dispatch never re-render on value changes).

The shopping cart reducer — complete

export const initialCart = { items: [], coupon: null, status: "shopping" };
// status: "shopping" | "checking-out" | "paid" | "error"

export function cartReducer(state, action) {
  switch (action.type) {
    case "item/added": {
      const existing = state.items.find((i) => i.id === action.item.id);
      return {
        ...state,
        items: existing
          ? state.items.map((i) =>
              i.id === action.item.id ? { ...i, qty: i.qty + action.item.qty } : i
            )
          : [...state.items, action.item],
      };
    }
    case "item/removed":
      return { ...state, items: state.items.filter((i) => i.id !== action.id) };

    case "item/qtyChanged":
      return {
        ...state,
        items: state.items.map((i) =>
          i.id === action.id ? { ...i, qty: Math.max(1, action.qty) } : i
        ),
      };

    case "coupon/applied":
      return { ...state, coupon: action.coupon };

    case "checkout/started":
      return { ...state, status: "checking-out" };

    case "checkout/succeeded":
      return { items: [], coupon: null, status: "paid" };

    case "checkout/failed":
      return { ...state, status: "error", error: action.reason };

    case "cart/dismissedError":
      return { ...state, status: "shopping", error: undefined };

    default:
      throw new Error("Unknown action: " + action.type);   // never silently no-op
  }
}

  switch (action.type) {
    case "field/changed":
      return { ...state, data: { ...state.data, [action.field]: action.value } };

    case "step/next":
      if (state.step >= 3) return state;             // guard: no step 4 exists

    case "step/back":

    case "submit/succeeded":

Rendering Fundamentals & React’s Render Cycle

Trigger → Render → Reconcile → Commit → Paint — the model behind every behavior in this guide

What “rendering” means in React — three meanings you must keep apart

  1. React render (this module): React calling your component functions to compute what the UI should be. Pure computation — no DOM touched.
  2. React commit: React applying the computed differences to the actual DOM.
  3. Browser paint: the browser drawing pixels to the screen. React does not paint — it only triggers conditions under which the browser will.

Most React confusion is a category error between these three. “It rendered” does not mean “the DOM changed”; “the DOM changed” does not mean “pixels moved”. Keeping the pipeline explicit dissolves whole bug families.

The pipeline

1 · TRIGGERsetState / root render
2 · RENDERcomponent functions run
3 · RECONCILEdiff new vs old tree
4 · COMMITmutate the DOM
5 · PAINTbrowser draws
state update→pure computation→plan→apply→pixels

Step through it live, trigger by trigger, in Lab 09 — React Render Cycle Visualizer; trace a real component tree in Workshop 1 — Render Trace Studio. Full-size diagram: Visual Model 8.

Step 1 — What triggers a render

  • Initial render: createRoot(...).render(<App />) mounts the tree once.
  • State update in a component: setState, dispatch, or a context value change above it — after the event’s handlers finish (batched).
  • Parent re-render: when a component re-renders, React re-renders its children by default — recursively, regardless of whether their props changed. (This — not “props changed” — is why children re-render; stopping it is React.memo’s job, Module 14.)

A render is scheduled, not immediate: React prioritizes (urgent input above expensive transitions) and may batch several updates into one pass. Nothing about a scheduled render guarantees it completes — a newer update can interrupt and supersede it (concurrent rendering, Module 24).

Step 2 — The render phase: your functions run

React calls the affected component function with its current props and state snapshots; your JSX evaluates to a new tree of elements. Two hard rules:

!Render must be pure
Same inputs, same output — and no side effects: no network calls, no localStorage writes, no mutating outer variables, no Math.random()/Date.now() driving output, no DOM manipulation. Your component may run multiple times per commit (Strict Mode in dev, interrupted/retried renders in concurrent React) — code with side effects in render will execute those effects the same number of times, visibly.

Purity is also why state is a snapshot (Module 06): each render sees a frozen props + state pair. The function is a photograph-taking machine; it never sees the future.

Step 3 — Reconciliation: comparing trees

With the freshly computed tree, React compares it element-by-element against the previous tree, starting at the changed component and walking down. The comparison is heuristic and fast — not a full-app diff:

  • Different element type at a position (e.g., <section> became <div>, or Profile became Settings) → React destroys that subtree (state included) and mounts the new one. No reuse is attempted.
  • Same type → React keeps the existing component instance and DOM node, updates changed props/attributes, and recurses into children.
  • Lists → keys disambiguate which child is which (Module 13).

Step 4 — Commit: the only DOM moment

After reconciliation produces a mutation plan, React applies it synchronously and atomically: DOM nodes created/removed, attributes updated, refs attached/detached. If the reconciled output is identical to what is already in the DOM, the commit applies nothing — a re-render with unchanged output costs CPU, not DOM churn. (Why “my component re-renders but the DOM is untouched” is a normal, healthy observation.) Effects from this render run after the commit (Module 08): layout effects before paint, passive effects after.

Step 5 — Browser paint (React’s neighbor, not React’s job)

After commit, the browser schedules a paint when it decides to — style recalculation, layout, compositing, raster. React neither paints nor directly controls paint timing (except deliberate escapes: useLayoutEffect runs before it, flushSync forces through it). A committed change might never paint if superseded before the next frame. When you profile “slow React”, always check which stage is actually slow — script (render/commit) vs rendering vs painting & compositing — before optimizing the wrong thing (Module 14).

Why rendering happens more than once

  • Strict Mode (dev only): renders each component twice to surface impurity — if the double result differs, your render is impure.
  • Concurrent interruption: a low-priority render can be abandoned when something urgent arrives, then restarted later.
  • Chained state updates: an effect that sets state after commit schedules another pass (the “extra render” of effect-driven derivations — a reason to avoid them, Module 08).
  • Parent cascades: an update high in the tree re-renders the whole subtree once — but each child’s function runs in that same pass, not separately.

A component can re-render 100 times without remounting — and remounting once (via a changed key or type) discards state that 100 re-renders would have preserved. That distinction is the subject of Module 13.

User clicks “Select 42”. The full trace:

  2. Render (Page) — React calls Page with the new snapshot: selectedId = 42. Its JSX computes; ProductTable is same-type, so React recurses.

Reconciliation, Keys & Component Identity

Why state survives some updates and vanishes in others — element identity, precisely

Element identity: what React actually tracks

Every element React renders has an implicit identity made of exactly two things: its type (the tag or component function) and its position in the tree relative to its siblings — disambiguated by the key when siblings share a type. When the next render produces the same type+key at the same position, React treats it as the same component: it keeps the DOM node, keeps all state (hooks, local state, input contents), and just updates props. Different type or different key: React treats it as a new component — the old one unmounts (state destroyed, cleanup runs), a fresh one mounts. That single rule explains every “why did my state disappear?” mystery.

iNot a full diff
Reconciliation is heuristic and local: React compares a position’s new element type/key against the old one and recurses — it never re-homes a moved component to a far-away position, and it does not diff the whole application on every update. The algorithm trades perfect minimal-DOM for speed and predictability; the trade is what keys let you control.

The two outcomes, demonstrated

● TYPE CHANGE — state destroyed
● SAME TYPE — state preserved

Neither outcome is “the bug” — they are two tools. You choose reset or preserve by choosing types and keys. The failures come from choosing accidentally.

Keys and list rendering

// Same type (<TodoRow />), four siblings — the key is the ONLY
// thing telling React which old-render row is which new-render row:
{todos.map((todo) => (
  <TodoRow key={todo.id} todo={todo} />
))}

Without keys React warns; with stable, domain-meaningful keys (an id from your data), reordering the array reorders DOM nodes while each row keeps its state — exactly what users expect. Keys must be unique among siblings only, and stable across renders.

Why array indexes are dangerous

Index keys tell React “row #0 is row #0, forever” — but when the list reorders, row #0 is now a different todo. React dutifully preserves state and DOM for position, so state attaches to the wrong item:

const [todos, setTodos] = useState([
  { id: "t1", text: "Ship invoice page" },   // index 0
  { id: "t2", text: "Fix timezone bug" },    // index 1
]);

// Each row keeps LOCAL state — say, an open "edit mode" toggle
// — and an uncontrolled input draft:

{todos.map((todo, index) => (
  <TodoRow key={index} todo={todo} />      // ✘ index key
))}

// User opens edit mode on "Ship invoice page" (index 0),
// then DELETES it. Array shifts: "Fix timezone bug" is now index 0.
// React reconciles: same type, same key(0) → "same component!"
// → edit-mode=true now belongs to "Fix timezone bug".
// The user's edit draft visibly teleports to the wrong todo.

Index keys are acceptable only when the list is static (never reorders, never inserts/deletes in the middle) and items have no state — and even then a stable id costs nothing. Math.random() keys are always wrong: they destroy identity on every render, remounting everything. Performance Optimization & Rendering Behavior

Measure first — then move state, split components, and only then memoize

What actually causes performance problems

React apps feel slow for a small set of reasons, in rough order of real-world frequency:

  1. Doing too much work per render — expensive computation or huge JSX trees running inside components that re-render often.
  2. Render cascades — state placed too high, so a keystroke re-renders half the application (Module 12’s trace, multiplied).
  3. Mounting too much — giant initial bundles and mounting thousands of DOM nodes at once; network waterfalls (Module 18).
  4. Unnecessary remounting — identity bugs (Module 13) destroying and rebuilding trees.
  5. Non-React costs — layout thrash, huge images, blocking scripts; React is innocent and optimizing it is wasted effort.

The memoization trio (React.memo, useMemo, useCallback) addresses only #1 and partially #2 — which is why reaching for it before measuring usually optimizes nothing.

Measure before optimizing

  • React DevTools Profiler: record an interaction; it shows every component that rendered, why (state change / parent render / context change / hook change), and how long each took. The “Highlight updates” option flashes re-rendered regions — the fastest way to see a cascade.
  • Chrome Performance panel: distinguishes scripting (React’s render/commit) from rendering/layout/paint. If scripting is small, memoization cannot help — look at CSS/layout/images instead.
  • Console counting (crude but clarifying): console.count("ProductRow") inside the component body during a realistic interaction.
!Profiler dev caveat
Dev-mode timings are inflated (extra checks, Strict Mode double work) and can misrank cheap components. Use relative comparisons in dev — who renders how often — and production builds for absolute numbers. A component rendering 40 times at 0.1 ms is a non-issue; one rendering twice at 80 ms is the target.

The referential-equality problem

Everything in this module hinges on one JavaScript fact: {a: 1} !== {a: 1} and (() => {}) !== (() => {}) — fresh objects, arrays and functions are new references every time. Props containing freshly-created references always look “changed” to a memoized child, defeating the memo:

const ExpensiveList = React.memo(function ExpensiveList({ items, onSelect }) {
  return /* 800 rows of rendering */;
});

function Parent() {
  const [query, setQuery] = useState("");           // typing → Parent re-renders

  const items = getFilteredItems(query);            // new array reference ✘
  const onSelect = (id) => select(id);              // new function reference ✘

  return <ExpensiveList items={items} onSelect={onSelect} />;
  // React.memo compares props: items changed? YES (new []).
  // Semantically identical, referentially different → memo useless.
}

The toolkit: memo, useMemo, useCallback

import { memo, useMemo, useCallback, useState } from "react";

  return /* 800 rows */;
});
// memo: skip RE-RENDERING this component when all props are
// referentially equal. It does NOT cache results by itself —
// it only makes prop equality a useful signal.

function Parent({ allItems }) {
  const [query, setQuery] = useState("");

  const items = useMemo(                            // cache the REFERENCE
    () => expensiveFilter(allItems, query),
    [allItems, query]                               // recompute only when these change
  );

  const onSelect = useCallback(                     // cache the FUNCTION reference
    (id) => console.log("selected", id),
    []                                              // empty: same function forever
  );

  return <ExpensiveList items={items} onSelect={onSelect} />;
  // Now typing in an UNRELATED parent state (not query) can skip
  // ExpensiveList entirely — but a query change still re-renders it,
  // because items genuinely changed. Correct behavior.
}

They do not make your app fast, do not parallelize work, and do not skip the first render. Every use adds comparison + memory cost and a dependency list to maintain. Prefer structural fixes: state placement and component splitting

● BEFORE — state too high, everything re-renders
● AFTER — state pushed down to its consumers

State placement is the highest-leverage performance tool in React: put each piece of state as close to its consumers as possible, and every update becomes cheap by construction — no memo tables, no dependency lists, no staleness risk. The same logic applies to component splitting: extracting the changing part (the animated badge, the ticking clock) into its own component walls off its renders from its neighbors.

Context-related re-rendering

A context value change re-renders every consumer, no matter how deep. Countermeasures, in order: split contexts by change frequency (Module 10); memoize the provider value; move frequently-changing values out of context entirely; select surgically with an external store when only 2 of 200 consumers need the churning value. Custom Hooks & Reusable Logic

Extract behavior, not wrappers — six production-grade hooks, built and critiqued

What a custom hook is — and is not

A custom hook is a function whose name starts with use and that calls other hooks. That is the entire definition — no registration, no special API. It is React’s mechanism for reusing stateful logic between components: each caller gets independent state (the hooks inside run against that component’s cells), but the logic is written once. Custom hooks extract behavior; components extract markup; the two compose freely.

  • Sharing logic ≠ sharing state — two components using useLocalStorage("theme") each have their own slice unless you add an external store underneath.
  • The use prefix is a contract with the linter: inside this function, the Rules of Hooks apply and are checked.
  • Return value conventions: return a tuple for 2–3 heterogeneous items ([value, setValue]), an object for many named items.

useLocalStorage — state that survives reloads

import { useState, useEffect, useCallback } from "react";

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {          // lazy: read once
    try {
      const raw = window.localStorage.getItem(key);
      return raw !== null ? JSON.parse(raw) : initialValue;
    } catch {
      return initialValue;                            // private mode, quota, corrupted
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {
      /* storage unavailable — state still works in memory */
    }
  }, [key, value]);

  const remove = useCallback(() => {
    try { window.localStorage.removeItem(key); } catch { /* noop */ }
    setValue(initialValue);
  }, [key]);

  return [value, setValue, remove];
}

// Usage: const [theme, setTheme] = useLocalStorage("theme", "dark");

Design notes: lazy initialization avoids re-reading storage on every render; every storage call is guarded (Safari private mode throws); JSON round-trips support any serializable value. Limitation to state aloud: this does not sync across tabs — add a storage event listener if you need that, or use useSyncExternalStore with a storage-backed store for true multi-tab sync.

useDebounce — delay a churning value

import { useState, useEffect } from "react";

export function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);      // every new value cancels the pending one
  }, [value, delay]);

  return debounced;
}

// Usage — search that fires after the user pauses:
const debouncedQuery = useDebounce(query, 400);
useEffect(() => {
  if (debouncedQuery) search(debouncedQuery);
}, [debouncedQuery]);

Note what this hook is not: it is not a throttler (max frequency) and not a debounce of the callback — it debounces the value, which composes better with React’s data flow. Cleanup is the correctness mechanism: without it, every keystroke would eventually fire.

useFetch — with its limitations stated honestly

import { useState, useEffect, useCallback } from "react";

export function useFetch(url) {
  const [state, setState] = useState({ status: "loading", data: null, error: null });

  useEffect(() => {
    let ignore = false;
    const controller = new AbortController();

    setState({ status: "loading", data: null, error: null });   // restart per URL
    fetch(url, { signal: controller.signal })
      .then((res) => {
        if (!res.ok) throw new Error("HTTP " + res.status);
        return res.json();
      })
      .then((data) => { if (!ignore) setState({ status: "success", data, error: null }); })
      .catch((error) => {
        if (!ignore && error.name !== "AbortError")
          setState({ status: "error", data: null, error });
      });

    return () => { ignore = true; controller.abort(); };
  }, [url]);

  return state;
}

The stated limitations (why production apps reach for a query library — Module 18): no cache (remounting refetches), no deduplication (three components = three requests), no revalidation, no mutation story, no retry/backoff, no pagination or prefetching. TanStack Query is this hook plus all of that, battle-tested. Build useFetch once to understand the machinery; ship a query library for real apps.

usePrevious — with timing semantics

Covered in Module 09 (refs): it returns the value from the previous committed render, updated after commit — right for change-logging and diff-driven effects, wrong for synchronous render decisions. When a custom hook has subtle timing, document it in the hook file; the docstring is part of the API.

Designing custom hooks — the checklist

  • Name it after behavior, not implementation: useDebouncedQuery, not useTimeoutState.
  • Accept functions/values that change as arguments — do not hide them in the closure if the caller needs control.
  • Return the minimum: every extra returned reference is API surface you maintain.
  • Clean up everything: an event-listener hook without cleanup is a leak factory — Strict Mode’s double-mount will usually expose it in dev.
  • Keep it pure of rendering: hooks return data/functions, never JSX (a hook returning markup is a component wearing a disguise).
  • Test it in isolation: renderHook from React Testing Library exercises a hook without building a component around it (Module 22).

HTML forms in React

React renders form elements like any element, but inputs are special: they own internal state (what the user typed). React’s choice is which side owns that state — you (controlled) or the DOM (uncontrolled).

● UNCONTROLLED — the DOM keeps the value; you visit it

Validation strategy

function validateRegistration(values) {
  const errors = {};                                   // plain function → unit-testable

  if (!values.email) errors.email = "Email is required.";
  else if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(values.email))
    errors.email = "Enter a valid email address.";

  if (!values.password) errors.password = "Password is required.";
  else if (values.password.length < 10)
    errors.password = "Use at least 10 characters.";

  if (values.password !== values.confirm)
    errors.confirm = "Passwords do not match.";

  return errors;
}

Accessibility and native validation

  • Every input needs a programmatic label (<label htmlFor> or wrapping <label>); errors belong in aria-describedby with aria-invalid on the input (the Field above does both).

Events, User Interaction & UI Patterns

Event behavior, then the reusable patterns: modals, dropdowns, tabs, tooltips, toasts — built accessibly

React event handling

Handlers are functions passed as props: onClick, onChange, onSubmit, onMouseEnter, onKeyDown… They receive a synthetic event — a wrapper around the native event with a normalized cross-browser interface (e.target, e.preventDefault(), e.stopPropagation(), and all properties you know from the DOM). Historically (React 16 and earlier) the wrapper was pooled and recycled — accessing it asynchronously crashed — but pooling was removed in React 17; today’s synthetic events are ordinary objects you can keep and read later. Under the hood, React attaches few real listeners at the root and dispatches through its own system (event delegation) — an implementation detail, until the day a native listener on document sees events in an order that surprises you.

function Toolbar({ onRun, onSave }) {
  return (
    <div onClick={() => console.log("toolbar clicked")}>      {/* parent */}
      <button onClick={(e) => { e.stopPropagation(); onRun(); }}>
        Run                                   {/* stopPropagation: parent stays silent */}
      </button>
      <a href="/docs" onClick={(e) => {
        if (!e.metaKey && !e.ctrlKey) {       // let Cmd+click open a new tab
          e.preventDefault();                 // no native navigation
          showDocsInApp();

      }}>Docs</a>

  • Propagation: events bubble child → parent, same as the DOM; e.stopPropagation() fences a handler.
  • preventDefault stops the browser default (navigation, form reload) but not propagation — and vice versa.
  • Keyboard: onKeyDown/onKeyUp with e.key ("Escape", "Enter", "Tab") power menus, comboboxes and dialogs.
  • Handlers fire during React’s event processing; state updates inside them are batched (Module 06).

Focus management

Keyboard users navigate by focus; interactive UIs must manage it deliberately: move focus into a dialog on open, return it to the trigger on close, trap it inside while open (Tab cycles within), and never leave focus on a removed element (Module 09 shows the ref mechanics). Test every pattern you build with the keyboard alone — if you can operate it without touching the mouse, you are most of the way to accessible.

Modal — portals + focus + escape

import { useEffect, useRef } from "react";
import { createPortal } from "react-dom";

export function Modal({ open, onClose, title, children }) {
  const panelRef = useRef(null);
  const restoreRef = useRef(null);

  useEffect(() => {
    if (!open) return;
    restoreRef.current = document.activeElement;
    panelRef.current?.focus();

    const onKeyDown = (e) => {
      if (e.key === "Escape") onClose();
      if (e.key === "Tab") {                       // naive focus trap
        const focusables = panelRef.current.querySelectorAll(
          "button, [href], input, select, textarea, [tabindex]:not([tabindex='-1'])"
        );
        if (focusables.length === 0) return;
        const first = focusables[0], last = focusables[focusables.length - 1];
        if (e.shiftKey && document.activeElement === first) { e.preventDefault(); last.focus(); }
        else if (!e.shiftKey && document.activeElement === last) { e.preventDefault(); first.focus(); }
      }
    };
    document.addEventListener("keydown", onKeyDown);
    document.body.style.overflow = "hidden";        // no background scroll

    return () => {
      document.removeEventListener("keydown", onKeyDown);
      document.body.style.overflow = "";
      restoreRef.current?.focus?.();                // give focus back
    };
  }, [open, onClose]);

  if (!open) return null;

  return createPortal(                              // escape z-index/overflow prisons
    <div className="modal-backdrop" onMouseDown={(e) => { if (e.target === e.currentTarget) onClose(); }}>
      <div ref={panelRef} role="dialog" aria-modal="true" aria-label={title}
           tabIndex={-1} className="modal-panel">
        <h2>{title}</h2>
        {children}
      </div>
    </div>,
    document.body                                   // render at the document root
  );
}

Portals (createPortal) render children into a different DOM subtree while keeping them inside the React tree — context, event bubbling to React parents, and reconciliation all still work. Use them for modals, dropdowns and tooltips trapped inside overflow: hidden or low z-index ancestors. What they do not change: the component still lives at its React position — only the DOM placement moves.

Dropdown — the interaction pattern

import { useState, useRef, useEffect } from "react";

export function DropdownMenu({ label, items }) {
  const [open, setOpen] = useState(false);
  const rootRef = useRef(null);

  useEffect(() => {
    if (!open) return;
    const onPointerDown = (e) => {                 // click-outside close
      if (!rootRef.current?.contains(e.target)) setOpen(false);
    };
    const onKey = (e) => { if (e.key === "Escape") setOpen(false); };
    document.addEventListener("pointerdown", onPointerDown);
    document.addEventListener("keydown", onKey);
    return () => {                                 // both, cleaned up
      document.removeEventListener("pointerdown", onPointerDown);
      document.removeEventListener("keydown", onKey);
    };
  }, [open]);

  return (
    <div ref={rootRef} className="dd">
      <button aria-haspopup="menu" aria-expanded={open}
              onClick={() => setOpen((o) => !o)}>
        {label}
      </button>
      {open && (
        <ul role="menu" className="dd-menu">
          {items.map((item) => (
            <li key={item.id} role="none">
              <button role="menuitem" onClick={() => { item.onSelect(); setOpen(false); }}>
                {item.label}
              </button>
            </li>
          ))}
        </ul>
      )}
    </div>
  );
}

  • Tooltip: extra, non-essential information on hover/focus. Must be dismissible (Escape), hoverable, and never the only home of essential info. A title attribute is often enough; a custom one needs aria-describedby and careful show/hide delays. For interactive content inside, you have built a popover, not a tooltip — different rules.
  • Toast: transient notification. Render via portal, role="status" (or alert for urgent), auto-dismiss with a pause-on-hover timer stored in a ref (never state — the timer id does not render), and manage a queue with a reducer (Module 11’s notification manager).

Error boundaries

import { Component } from "react";

export class ErrorBoundary extends Component {
  state = { error: null };

  static getDerivedStateFromError(error) {          // render-phase: set fallback state
    return { error };
  }

  componentDidCatch(error, info) {                   // side-effect: report
    logErrorToService(error, info.componentStack);
  }

  render() {
    if (this.state.error) {
      return this.props.fallback ?? <p>Something went wrong. <button onClick={() => this.setState({ error: null })}>Retry</button></p>;
    }
    return this.props.children;
  }
}

// Wrap any subtree; a crash inside stays inside:
<ErrorBoundary fallback={<RouteError />}>
  <WidgetGrid />
</ErrorBoundary>

Error boundaries catch render/lifecycle errors in their subtree and show a fallback instead of a white screen. They do not catch: event handler errors (those are just JavaScript — wrap handlers), async code, errors in the boundary itself, or SSR. There is no official function-component equivalent; the community pattern composes them via a wrapper, and React 19’s docs still ship the class API. Place boundaries per meaningful region (route, panel, widget) — one boundary at the root recovers nothing gracefully.

  • Every interactive element is a <button>, <a href>, or real form control — not a clickable <div>.
  • Hover states have :focus-visible equivalents; focus is never removed (outline is restyled, not deleted).
  • Busy actions show pending state and disable double-submits.

Data Fetching, Async UI & Server State

The four states, race conditions, optimistic updates — and what a query library actually buys

Client state versus server state — the distinction that organizes everything

Client state lives and dies in the browser: form drafts, open menus, active tab — useState/useReducer are the right homes. Server state is a cached reflection of data owned by the server: it can go stale without you knowing, needs refetching, has loading/error states per request, and is shared by many components. Treating server state like client state (copy it into a useState once) produces every classic bug: stale pages, no refetch after mutations, three components fetching the same thing. Naming the distinction is what justifies the query-library category below.

The four states (and every UI must model all of them)

type Status = "loading" | "success" | "empty" | "error";
// empty = the request succeeded and honestly found nothing
// — a SUCCESS outcome, rendered differently from a failure.
// (States-as-a-union, Module 11 — impossible combos unrepresentable.)

import { useState, useEffect } from "react";

function ProductList({ query }) {
  const [state, setState] = useState({
    status: "loading", items: [], error: null,
  });

  useEffect(() => {
    let ignore = false;                          // stale-response guard (Module 08)
    const controller = new AbortController();

    setState({ status: "loading", items: [], error: null });
    fetch(`/api/products?q=${encodeURIComponent(query)}`, { signal: controller.signal })
      .then((res) => {
        if (!res.ok) throw new Error("HTTP " + res.status);
        return res.json();
      })
      .then((items) => {
        if (ignore) return;
        setState({ status: items.length ? "success" : "empty", items, error: null });
      })
      .catch((error) => {
        if (ignore || error.name === "AbortError") return;
        setState({ status: "error", items: [], error });
      });

    return () => { ignore = true; controller.abort(); };
  }, [query]);

  return (
    <section aria-live="polite" aria-busy={state.status === "loading"}>
      {state.status === "loading" && <ProductGridSkeleton rows={6} />}

      {state.status === "empty" && (
        <EmptyState
          title="No products match"
          hint={`Nothing found for “${query}”. Try a broader term.`}
        />
      )}

      {state.status === "error" && (
        <ErrorState
          message={String(state.error)}
          onRetry={() => setState((s) => ({ ...s, status: "loading" }))}
        />
      )}

      {state.status === "success" && <ProductGrid items={state.items} />}
    </section>
  );
}

Every async surface you build is this skeleton plus domain polish: skeletons over spinners for content-shaped regions (they set size expectations), retry with visible affordance for errors, honest empty states that suggest the next action, and aria-live/aria-busy so screen readers know a region is changing. All states are exercised deterministically — loading, error, cancel, stale, race — in Lab 13.

Race conditions and stale responses — the complete catalog

  1. Out-of-order responses (the classic): two fetches, slow first, fast second — stale data overwrites fresh. Fix: the ignore flag / AbortController (above), or a query library’s key-based last-write-wins.
  2. Missing cleanup: unmount mid-flight, then setState on a dead component (memory pressure, warnings, potential crashes in old patterns). Fix: cleanup function always aborts.
  3. Waterfalls: component A fetches, then child B fetches from A’s result, then C… latency adds serially. Fix: fetch in parallel (Promise.all at the top, or colocate queries — libraries dedupe automatically).
  4. Refetch storms: an effect keyed on an unstable dependency (object/array literal created in render) refetches every render. Fix: stabilize the dependency (useMemo / key primitives).

Optimistic updates

Show the expected result before the server confirms — for interactions where the user’s intent is near-certain (likes, renames, reordering):

async function rename(todoId, nextTitle) {
  const previous = queryClient.getQueryData(["todos"]);   // remember truth
  queryClient.setQueryData(["todos"], (todos) =>          // paint the guess
    todos.map((t) => (t.id === todoId ? { ...t, title: nextTitle } : t))
  );
  try {
    await api.rename(todoId, nextTitle);                  // confirm
  } catch (error) {
    queryClient.setQueryData(["todos"], previous);        // roll back
    toast.error("Rename failed — reverted.");
  } finally {
    await queryClient.invalidateQueries(["todos"]);       // converge on server truth
  }
}

The pattern’s price is honesty about failure: every optimistic write needs a rollback path and a notification. Reserve it for high-frequency, low-risk actions; payments and deletes get the pessimistic treatment. React 19 adds useOptimistic to model the same idea declaratively (Module 24).

Routing & Navigation

Client-side routing with React Router — nested routes, protected pages, URL as state

Why client-side routing exists

A traditional multi-page site requests a new HTML document per navigation. A single-page application (SPA) loads one document and swaps views in place — instant transitions, shared state, no full reloads. The router is the piece that keeps the URL honest while doing so: it maps URL → view, updates the address bar via the History API without a page load, and re-renders the matching UI. The URL is a contract with your users: shareable, bookmarkable, back-button-correct. Routing in React is not core — Ecosystem — and the dominant library is React Router (v7 at the time of writing; v7’s react-router package consolidates what v6 split across react-router-dom — imports below use the unified package, which also re-exports the old names for compatibility).

Two folder structures, dependency direction, state ownership — and the discipline to stop at “enough”

What frontend architecture actually decides

Architecture is the set of decisions that are expensive to change later: where code lives, which direction it may depend, who owns state, and how failures are contained. Everything else is formatting. The goal is not a beautiful tree diagram — it is that any engineer can predict where a new piece of code goes, and that changing one feature does not require reading five others.

      status: res.status,
      payload: await safeJson(res),

Error handling architecture

Avoiding over-engineering

Every structure in this module has a cost line: feature folders cost navigation overhead for small apps; enforced boundaries cost setup discipline; design systems cost governance. The professional posture is to grow structure with measured pain: flat until features collide, feature folders until cross-imports hurt, boundary linting until the violations appear, a shared package until a second app consumes it. Ask of each layer: what bug or slowdown does this prevent that we have actually experienced? Architecture that cannot answer is decoration. The reverse failure is worse: teams five years into a 4,000-component flat folder who cannot onboard anyone — structure arrived too late. Both failure modes are real; steer between them deliberately.

Migrating JavaScript React to TypeScript — a proven path

  1. Enable incrementally: allowJs: true in tsconfig.json; JS and TS coexist. Rename files .tsx one at a time — the build stays green throughout.
  2. Start at the leaves: shared components and API modules first (highest reuse of each type); pages last (they are thin composition).
  3. Type the boundaries first: props of shared components, API response shapes, context values — these types then flow inward by inference.
  4. Ban any from new code (lint rule) while tolerating @ts-expect-error on old code with ticket numbers — debt made visible, not hidden.
  5. Strict on day one: strict: true, noUncheckedIndexedAccess when ready. Retrofitting strictness later costs a full pass; enabling early costs nothing.

Philosophy: the user is the interface

A React component’s contract is what users see and do — text, roles, clicks, keyboard input — not its internal state or method names. Tests that query by role and label survive refactors; tests that query by implementation (instance.state, CSS classes, DOM structure details) break on every harmless change and train the team to ignore red builds. The Testing Library ecosystem encodes this: query the way a user (or a screen reader) would, assert on what is observable.

Accessibility, Security & Production Quality

The work that separates a demo from a product

Semantic HTML is 80% of accessibility

Assistive technology derives meaning from element semantics. A <button> announces itself as a button, is focusable, and answers Enter/Space — a <div onClick> announces nothing. The cheapest a11y work is choosing the right elements first and reaching for ARIA second:

// ✘ Div soup — invisible to assistive tech, unusable by keyboard
<div className="btn" onClick={save}>Save</div>

// ✓ Native semantics: role, focus, keyboard, all free
<button type="button" onClick={save}>Save</button>

// Headings reflect document structure (screen readers navigate by them):
<h1>Product catalog</h1>          // one per page
  <h2>Wireless mouse</h2>         // nesting follows meaning, not font size
    <h3>Specifications</h3>

// Landmarks come from the right elements:
<header><nav aria-label="Primary">…</nav></header>
<main>…</main>
<footer>…</footer>

Images: every <img> needs alt — descriptive for meaningful images, alt="" for decorative ones (never omit the attribute). Icons-only buttons need aria-label.

Keyboard navigation & focus discipline

  • Everything must be reachable by Tab and operable by keyboard — test every screen you build with the keyboard alone (the Module 17 patterns bake this in).
  • Focus order follows DOM order — visual order that differs from DOM order (CSS reordering, portals) creates keyboard mazes.
  • Focus must be visible: restyle :focus-visible to your theme, never remove outlines without a replacement.
  • Manage focus at the boundaries: into dialogs on open, back to triggers on close, skip links for long navs (Module 17).

ARIA fundamentals — the rules that keep it honest

The first rule of ARIA: don’t use ARIA if a native element exists. When you do use it: role declares what something is; aria-label/aria-labelledby name it; aria-expanded/aria-current/aria-selected expose state; aria-live announces async changes; aria-hidden hides decoration from screen readers. Roles impose behavior contracts — a role="menu" that lacks arrow-key navigation is a lie the screen reader will repeat to a stuck user. Verify with a real screen reader (VoiceOver on macOS/iOS, NVDA on Windows) on real flows, plus axe DevTools for mechanical violations.

Accessible forms

  • Every control has a label — <label htmlFor> wired with useId (Module 16); placeholders are hints, never labels.
  • Errors are announced (role="alert" or aria-live), associated via aria-describedby, and aria-invalid marks the offending field.
  • Group related controls (<fieldset><legend> for radio groups); keep instructions visible, not hover-only.

Color and motion

  • Contrast: body text ≤ 4.5:1, large text ≤ 3:1 against its background; never encode meaning in color alone (add icons/text to error and success states).
  • Respect prefers-reduced-motion: animations that communicate can stay; large decorative motion should stop (this guide’s own CSS practices what it preaches).

XSS fundamentals and safe rendering

Cross-site scripting is injecting executable markup into a page. React’s default posture removes the main vector: JSX escapes all rendered values — {userBio} containing <script> renders as inert text. The residual risks are the deliberate holes:

// 1. dangerouslySetInnerHTML — exactly as dangerous as it sounds

// Only with sanitized input: DOMPurify.sanitize(renderedMarkdown)

// 2. href with user data — javascript: URLs still work in browsers
<a href={userWebsite}>Website</a>                  // ✘ javascript:alert(1)
<a href={safeUrl(userWebsite)}>Website</a>        // ✓ allow only http(s)/mailto

// 3. Third-party scripts / eval-adjacent APIs: a CSP header is the fence
// Content-Security-Policy: script-src 'self' — ask your backend to set it

URL and input handling: validate shapes before use (typing helps — Module 21), encodeURIComponent anything interpolated into query strings, and treat every value that crossed the network as untrusted until validated at the boundary.

Authentication UI — and where its authority ends

Frontend auth is presentation: sign-in forms, session restoration, protected-route UX, token storage mechanics. The actual authority is the server: every API endpoint must verify identity and permissions on every request. Hiding an admin route is UX; the admin endpoint is the security boundary. Never ship real secrets in bundles (Module 02’s env rules), prefer HttpOnly cookies over localStorage tokens where the architecture allows, and design sign-out to clear both state and caches.

Modern React Ecosystem & Advanced Concepts

Concurrent rendering, Suspense, Actions, Server Components — each with what it solves, what it does not, and what it requires

React 18 and React 19 — the conceptual shift

React 18 (2022) introduced the concurrent renderer as the default: renders became interruptible, updates gained priorities, and createRoot replaced the legacy ReactDOM.render. React 19 (December 2024, the baseline of this guide, with continued 19.x releases through 2026) built on it: Actions (form submissions and async transitions as first-class concepts), new hooks (useActionState, useOptimistic, use), ref as a plain prop, resource preloading APIs, and full support for Server Components across frameworks. The mental model shift from 17-era React: rendering is scheduled and interruptible work, not a synchronous function call — and the ecosystem (React Compiler, Module 14) increasingly enforces the rules that make that safe.

Concurrent rendering

Concurrent rendering lets React pause, abandon and restart render work: an expensive background re-render (filtering 10,000 rows) can be interrupted by a keystroke, which renders first. It is opt-in per update — updates are urgent by default; you mark the non-urgent ones. What it solves: responsiveness under heavy render load. What it does not: make renders free (the work still happens), help with non-render bottlenecks, or excuse impure render logic — it requires purity, since abandoned renders may re-run. Requires: React 18+, createRoot.

Server Components — the boundary, precisely

Server Components (RSC) are components that execute on the server: they ship zero component JavaScript to the browser, can read databases and secrets directly, and render to a serializable format the client tree consumes. Client Components (annotated "use client") are everything this guide has taught — they run in the browser with state and effects.

Boundary map with allowed data flows: Visual Model 15.

!What RSC requires — no free lunch
Server Components are not available in a plain client-only React setup: they require a framework or bundler integration that compiles the two environments and streams the payload (Next.js and Remix ship this today; React 19’s RSC support is core, the tooling is not). Constraints that follow from the model: no useState/useEffect in server components, no event handlers, props crossing the boundary must be serializable, and context works only within one environment. Choose them when a framework is already your stack and data-heavy static regions would otherwise ship heavy client fetching code; skip them entirely for SPAs — nothing in this guide’s Modules 1–23 needs them.

SSR, hydration and streaming — the vocabulary

  • Server-side rendering (SSR): render components to HTML on the server → users see content before any JS loads (fast first paint, crawlability).
  • Hydration: the browser loads JS and React attaches to the server HTML, adopting it instead of re-rendering. Hydration mismatch bugs (server HTML ≠ client render — usually from Date.now(), Math.random(), or browser-only APIs during render) must be fixed by moving the nondeterminism to effects; React surfaces them explicitly.
  • Streaming SSR: the server flushes HTML progressively; Suspense boundaries let slow regions stream in later without holding the page hostage — React 18’s model made this the default mental model for server rendering.

Framework integration — when to adopt one

You have…Consider
A widget, dashboard, or internal tool with client-side dataPlain React + Vite (this guide’s stack) — a framework adds nothing you need
Content + marketing + app regions, SEO mattersA meta-framework (Next.js/Remix): routing, SSR/SSG, RSC, streaming
Deep product with heavy shared state and realtime UISPA remains excellent; add a query library and split routes
Existing CRA-era codebaseMigrate to Vite first (a day of work), consider frameworks later

The decision is about where data fetching and routing live — not about React itself, which is identical on both sides of the boundary. And the React Compiler (Module 14) applies to both worlds: it is build tooling that removes hand-memoization wherever you render.

Debugging, Maintenance & Professional Engineering

The bug catalog, the tooling workflow, upgrades, and what to do at 3 a.m.

The DevTools workflow

  • Components tab: live tree with props, state, hooks and context per node; edit values live; “Highlight updates” flashes re-renders; click a node then $r in the console to poke at it. The first stop for “what does this component actually have?”
  • Profiler tab: record the failing interaction → flame chart of what rendered, why (state/parent/context/hook change), and for how long. React 19’s DevTools surface the “why” reasons directly. The first stop for “why is it slow?”
  • Sources + breakpoints: set breakpoints in .jsx; inspect the render snapshot where it lives. console.count("ComponentName") answers “how often is this really rendering?”

Production incident debugging

  1. Triage scope: which routes/components? From monitoring (error grouping + component stacks) or user repro — source maps uploaded at deploy time make component stacks readable.
  2. Reproduce in staging with the same build; production-only bugs are usually env vars, timing (races), or data shape.
  3. Contain: an error boundary around the affected region keeps the rest of the app alive; a feature flag can disable the offending surface.
  4. Fix forward or roll back: reverted deploys are boring and boring is good; the failing test ships with the forward fix.
  5. Blameless postmortem: which missing test/monitoring/budget let it through — the fix is the guard, not just the patch.

Dependency upgrades and version migrations

  • Continuously, in small steps: Dependabot/Renovate PRs weekly beat annual upgrade catastrophes. Patch/minor on autopilot with green CI; majors read the changelog.
  • React major upgrades: run the codemods Meta ships (e.g., the 19 codemod suite for forwardRef removal, useActionState adoption); upgrade react and react-dom together; watch the console for deprecations — they are the migration checklist.
  • Ecosystem majors (Router, TanStack Query): their upgrade guides are honest about breaking changes; budget a day, upgrade, run the E2E suite.
  • Lockfile hygiene: never upgrade and refactor in the same PR — bisectability is worth more than efficiency theater.

Code review standards for React

  • Correctness first: rules of hooks, effect deps honest, races guarded, keys stable, updates immutable.
  • Boundary discipline: does this PR put product knowledge into shared code? feature-to-feature imports? (Module 20)
  • State design: is any new state actually derived? is ownership at the right level? is server state sneaking into useState?
  • Accessibility: labeled controls, keyboard operation, semantic elements — reviewed like any other correctness.
  • Tests as evidence: does the PR’s test fail without the change? A test that cannot fail is a comment.
  • Review the diff, not the person; ask questions, not verdicts (“what happens when query changes mid-flight?”).

The full review craft — comment tone, escalation, review of reviews — has its own guide: Code Review Mastery.

Component documentation

  • Props tables generated from types (TypeScript + doc comments); examples rendered live (Storybook or a tiny in-repo playground).
  • Document behavior contracts, not implementations: what it renders for each state, what events it emits, what it does on unmount. The how is the code’s job.
  • Custom hooks need docstrings with timing semantics and cleanup behavior (Module 15).
  • ADRs for the decisions — “why context here, why not a store” — so the next engineer inherits reasoning, not folklore. Writing discipline lives in Software Documentation.

Maintainability — the long game

  • Complexity budget per component: above ~150 lines or three responsibilities, extract (Module 04; practiced in Workshop 4).
  • Delete aggressively: dead code, speculative props, unused features — git remembers, your codebase should not.
  • Refactor on touch: the file you are already changing gets left cleaner (the refactoring discipline has its own guide: Refactoring Catalog).
  • Onboarding is the maintainability test: if a new engineer cannot ship a small change in day one, the architecture — not the engineer — is the defect.

Capstone — production-style React dashboard

The capstone is a complete dashboard application that exercises every part of the guide. It is deliberately specific: “a dashboard” teaches nothing; “this dashboard, with these requirements” teaches engineering.

Specification

  • Layout & navigation: persistent sidebar + header; nested routes: Overview, Products (list + detail), Orders, Settings (protected), Admin (lazy); URL-owned filters/search/pagination.
  • Design system: shared Button/Card/Field/Modal/Tabs/Toast; theme context (dark default) persisted; every component accessible and documented.
  • State architecture: server state via a query layer (TanStack Query or your tested useFetch + cache map); client workflows (bulk edit, filters draft) via reducers; auth context with session restore; explicit state-ownership ADR.
  • Async UI: every data view implements loading (skeletons), empty, error (retry), success; searches debounced and race-guarded; optimistic quantity updates with rollback.
  • Forms: product create/edit form with derived validation, touched tracking, dynamic attribute fields, pending state, accessible errors.
  • Quality: typed throughout (Module 21 patterns); reducer + validation unit tests, two component tests with mocked network, one Playwright checkout journey; axe-clean on core flows; performance budget verified on the production build (report numbers).

Architecture decisions you will defend

  1. Where does the filter state live? (URL — shareable, refresh-proof; defend against “it is just UI state”)
  2. Why reducer for bulk edit and useState for filter drafts? (multi-event transitions vs single value; Module 11’s table)
  3. Why split state and dispatch contexts? (dispatch-only buttons never re-render; measure it)
  4. Why a query layer instead of useEffect fetching? (cache, dedupe, invalidation — name the exact bugs it removes)
  5. Where are error boundaries, and why there? (per route + per panel; recovery granularity)

Write each decision as a short ADR: context, options, decision, consequences — the capstone’s documentation is half its value. Trade-offs to surface honestly: what you would change with a second backend consumer, where the design system needs a second app to validate abstractions, which tests would break first under a design change and why that is acceptable.

When all boxes tick, you have not just “learned React” — you have built, debugged, tested, documented and defended a React application the way professional teams do.
