01

What Refactoring Is

Behavior-preserving transformations — and everything refactoring is not

The definition

Martin Fowler’s definition, from Refactoring: Improving the Design of Existing Code: refactoring is the process of changing a software system in ways that do not alter its external behavior, yet improve its internal structure. The key word is behavior-preserving. Every individual refactoring is a small, structured transformation — rename a method, extract a function, move a field — that you can apply and verify in minutes. Large restructurings are sequences of these small steps, with the code kept working between them.

iTwo tests for “is this refactoring?”
(1) The change does not alter the software’s externally observable behavior. (2) The change improves internal structure — readability, cohesion, coupling, testability — not just formatting or style. If it changes behavior, it is a feature change or a bug fix. If it only reshuffles lines or reformats, it is cleanup. Both are legitimate work — they are just not refactoring, and mixing them in one commit destroys the safety review.

Internal structure vs external behavior

“Externally observable behavior” means what callers, users and downstream systems can perceive: returned values, thrown exceptions, emitted events, database rows written, HTTP status codes, log output that something depends on, timing contracts that are documented. “Internal structure” means everything else: names, method boundaries, class responsibilities, private helpers, internal data representation, design patterns used. Refactoring changes the second category while holding the first constant.

DimensionUnchanged during refactoringFree to change
InterfacePublic method signatures, endpoint contracts, event schemasPrivate helper signatures, internal parameter passing
BehaviorOutputs for given inputs, exception types, side-effect order where observableThe order of invisible internal computations
DataStored schema, row contents, message payloadsIn-memory representation, intermediate structures
Design—Class boundaries, responsibilities, patterns, module layout

Be honest about gray zones: performance is partially observable. A refactor that makes a hot path 40 times slower has effectively changed behavior for timeout-sensitive callers, even if outputs are identical. Performance-sensitive code needs performance tests in the safety net (see Module 03).

The boundaries blur in practice: fixing an N+1 query is optimization that often is done as refactoring (Introduce Repository, batch fetch). A rewrite may be executed as hundreds of refactorings plus one cutover. What matters is that you know which activity you are performing, because it determines your safety net, your commit strategy and your review criteria. Never mix refactoring and behavior change in one commit — the diff becomes unreviewable and a regression becomes unfindable.

Small steps, always working

A refactoring session is not “rewrite this class nicely over three days.” It is: extract one method → run tests → rename one variable → run tests → move one field → run tests → commit. Each step is small enough to review at a glance and cheap to revert. The code compiles and passes its tests after every step. This is what makes refactoring safe in production software, and it is the single habit that separates engineers who refactor confidently from engineers who “clean up” and break things.

small transformation→ run tests→ inspect→ commit or revert→ repeat

Three honest caveats

1. Tests do not prove behavior preservation

Tests check the cases they check. Refactoring can silently change behavior in untested corners — a rare null path, a logging side effect someone parses, exception types, iteration order. Strong test suites make refactoring reasonably safe, not provably identical. That is why small steps matter: each step is easy to reason about even where tests are silent, and a failure surfaces within minutes of its cause, not weeks.

2. Shorter is not the goal

Refactoring often reduces line count (deduplication, dead code removal), but plenty of excellent refactorings add lines — extracting a method adds a signature, introducing a value object adds a class, guard clauses add early returns. Judge structure by how hard it is to understand and to change, not by size. Code golf is not refactoring.

3. Abstraction is a cost, not a virtue

Every abstraction adds indirection that a future reader must traverse. Extracting an interface for a single implementation, creating a “generic handler framework” for three similar cases, or adding configuration for variation nobody needs makes the code worse while looking more sophisticated. The rule of thumb: abstract after the second or third concrete duplication proves the pattern, not before — and prefer deleting a wrong abstraction early (see Speculative Generality).

Why It Matters

Maintainability economics, technical debt, coupling and cohesion — and when code should be left alone

Software rots because change is constant

Code that is never changed never needs refactoring. Real systems change constantly — new regulations, new pricing rules, new integrations — and each change is applied under time pressure, often by someone who understands only part of the design. Structure erodes: a method grows twenty lines per feature, a class accumulates a fifth responsibility, the same validation gets copied “just this once.” Nobody decides to build a mess; the mess emerges from locally reasonable decisions. Refactoring is the counter-force: continuous, small investment in keeping the structure aligned with what the code now does.

What good structure buys you

QualityDefinitionWhat refactoring buys
ReadabilityHow fast a competent newcomer understands the codeNames that say what, methods small enough to hold in your head, logic that reads like the domain
MaintainabilityCost of a typical changeChanges touch one place instead of five; regressions become local, not systemic
ExtensibilityCost of the next category of changeNew payment method = new class, not new branch in a 12-arm conditional
TestabilityEase of writing precise, fast testsDependencies injected and logic separated from I/O; unit tests without a database
ModularityClear boundaries with narrow interfacesParts can be understood, tested and replaced independently
Lower couplingHow much one part must know about anotherChanges stop propagating across the codebase (fewer “shotgun surgery” days)
Higher cohesionHow well a unit’s parts belong togetherRelated logic lives together; classes have one reason to change
Lower complexityCyclomatic complexity, nesting depth, state spaceFewer defects per change — complexity is where bugs hide

Technical debt, stated precisely

Technical debt is the difference between the cost of changing the system as it is and the cost of changing it as it should be structured. Like financial debt it can be rational — shipping a tactically ugly implementation to hit a deadline, with intent and a plan to repay — or reckless: no design, no tests, no repayment. Interest compounds: every feature built on tangled structure takes longer and breaks more, and the moment you need an architect-month to “pay the debt down,” the business has usually learned to live without the feature. This is why refactoring works best as part of everyday development — the boy scout rule (leave the code cleaner than you found it) applied within the blast radius of your current ticket — rather than as a separate “hardening sprint” that must compete with features for priority.

!Interest you cannot see
The most expensive debt is invisible on any dashboard: engineers who quietly route work around a scary module, estimates that double “because that part is tricky,” onboarding that takes months. By the time the debt shows in velocity, it has been costly for a long time. Use the prioritization matrix to make the invisible explicit.

Coupling and cohesion: the two dials

Nearly every refactoring moves one of two dials. Cohesion up: things that change together, live together (Extract Class, Combine Functions into Class, Move Function). Coupling down: modules stop reaching into each other (Introduce Interface, Encapsulate Collection, Hide Delegate, Dependency Injection). When you cannot decide whether a design is good, ask: if this business rule changed, how many files would I touch, and how much would I need to know about code far away from the change? Few files, little knowledge → good structure.

Refactoring as everyday engineering

  • Preparatory refactoring — make the upcoming feature easy, then build it. Adding a gold tier? First extract the pricing rules so the new tier is one more rule, not another nested branch.
  • Comprehension refactoring — you just spent an hour understanding a gnarly method; capture that understanding in names and structure so the next reader gets it in five minutes.
  • Litter-pickup refactoring — small violations you pass (a dead method, a duplicated constant) fixed on the spot, kept inside your change’s blast radius.
  • Planned refactoring — for debt too large for ticket-sized work: scheduled, tested, and justified with evidence (defect clusters, change-frequency data), not aesthetics.

What this looks like in practice: your team’s definition of done includes “the code is reasonably clean for what it now does,” refactoring commits are separately reviewable, and nobody asks permission to extract a method — but everybody reviews a proposal to split a core service.

When code should be left alone

Refactoring has costs and risks; it is not a moral duty. Leave code alone when:

  • It is stable and rarely touched — a formatter last modified in 2019 with zero open bugs is not a refactor target, however ugly.
  • It is near end of life — the module is scheduled for replacement; investment there is waste.
  • The blast radius exceeds the benefit — a shared library consumed by 40 teams cannot be casually restructured.
  • You cannot test it and cannot add tests economically — without a safety net, restructuring is gambling (see Legacy Code Rescue for what to do instead).
  • The code merely differs from your style — unfamiliar or stylistically different is not broken. Idiomatic variation is not a smell.
✗The overengineering trap
The mirror-image failure of never refactoring is refactoring everything into speculative frameworks. Both waste engineering time; the second one also adds indirection that future maintainers must fight through. Every abstraction must pay rent with a concrete second use that exists today, and the decision tools in the Decision Guide exist to keep you honest about that.

The Safe Refactoring Workflow

Ten disciplined steps — the difference between refactoring and hoping

Refactoring is safe exactly to the degree that it is boring. The workflow below looks bureaucratic for one-line changes — skip steps consciously for those — but for anything a reviewer would notice, it is what keeps behavior preserved and regressions findable. Tests red at any point → you just found either a refactor bug (fix it now) or a missing test (add it, then continue). Either outcome improves the system.

  1. Understand the existing behavior. Read the code and its callers before touching anything. What inputs can arrive, what is returned, what is thrown, what side effects occur (DB writes, events, logs someone parses)? For public code, check how other teams actually use it — usage, not Javadoc, is the real contract.
  2. Identify the code smell or structural problem. Name it — “Long Method,” “Feature Envy,” “Divergent Change” — using the smell catalog. A named smell points to a family of proven treatments instead of a creative redesign.
  3. Establish a safety net with tests. If tests exist, run them and check they cover the behavior you are about to move. If not, write characterization tests that pin down current behavior — including its bugs — before changing anything (see Module 04 and Legacy Code Rescue).
  4. Choose one small refactoring. Not “clean up this class” but “Extract Method for the pricing block.” If the smell needs several techniques, sequence them and do them one at a time.
  5. Apply one transformation at a time. Prefer IDE-assisted operations (Rename, Extract, Move) over hand-editing — the tool rewrites every reference mechanically. Keep the code compiling at each step.
  6. Run relevant tests immediately. The full suite if it is fast; the affected slice plus integration tests if not. The point of small steps is that a red test points at a change made minutes ago.
  7. Inspect the resulting code. Does the new structure actually communicate better? Did the mechanical extraction leave a six-parameter helper that now needs Introduce Parameter Object? Plan the follow-up instead of bolting it on half-done.
  8. Review behavior and edge cases. Walk the edge cases you listed in step 1 through the new code by hand: nulls, empty collections, boundary amounts, exception paths. Tests are silent where they do not look.
  9. Commit small and understandable. One logical transformation per commit, message says what and why: “Extract pricing rules from OrderService (Long Method)”. Never mix refactoring with feature or fix changes.
  10. Repeat. Refactoring is a loop, not an event. Either continue to the next transformation in your sequence, or stop cleanly — the system works after every commit.

Local, broad, and “refactorings” that are not refactorings

Not all transformations carry the same risk. Classify before you choose your process:

ClassExamplesWhy it is (or is not) safeRequired process
Local & mechanically verifiableRename, Extract Variable, Inline Function, Replace Magic NumberCompiler + IDE verify all references; blast radius is one file or one call graphStandard loop; IDE tools; fast tests
Broad but still behavior-preservingExtract Class, Move Method across modules, Replace Conditional with Strategy, Introduce InterfaceBehavior can be preserved, but the change spans collaborators and tests may encode structure, not behaviorFull safety net; sequence of local steps; reviewer double-checks observable contracts
Migrations — cannot be treated as refactoringRenaming a DB column, changing an event schema, altering a public API, moving logic to another serviceExternal systems hold copies of the old shape; “identical behavior” is not locally verifiable — old and new versions coexist during rolloutExpand-and-contract with compatibility versions, dual reads/writes, staged rollout, rollback plan (Systems module)

Version control discipline

  • Small commits are your rollback strategy: git revert of one transformation is trivial; reverting a 2,000-line “cleanup” branch is archaeology.
  • Refactoring PRs should show structure change only. Reviewers can then verify behavior preservation with a diff-level eye and are far more likely to catch a subtle slip.
  • Feature flags are for behavior changes, not structure changes — but they earn their place when a structural change alters timing (connection pooling, batching) and you want a fast kill switch in production.
  • Bisect-friendly history — because every commit keeps tests green, a future regression bisects cleanly to the exact transformation that caused it.
✓The habit in one sentence
If you cannot describe your refactoring as “I applied technique X to smell Y, tests were green before and after, and the commit shows only that” — stop and re-plan; you are probably doing a rewrite wearing a refactoring costume.

Safety Nets: Testing and Tooling

What each net catches, what it misses, and how to combine them

A safety net is anything that turns a silent behavior change into a loud, immediate signal. No single net catches everything; the craft is knowing what each one misses.

The net inventory

Coverage: useful, misunderstood

Coverage tells you what executed during tests, not what was asserted. A suite can execute 100% of lines and assert almost nothing. Use coverage as a map of untested territory — before refactoring a method, look at whether tests reach its branches — never as a proof of safety or a target to game. The refactoring-relevant question is narrower: do tests exercise and assert the observable behavior of the code I am about to move?

Choosing the net for the job

  • Extract Method / Rename in one class → existing unit tests + compiler + IDE is usually enough.
  • Extract Class / Move Method → add integration tests around the collaborators first; unit tests alone will not catch wiring loss (e.g. a Spring bean no longer registered).
  • Replace Conditional with Strategy/State → table-driven tests: every branch of the old conditional becomes a case; then refactor; then the same cases must pass unchanged.
  • Spring service restructuring → @SpringBootTest slice covering the endpoint behavior (request in, response out, side effects asserted).
  • Shared API / event schema → contract tests owned by consumers, run against the provider before and after.
  • Performance-sensitive path → add a benchmark or latency assertion to the net before “harmless” restructuring changes batching or caching behavior.

A

Composing Methods

Taking apart methods that are too long or too dense — the highest-traffic refactorings in the catalog

⚙
Most of the code humans find unreadable is a method doing too many jobs. This category decomposes methods: extract the parts that deserve a name, inline the indirections that hide nothing, and flatten conditionals so the main flow reads like a summary. These techniques affect readability, method length, variable scope and single responsibility — and almost never change behavior beyond what names can express. Worked example: J1 — decomposing a 40-line order processor.
▸
B

Organizing Data

Turning loose primitives and records into structures that protect their own meaning

☰
A String that is an email, a BigDecimal that is money, a Map<String,Object> that is a customer — unstructured data forces every reader to re-derive the rules. This category gives data a home: value objects for money, dates and identifiers; encapsulation so invariants live with the fields they govern; parameter objects for arguments that travel in herds. Themes to watch: immutability, defensive copying, equality, and collection encapsulation. Worked example: J6 — Money and EmailAddress value objects.
▸
C

Organizing Objects and Classes

Responsibility boundaries, coupling, cohesion and how objects collaborate

▦
Classes earn their keep by owning one responsibility and exposing a narrow interface. This category reshapes the object graph: split classes that accumulate reasons to change, move behavior to the object that owns the data it uses, re-parent fields and methods through hierarchies, and replace both inheritance with delegation and delegation with inheritance when the trade-off flips. Worked example: J3 — splitting an order God Class and J10 — composition over inheritance.
▸
D

Simplifying Conditional Logic

Guard clauses, polymorphism, Strategy, State — and knowing when an if is just fine

∧
Conditionals are where behavior concentrates — and where refactoring must be most careful, because a mis-copied branch changes outputs. The ladder: guard clauses for special cases, decomposition for dense conditions, polymorphism / Strategy / State when the same type-switch appears everywhere. Understand the differences: polymorphism moves type-specific behavior into subclasses; Strategy injects a varying algorithm that callers choose; State lets an object change behavior as its lifecycle status changes. Do not force a pattern where a simple conditional is clearer. Worked examples: J2, J4, J17; practice in the Guard Clause Workshop and Strategy Lab.
▸
E

Simplifying Method Calls

Signatures that are easy to understand and hard to misuse

ƒ
The signature is a method’s user interface. Bad signatures leak internals (flag arguments), invite transposition errors (adjacent same-typed parameters like (BigDecimal, BigDecimal)), and force every caller through ceremony. This category makes calls self-explanatory: rename to intention, group parameters that travel together, replace boolean flags with explicit methods or options, and separate questions from commands so callers know what side effects to expect.
▸
F

Dealing with Generalization

Pulling up, pushing down, and dismantling hierarchies that stopped earning their depth

↯
Inheritance generalizes — sometimes usefully, sometimes speculatively. This category maintains the resulting hierarchies: pull up what subclasses share, push down what only one needs, and collapse the hierarchy when variation moved elsewhere. The dangers are real: premature inheritance built for an imagined future, the fragile base class problem (superclass changes ripple invisibly into subclasses), and deep taxonomies that must be understood end-to-end to change anything. Delegation-based alternatives (Category C) usually age better.
▸
G

API and Integration Refactoring

Boundaries to the outside world — where internal refactoring rules change

⇆
A private method renamed is a mechanical change; a public API renamed is a negotiation. This category refactors the seams: facades and gateways that wrap external systems, adapters that translate shapes, anti-corruption layers that keep someone else’s model out of yours, and DTOs that decouple wire formats from domain models. Internal structure improves freely; public contracts evolve — add, deprecate, migrate, then remove — and every step must respect consumers you cannot see (see Systems module for versioning and compatibility strategy).
▸
H

Database and Persistence Refactoring

Schema and query changes under live data — migrations, not refactorings

▦
Code refactoring is verified by tests in seconds; data refactoring is verified by months of compatible operation. Because deployed schema is shared state, most changes here are migrations executed as expand-and-contract: introduce the new shape alongside the old, deploy code that writes both or reads the new, backfill, switch reads, and only then drop the old. Application-side techniques (repository abstraction, persistence/domain separation, N+1 elimination) are true refactorings; schema techniques are staged operations — the entries say so explicitly. Worked example: J18 — safe column rename with Flyway.
▸
I

Architectural Refactoring

Modules, layers, boundaries — the biggest safe steps, and the ones that stop being refactorings

☉
Above classes sits architecture: modules, layers and dependency direction. This category makes large-scale structure malleable — introduce a domain layer under the business logic, ports and adapters around it, break dependency cycles between modules — always as sequences of code-level refactorings, each individually safe. Know the boundary: reorganizing code inside a deployable is architecture refactoring; extracting a separately deployed service is a migration with operational consequences (data ownership, network failure, independent deploys) that no local test can verify. Worked example: J15 — breaking a Spring circular dependency.

Refactoring Decision Guide

Decision tree, refactor-vs-leave-alone rules, prioritization matrix and sequence planning

The questions to ask, in order

  1. Is this code worth refactoring at all? — the tree below is the gatekeeper.
  2. What is the actual problem? Name the smell; do not accept “it’s ugly.”
  3. Which technique fits? Shortlist from the smell lookup; read the entries’ “when not to.”
  4. Is the change local or architectural? This decides review depth and safety net size.
  5. What is the safest transformation sequence? Big moves decompose into small ones — plan them (planner below).
  6. Do tests exist? Can characterization tests be written? If both answers are no, you are not refactoring yet — you are building a net.
  7. Could this change affect public behavior? API, schema, events, timing, logs — if yes, switch to migration thinking (Systems).
  8. Is the code frequently modified? Change frequency is the strongest predictor of refactor ROI.
  9. Is the refactoring worth its cost? Hours now vs recurring friction — use the prioritizer below, then apply judgment.
  10. Now or later? Preparatory (before the feature), opportunistic (inside your current PR), or scheduled (too big for a ticket). Pick one deliberately.

Decision tree

Refactor vs Leave Alone

Code does not need refactoring simply because it is unfamiliar, stylistically different, or not how you would have written it. Reading code you did not write is a skill; imposing your preferences on working software is not refactoring — it is churn with a Git history cost. The honest Leave Alone signals:

SignalWhy it argues for leaving alone
Low change frequency, low defect frequencyROI is roughly zero; risk is nonzero — bad trade
Comprehensible to the team that owns itReadability is audience-relative; the audience is fine
Isolated blast radiusUgly but quarantined code cannot spread rot
No safety net and high criticalityChange without a net is gambling with other people’s uptime
End of life approachingEvery hour there is an hour not spent on the replacement

And the honest Refactor signals: the same module appears in every recent incident retro; estimates for changes there are habitually inflated; new engineers take weeks to become productive in it; you are about to build a feature on top of it (preparatory refactoring has the best ROI of all — the cost is immediately amortized).

What drives the decision: the six factors

  • Change frequency — hot code multiplies every structural improvement; cold code wastes it.
  • Defect frequency — bugs cluster in complexity; where defects cluster, structure is failing.
  • Complexity — nesting, state space, implicit couplings; the cost of the NEXT change.
  • Business criticality — amplifies both benefit (downtime cost) and risk (blast radius). Critical code needs stronger nets, not slower decay.
  • Maintenance cost — onboarding, fear-driven workarounds, review friction; mostly invisible, mostly real.
  • Refactoring risk — test coverage, seam availability, contract surface. High risk + weak net = build the net first.

Legacy Code Rescue

Feathers’ discipline: gain control of untested code before you change it

Michael Feathers’ definition made the problem precise: legacy code is code without tests — untested code is unsafe to change, so it calcifies no matter its age or language. The rescue discipline is therefore not “rewrite it” but: find a seam, pin the behavior, then refactor behind the net. A seam is a place where you can alter program behavior without editing the code itself — an injectable dependency, an overridable method, a clock, a wrapped static call, a test double at an interface.

The rescue playbook

  1. Understand before touching. Trace the entry points (scheduler, endpoint, queue consumer). List inputs, outputs, side effects and the timing/nondeterminism (system clock, randomness, external services, ordering). Read git history — recent hotfixes show where behavior is fragile.
  2. Choose a characterization strategy. Unit-level seams where dependencies are injectable; golden-master for gnarly pure computation (pricing, formatting, serialization); integration-level capture (record real request/response pairs) where the system is a black box.
  3. Break the dependencies to create seams. Extract Interface on the collaborator, wrap the static call, inject the clock — these preparatory moves are themselves refactorings, so keep them small and separate.
  4. Pin behavior — including the bugs. Characterization tests assert what the code DOES do. The off-by-one rounding you spotted gets pinned as-is; fixing it is a later, separately reviewed change.
  5. Isolate nondeterminism. FixedClock, seeded Random, in-memory fakes for the SMTP client, deterministic ordering for assertions. Freeze or filter timestamps in golden masters.
  6. Refactor behind the net with the Module 03 loop — now an ordinary, safe activity.
  7. Stop at a clean boundary. The goal is never “rewrite the entire system”; it is “the part I need to change is now covered and comprehensible.” Coverage grows outward from value, one rescue at a time.

Worked example: pinning a legacy service

A 2014-era royalty service runs nightly, has zero tests, and your team must add a new contract type next sprint. Before changing anything, you build the net:

● BEFORE — untestable by construction
● AFTER — seams created, behavior pinned

Behavior equivalence: the nightly run performs the same loads, arithmetic and emails for the same artists; the only changes are who provides time and mail (injected, real implementations wired in production configuration) — invisible to the job’s observable output. The 180 arithmetic lines moved verbatim into royaltiesFor; the golden-master cases came from running the old code on production-shaped data and capturing outputs. Trade-offs: a seam-extraction PR touches production wiring (review the configuration twice); characterization tests will faithfully assert bugs — label them, and fix each deliberately later. Tests added: tier pinning, zero-amount side effect, boundary dates around month rollover (clock seam makes those writable).

Database-coupled logicIntegration test on a throwaway schema (Testcontainers-style), repository seamSQL and mapping are the behavior; mocks would test nothing
External services (SMTP, payment)Interface seam + stub recording callsAssert side effects (that the email was attempted) without sending email
Message consumersContract test on the topic/queue schemaThe contract with publishers is the risk, not your internal handling
Nondeterministic logicProperty-based invariants, seeded randomness, frozen clockDeterministic assertions remain possible once volatility is isolated

Transformation 1 — fat controller to layered application service

● BEFORE — the controller is the application
● AFTER — each layer does its own job

Behavior preserved: same endpoint, same validation outcomes (400 for missing sku / non-positive qty, 404 unknown sku now surfaced as a mapped domain exception producing the same status), same persistence, payment call and email-equivalent event, same response body shape. Why better: the use case is callable from a scheduler or message listener without HTTP; validation is declarative and testable; the discount rule moved next to the total it modifies (rich domain method Order.place); constructor injection makes the service unit-testable without Spring. Cost: more files and one mapping layer — the honest price of a testable boundary.

Transformation 2 — anemic entity to rich domain model

● BEFORE — state without judgment
● AFTER — the entity defends its own rules

Behavior preserved: identical state transitions and totals for identical inputs; illegal transitions still throw the same exception type. Why better: an invalid CANCELLED → SHIPPED hop is now unrepresentable; every future service touches order rules through the entity instead of re-implementing them. Caution: keep persistence concerns (lazy relations, cascade) out of the domain methods — entities may host rules, not infrastructure.

Transaction boundaries, done deliberately

Same charges and emails reach the same destinations; the difference is that a payment-provider hiccup no longer holds a database connection hostage, and mail cannot roll back an order. The transactional-outbox pattern is the standard bridge — covered further in Systems.

Wiring: constructor injection as default

  • Field injection hides the dependency count (14 fields reads as 2 in review) and forces Spring/reflection into unit tests.
  • Constructor injection makes the dependency list a visible API, supports final fields, fails fast on missing beans, and lets tests construct the object with fakes directly. Since Spring Framework 4.3 a single constructor needs no annotation.
  • Lombok-style @RequiredArgsConstructor is fine; just keep the constructor visible in review when the parameter list crosses ~7 — that smell wants Extract Class, not a shorter constructor.
  • Too many constructor parameters is a design signal about the class, not about injection style.

Database, API & Distributed Refactoring

Where behavior preservation ends and coordinated migration begins

✗The one-sentence rule
Refactoring is verified by running tests on one machine in seconds. Database schemas, public APIs and message contracts are shared with systems you cannot run — old and new versions must coexist in production for a while. That coexistence period (compatibility, backfill, dual writes, staged rollout) is migration engineering, and it is what this module teaches.

Database refactoring: expand-and-contract

Deployed schema is state, not code: you cannot atomically change the schema and every reader and writer of it. The safe pattern runs in six steps:

  1. Expand — add the new column/table/index alongside the old shape (nullable, no constraints yet). Additive DDL only; deploy it with Flyway before any code depends on it.
  2. Deploy backward-compatible code — the application writes both shapes (or the new one while still reading the old), so old and new versions of the service run correctly against either schema.
  3. Backfill — migrate existing rows in batches (bounded UPDATE ... WHERE id BETWEEN loops or a migration tool), not one giant transaction that locks a hot table.
  4. Switch reads — after verification, read from the new shape behind a feature flag; compare dual-read results in shadow first.
  5. Verify — row counts, checksums, application metrics, a soak period with dual-write still enabled.
  6. Contract — only when no deployed code version can read the old shape: drop columns, add the deferred constraints. Keep the drop as its own migration, deployed after a safe margin.

The fully worked PostgreSQL/Flyway version of this — renaming cust_nm to customer_name on a live table — is Example J18 in the library.

!Rollback is asymmetric
Expanding is cheap and reversible; contracting is destructive. Before each step ask: “if this goes wrong at 2 a.m., what does rollback look like?” — forward-fix (re-run backfill) is usually the answer after step 3, which is exactly why the verification soak matters.

What the database layer tolerates

API refactoring: contracts evolve, they do not refactor

Internal refactors (rename a private method, extract a service) are invisible to consumers. Public API improvements must be staged so consumers you cannot deploy keep working:

  • Backward-compatible additions — new optional fields, new endpoints — can ship freely (old clients ignore them).
  • Breaking changes — removed fields, renamed properties, changed semantics, stricter validation — need: new version or field alongside old → deprecation headers/docs → consumer migration window with usage telemetry → removal. REST commonly uses path-versioning (/v2/orders); the exact scheme matters less than the discipline.
  • Consumer-driven contract tests (Pact, Spring Cloud Contract) invert verification: each consumer pins the parts of the provider it uses; the provider’s pipeline fails if a change breaks any consumer’s pinned contract. This is the safety net for API refactoring.
  • DTO evolution rule: additive only within a version; anything else is a new version. Tolerant readers (ignore unknown fields) buy enormous freedom — build them from day one.

Distributed systems: coordination replaces verification

A local refactoring is safe because you control every caller at compile time. Across service boundaries you do not: consumers deploy on their own schedules, replay old messages from queues, and cache old shapes. The techniques:

ProblemSafe patternNotes
Message schema change (Kafka topic / RabbitMQ queue)Backward-compatible evolution: add optional fields with defaults; never rename or reuse field meaning; prefer schema registries with compatibility modesOld consumers must be able to read new messages (forward compat) during rollout
Shared database between servicesIntroduce a service-owned API in front of the data; expand-and-contract the readers one service at a timeThe shared DB is the coupling; the fix is ownership, not better queries
Atomic write + publishTransactional outbox: write the event to an outbox table in the same transaction; a relay publishes itKills the dual-write inconsistency class; see the Spring snippet above
Re-delivered / replayed eventsIdempotent consumers: keyed operations, deduplication, upserts instead of blind insertsReplay is a fact of messaging; consumers must tolerate it
Endpoint / event consumers migratingParallel run: old and new consumers active; shadow-verify; then retire oldAvoids synchronized deployments across teams
Service boundary change (move logic between services)Strangler-style staged migration with anti-corruption at the seamThis is architecture migration, not refactoring — see Category I
iWhy more coordination?
In-process, a renamed method breaks compile — you find every caller in seconds. Across services, the “compiler” is production traffic from systems with independent deploy calendars. Every distributed technique above is a substitute for the compiler you lost; the contract tests, compatibility modes and staged rollouts ARE the refactoring tools at this scale.

IDE-Assisted Refactoring

What the machine verifies, what it cannot, and how to drive it safely

Modern IDEs (IntelliJ IDEA first among them; VS Code and Visual Studio capable in their stacks) are the safest way to execute most refactorings: they rewrite every reference mechanically instead of leaving your regex to miss one. The skill is two-part: knowing what the tool guarantees, and knowing where its model of the program ends. The operations below are described conceptually — invoke them from your IDE’s Refactor menu, and check its built-in cheat sheet for the current shortcut on your platform (shortcuts change across versions and OS layouts, so none are claimed here).

The blind spots — always the same three

  1. Reflection and string-based access: Class.forName(...), JSON property names mapped by convention, SpEL expressions, JNDI lookups, annotation scanners. The tool’s model says “no reference”; the runtime disagrees.
  2. Framework magic: Spring wires by annotation scanning — moving a bean to an unscanned package compiles fine and fails at startup; component names can appear in configuration by string.
  3. Other repositories: your IDE sees this repo. A public method renamed is a breaking API change for callers you cannot see.

Driving the IDE safely — a working ritual

  1. Find Usages first. Zero usages of a “used everywhere” method means dynamic access — stop and investigate before touching it.
  2. Tests green before, tests green after, one operation between. The IDE executes the transformation; the tests judge whether it was behavior-preserving.
  3. Read the diff preview the IDE offers before applying — it is a free, high-quality review of the mechanical change.
  4. Run the app or context test (Spring slice) after Move/Extract operations — wiring errors are runtime failures, not compile failures.
  5. Commit per operation. Three renames in one commit with three messages is archaeology later; three commits is bisect heaven.
iVS Code and Visual Studio
VS Code’s Java and C# extensions cover rename, extract and move for their languages (powered by language servers); Visual Studio’s refactorings are similarly strong for the .NET stack. The same blind spots apply everywhere — the language server’s view of “all references” ends at dynamic access and other repositories.
