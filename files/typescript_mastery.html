Introduction to TypeScript

What TypeScript is, what it compiles to — and where types live and die

What TypeScript is

TypeScript is a superset of JavaScript developed by Microsoft that adds a static type system on top of the language. Every valid JavaScript program is (with rare, deliberate exceptions) a valid TypeScript program; TypeScript adds syntax for describing shapes — string, { id: number }, <T> — and a compiler that checks those descriptions before the code ever runs. The checking is static: it happens at compile time, on source code, without executing the program.

The relationship to ECMAScript matters: ECMAScript is the standard that defines JavaScript the runtime language. TypeScript is not a separate runtime — it is a layer of tooling and syntax over ECMAScript. Its compiler also lets you author in tomorrow’s ECMAScript and emit today’s, though today that transpilation role has largely moved to dedicated tools (Babel, esbuild, bundlers) with TypeScript used purely as a checker (tsc --noEmit or tsgo).

The pipeline: where checking happens, where execution happens

Read the diagram left to right. The type level exists only in the first two boxes: source text and compiler analysis. The runtime level is ordinary JavaScript executing in a browser or Node.js. Nothing you write as a type — interface, generic parameter, conditional type — survives into the output. This single fact explains most of the advanced modules in this guide, including the entire discussion of runtime validation boundaries.

What the compiler actually does with your types

● SOURCE — greeting.ts
function greet(name: string): string {
  return `Hello, ${name}!`;
}
const total: number = greet("Ada").length;
console.log(total);
● OUTPUT — greeting.js (erased)
function greet(name) {
  return `Hello, ${name}!`;
}
const total = greet("Ada").length;
console.log(total);

Notice what disappeared: : string annotations, the return type, everything. This is type erasure. A direct consequence follows: TypeScript’s type system gives you no runtime guarantees about data that arrives from outside your program — parsed JSON, HTTP responses, localStorage, user input. An interface describes what a value should look like; it does not inspect what a value actually looks like. That gap is closed by runtime validation, covered in Module 23.

Benefits and honest limitations

Benefits: classes of bugs (typos in property names, wrong argument counts, null dereferences under strictNullChecks) are caught before the code runs; large refactors become mechanical; editor intelligence becomes dramatically better; types serve as always-current documentation; and the type system can encode domain rules so that illegal states fail to compile.

Limitations: TypeScript cannot check what it cannot see — untrusted runtime data, dynamic eval tricks, or library behavior behind loose any typings. Heavy type-level programming can slow builds and confuse teammates. And a type error is not always a bug, nor is the absence of errors the absence of bugs: logic errors live happily inside well-typed code.

×The three boundaries to burn in now
  • TypeScript does not replace JavaScript at runtime — it produces and then supervises JavaScript.
  • Type annotations are removed during compilation — they cost nothing at runtime and enforce nothing at runtime.
  • Static checking does not automatically validate untrusted data — JSON.parse returns any-like trust that must be earned back with validation.

Knowledge check

A teammate says “TypeScript catches bugs before runtime, so we don’t need input validation on our API anymore.” What is wrong with that?

TypeScript checks the source code you wrote, not the data your program receives. An HTTP client can send {"id": "abc"} no matter what your interface User { id: number } says — the interface is erased from the compiled output and never inspects incoming bytes. Validation must happen at runtime (hand-written guards or a schema library like Zod, see Module 23).

Why can a program type-check cleanly and still crash at runtime?

Because checking is static and conservative. Type assertions (as) can lie, any disables checking entirely, external data can violate assumptions, and logic errors (wrong formula, wrong order of operations) are invisible to a type system that only sees shapes.

Exercises

  1. Write a small .ts file with one typed function and one deliberate type error; compile it with npx tsc, read the diagnostic, then fix it and inspect the emitted .js to see the annotations vanish.
  2. Paste any JavaScript file you own into the TypeScript Playground, turn on strict, and catalog what the compiler finds.

Environment and Tooling

tsc, tsconfig, VS Code, bundlers, linting and testing — the working setup

Prerequisites and installation

TypeScript runs on Node.js. You need Node installed (any current LTS line), and then the compiler as a project-local development dependency — not a global install:

!Global vs project-local, and why teams pin the version
A global typescript install gives every project on the machine the same compiler — which is exactly what you do not want. Different projects need different compiler versions, and a version mismatch between machines produces “works on my laptop” diagnostics. Installing with --save-dev records the version in package.json + package-lock.json, and npx tsc then always runs the pinned project version. CI, every teammate and your editor all agree.

The project shape

A typical layout separates source from output, because compiled artifacts should never mix with authored files:

Editor experience and diagnostics

VS Code ships with TypeScript support built in and is the reference editor: inline squiggles for errors, quick-fixes, hover types, “Go to Definition” across files, and automatic import acquisition. One trap: VS Code bundles its own TS language service version, which can differ from your project’s pinned compiler — select the workspace version via the editor’s TypeScript version picker so diagnostics match tsc. Compiler diagnostics here are real diagnostics from the language service; the same numbers (TS2322 and friends) appear in CI builds.

Two files connect errors in dist/ back to your source: source maps (sourceMap: true) map emitted positions to original positions for debuggers, and declaration files (declaration: true) emit a .d.ts describing your module’s public types so other TypeScript projects can consume your library without seeing its source.

Build tools: Vite and friends

In modern applications, tsc usually no longer emits the shipped JavaScript. The split of labor looks like this:

  • Vite (and webpack, esbuild, Turbopack) transform and bundle modules, using esbuild/swc to strip types instantly.
  • tsc --noEmit (or a type-aware task in the build pipeline) performs the actual type checking, because bundlers do not check types.
  • tsx or ts-node run TypeScript directly in development scripts without a build step.

Linting and testing

ESLint with typescript-eslint layers code-quality rules on top of compiler checks — the compiler answers “is this well-typed?”, the linter answers “is this well-written?”. Keep the concerns separate: do not fight the compiler with lint suppressions. For testing, Vitest and Jest both run TypeScript via esbuild/babel transforms; type-check tests in CI with tsc --noEmit covering the test files too, because the test runner itself will silently skip type errors.

★The zero-install laboratory
The TypeScript Playground runs the real compiler in your browser with configurable strictness and target — ideal for the exercises in this guide when you do not want a project. Every code block here is copyable; paste it into the Playground to see genuine compiler behavior.

Knowledge check

Why does vite dev not show type errors even when your file has them?

Vite uses esbuild (or swc) to strip types, not check them — stripping is near-instant, checking is not. Type errors surface from the editor’s language service and from the explicit tsc -b/tsc --noEmit step in the build script. If you remove the check step, nothing ever catches them.

What breaks if two developers on a team use different TypeScript major versions?

Diagnostics and inferred types can differ, so code that errors on one machine passes on another; library typings generated for one version may not parse under another; and lockfile discipline is undermined. Pinning the version via devDependencies and running npx tsc fixes the compiler for everyone, including CI.

Exercises

  1. Set up a scratch project: npm init -y, install TypeScript locally, tsc --init, then deliberately break a type and observe the same diagnostic in VS Code and in npx tsc.
  2. Configure a build script that type-checks before bundling, and confirm that removing the check step lets a type error silently ship.

Type Annotations and Basic Types

Primitives, the special four — any, unknown, never, void — and how widening works

Annotations and inference

A type annotation explicitly states a value’s type; inference lets the compiler derive it. The professional default is: annotate the boundaries, infer the locals. Function parameters (a boundary you control) get annotations; a variable initialized from an expression usually does not need one.

The primitive vocabulary

any versus unknown — the safety hinge

any says “skip checking here”, and the skip is contagious: operations on any produce any, so one untyped edge poisons everything downstream. unknown says “this could be anything, so prove what it is before touching it”. The compiler enforces that proof — you must narrow (Module 08) before use.

● BEFORE — any: the hole widens
const data: any = JSON.parse(raw);
data.user.address.zip.toFixed();
// compiles. crashes at runtime if anything
// in that chain is missing or not a number
● AFTER — unknown: proof required
const data: unknown = JSON.parse(raw);
if (isUserResponse(data)) {      // guard narrows
  data.user.address.zip.toFixed();
} else {
  // handle malformed input — compiler
  // forces you to think about it
}
iRule of thumb
Accept unknown at boundaries (parsed JSON, external APIs, event payloads), narrow to concrete types, and keep any for controlled, commented exceptions — usually during a migration. The strict compiler flag noImplicitAny (part of strict) turns silent implicit any into an error so the hole can never open by accident.

void versus never

void describes a function whose return value should be ignored — it exists and is usually undefined. never describes something that cannot occur: a function that always throws or never returns, or a variable that can hold no value at all. They are not interchangeable:

Add { kind: "triangle"; base: number; height: number } to Shape and the default branch stops compiling — the compiler tells you a case is unhandled. This pattern (and why never accepts only never) is developed fully in Module 07.

Literal types and widening

A literal type is a type with exactly one value. let mode = "read" infers string — the literal widens because let permits reassignment. Contexts that expect a literal (a parameter typed "read" | "write") re-narrow it. as const freezes whole structures into literals (Module 20). Widening is invisible until it bites:

Knowledge check

Why is unknown safer than any if they both mean “could be anything”?

Because of what you may do with them. On any, every operation is allowed and the result is any — errors propagate silently. On unknown, almost nothing is allowed until you narrow the value with checks; the compiler forces the proof. Same domain of values, opposite enforcement policy.

A function returns never. Can a caller assign its result to a variable and use it?

The call itself does not return, so the assignment only happens on paths that never complete. That is exactly why never is assignable to every type — a value that cannot exist is safe anywhere — and why assertion functions that throw use it in signatures.

Variables, Arrays, Tuples and Objects

Modeling data: arrays, tuples, object shapes, readonly and the excess-property trap

Arrays and readonly arrays

readonly T[] prevents mutation through that reference (assignment of the array itself is still possible unless the variable is also const — two independent locks). Prefer ReadonlyArray<T> on function parameters when a function should only read; it documents intent and catches accidental mutation.

Tuples: fixed-length, positionally typed

!Tuple abuse smells
Tuples shine for pairs, coordinates and function returns ([value, error]). A tuple past three or four elements, or one whose positions carry unrelated meaning, is an object waiting to be written — named fields age better than positions.

Object types: the everyday workhorse

Optional versus | undefined

description?: string means the property may be missing or present as string. Under exactOptionalPropertyTypes (Module 22), assigning undefined explicitly to it becomes an error — “absent” and “present but undefined” are distinguished. Without the flag, description?: string and description: string | undefined accept nearly the same values; the difference is whether the key may be entirely absent.

Index signatures and record-style data

×Index signatures disable excess-property safety
An index signature says “any key of this type maps to this value type”, so typos like usersById["usr-1"] pass silently. For fixed vocabularies prefer literal key unions (Record<"admin"|"editor", ...>) or plain object types; reach for index signatures only when keys are genuinely dynamic.

Excess property checks: the fresh-literal rule

Structural typing (Module 06) says an object with extra properties is still assignable to a smaller type. TypeScript carves out one exception: object literals written directly at the assignment site are checked for unknown properties. This is why the same object behaves differently assigned via a variable:

The rule exists to catch typos (prot vs port) exactly where they are most common. It is not an inconsistency to memorize — it is deliberate hygiene for literals.

Knowledge check

Why does push fail on readonly number[] while arr[0] = 1 also fails, yet reassigning the whole variable may not?

readonly T[] locks the reference’s view: no mutating members exist on it. If the variable is declared const, the binding is also fixed. But a let x: readonly number[] can be pointed at a different array — readonly on the type is about mutation through that reference, const is about the binding. Two orthogonal axes.

You need a settings object where any string key holds a number, plus one mandatory version field. How do you type it?

Combine a fixed member with an index signature: type Settings = { version: number; [key: string]: number }. The known key is checked by name; everything else must be a number. If only certain keys are legal, use a literal-keyed Record instead and drop the index signature.

Exercises

  1. Model an API response envelope: { status: number; headers: Record<string, string>; body: unknown }, then make it readonly at the top level and note what operations disappear.
  2. Convert a tuple-based [name, email, age] into a named object type and list the call sites that become safer.

Functions and Function Types

The most important type in JavaScript, typed properly

Every way to type a function

Parameter styles compose: optional parameters (prefix?: string) must come after required ones; default values both make a parameter optional and fix its type from the default; rest parameters (...values: number[]) collect the tail into an array. The classic signature is “required, defaulted/optional, rest” in that order.

Contextual typing

When a function is passed where a signature is expected, TypeScript back-fills parameter types from the expectation — you do not annotate them again:

Overloads versus union parameters

Function overloads let one function expose multiple call signatures. TypeScript picks the first matching overload; the implementation signature stays hidden. The honest engineering guidance: a union parameter is simpler and usually enough; overloads earn their keep when different argument shapes produce different return types or when defaults/optionality differ structurally per shape:

● SUFFICIENT — union parameter
function delay(ms: number | string): Promise<void> {
  const n = typeof ms === "number"
    ? ms
    : Number(ms.endsWith("ms") ? ms.slice(0, -2) : ms);
  return new Promise(r => setTimeout(r, n));
}
● EARNED — overload with type change
function query<T>(key: string): Promise<T | undefined>;
function query<T>(key: string, fallback: T): Promise<T>;
function query<T>(key: string, fallback?: T) {
  // implementation signature is not callable
  // from outside — callers see the two above
  return cache.has(key)
    ? Promise.resolve(cache.get(key) as T | undefined)
    : Promise.resolve(fallback);
}

Function compatibility (a first look)

Assigning a function to a signature type succeeds when the function can handle at least what the signature demands: it may accept fewer or equivalent parameters (extra caller arguments are ignored) and must return something assignable to the expected return. This “functions are compatible if they can stand in” rule is structural typing applied to call signatures — the full variance story (and why parameter checking runs contravariantly under strictFunctionTypes) lands in Module 19.

★API design with callbacks
Type callbacks once, name them, and reuse: type AsyncCallback<T> = (err: Error | null, value?: T) => void. Every hand-written inline (err, value) => ... annotation is a place a signature can drift. Sorting comparators, event maps and middleware chains all become reviewable when the callback types are named artifacts.

Knowledge check

Why can a (message: string) => void accept a function taking zero parameters, but not one taking two?

Compatibility asks: can the substitute survive every call the type allows? The type promises calls with exactly one argument; a zero-parameter function ignores it — safe. A two-parameter function needs a second argument the caller never provides — it would read undefined at runtime, unsafe, so the compiler refuses.

When do you actually need overloads instead of a union parameter?

When the relationship between arguments and the result changes per shape — e.g. create(x: string): A versus create(x: number): B — or when optionality patterns differ per shape. If every shape funnels into the same return type, unions plus narrowing inside the function are simpler and infer just as well.

Exercises

  1. Write groupBy<T>(items: T[], keyFn: (item: T) => string): Record<string, T[]> using contextual typing — no annotations inside the callback.
  2. Design an event-emitter on(name: string, handler: (payload: unknown) => void): () => void whose return value un-registers the handler; then tighten the payload type with generics.

Type Aliases, Interfaces and Structural Typing

How TypeScript decides what fits where — and interface vs type without dogma

Structural typing: the ground rule

TypeScript is structurally typed: a value is assignable to a type when it has the members the type requires — not when it declares a relationship. This is “duck typing, checked statically”. Where a nominally-typed language (Java, C#) asks “does this class say it implements that interface?”, TypeScript asks “does this value’s shape satisfy that interface?”

Assignability is recursive and computed member by member: object fields must be assignable, function members must be compatible (Module 19), arrays elementwise. When an assignment fails, the compiler walks the structure and reports the first offending member — reading those long error paths is a trainable skill (Lab I drills it).

Aliases and interfaces: capabilities, side by side

Capabilitytype aliasinterface
Object shapes✓✓
Unions, intersections, primitives, tuples, conditional types✓✗

Neither is universally superior. A pragmatic house rule many teams adopt: use interface for object shapes that may be extended or augmented (especially public library surfaces and DOM/module augmentation), use type for unions, intersections, tuples, function types and every type-level computation (Modules 13–18 are type territory by necessity). Consistency within a codebase matters more than the choice itself.

Extension, intersection and re-opening

!Intersections can build impossible types silently
type A = { kind: "circle" } & { kind: "square" } compiles — and describes an uninhabited type, since kind cannot be both literals at once. Nothing warns you. Intersections are best for combining disjoint fields; when discriminants overlap, what you almost always want is a union (Module 07), not an intersection.

Design exercise: users, admins, API data

Notice the decisions embedded in shapes: readonly marks identity as immutable; the wire format is a separate type that documents reality rather than wishing it were the domain model; the DTO derivation (via Omit + intersection) lives in one place, so a wire change breaks exactly one line.

Knowledge check

Why does interface support declaration merging while type does not?

Deliberate design: merging is what makes augmentation possible — adding members to Window or to a library’s exported interface without touching its source. A type alias is a single immutable binding; two aliases with one name are simply a redeclaration error. If you do not want accidental merging, a type is the safer fence.

Structural typing means an object with extra properties is assignable — so why did Module 04’s excess-property error happen?

Excess property checking applies only to fresh object literals at the assignment site — a hygiene exception layered on top of structural assignability to catch typos exactly where they are typed. Route the same data through a variable and pure structural rules apply again. Both rules coexist by intent.

Exercises

  1. Model Product, DigitalProduct extends Product (with downloadUrl) and PhysicalProduct extends Product (with weightKg), then replace the two extensions with a discriminated union and argue which fits an order line better.
  2. Define a wire type and a domain type for a newsletter subscriber, and write the mapping function between them — no shared fields should be retyped by hand twice.

Union Types, Intersection Types and Literal Types

Modeling state so that invalid data is hard to represent

Unions and literals: the vocabulary of state

The membership rule: on a union value, you may only use what every member provides. That constraint is the engine of safety — to do anything member-specific you must narrow (Module 08), and the compiler tracks you doing it.

Discriminated (tagged) unions

A discriminated union gives every member a shared literal field — the discriminant — so a single check splits the union cleanly. This one pattern is the highest-value modeling tool in TypeScript:

Make invalid states unrepresentable

Contrast the two modeling styles for a payment flow. The optional-fields version permits twenty-four shape combinations, most of them nonsense — a loading state with an error, success without a receipt. The union version permits exactly three, all meaningful:

● BEFORE — booleans + optionals
type PaymentState = {
  status: string;          // typo-prone open string
  isLoading: boolean;
  error?: string;
  receiptId?: string;
  retries: number;
};
// legal nonsense: status:"ok", isLoading:true, error set
// legal nonsense: status:"error" with no message
● AFTER — one state, one member
type PaymentState =
  | { state: "idle" }
  | { state: "processing"; attempt: number }
  | { state: "failed"; error: string; canRetry: boolean }
  | { state: "completed"; receiptId: string };
// 4 legal states. "processing with receipt": cannot be written.

Exhaustiveness with never

When a switch covers every discriminant, the default branch’s value can only be never. Assign it to never and the compiler enforces future coverage for free:

Intersections: composition, not state

Where unions say “one of”, intersections say “all of”. They are for combining capabilities (Serializable & Loggable), not for modeling alternatives — and never for overlapping discriminants. The classic everyday intersection is type X = A & B where A and B bring disjoint fields; the classic anti-pattern is intersecting two shapes that both define type or kind with different literals.

Optional properties versus union states — the decision rule

★Choose by asking “when B is present, must A be absent?”
If fields are independent (a user may have both a phone and a fax), optionals model them fine. If field groups are mutually exclusive or travel together (receipt only exists when completed; attempt only while processing), a discriminated union is the honest model. Optional-everything types let the compiler see 2n shapes; the union shows it exactly n.

Knowledge check

Why is { success: true; data: T } | { success: false; error: string } better than { success: boolean; data?: T; error?: string }?

The union ties each payload to its flag: data exists only when success is true, error only when it is false. After one if (r.success) check, both payload accesses are proven safe. The boolean+optionals version leaves the compiler unable to know which payload applies, so every access needs its own guard or ! — and nonsense combinations compile.

What does assigning the switch default value to never actually verify?

That the only way to reach the default is with a value that has no type — i.e., that every union member was already handled above. When someone adds a member, the default value suddenly has a real type, which is not assignable to never, and the omission becomes a compile error at the exact spot handling decisions live.

Generics Fundamentals

Type parameters, inference, and why generics preserve relationships

Start from the identity function

Unpack the three ideas the signature carries:

  • What T is: a type parameter — a placeholder filled per call. The caller decides the type, once, and the whole function body is checked against that decision.
  • How inference works: at each call site, TypeScript matches the argument’s type against the parameter pattern T and solves for T. You rarely write identity<number>(...) — the argument is the evidence.
  • Why it beats overloads or any: (value: any) => any loses the connection; identity keeps input and output linked — the return type is the same T the argument provided. That preserved relationship is the entire point of generics.

Where the relationship matters: an API response envelope

● WITHOUT generics — the any slide
function fetchUsers(): Promise<any> {
  return http.get("/users");
}
const users = await fetchUsers();
users.map((u) => u.naem);   // typo compiles;
                              // undefined at runtime
● WITH generics — typed end to end
type ApiResponse<T> = {
  status: number;
  data: T;
  fetchedAt: Date;
};

async function get<T>(url: string): Promise<ApiResponse<T>> {
  const res = await http.get(url);
  return { status: res.status,
           data: res.body as T,          // one honest `as`
           fetchedAt: new Date() };      // at ONE boundary
}

const users = await get<User[]>("/users");
users.data.map((u) => u.naem);  // compile error caught here

Note the discipline in the AFTER version: the as T assertion appears exactly once, at the network boundary, and is justified by an external contract. Downstream code inherits checked types with no further assertions — the shape of good generic API design.

Generic result wrapper — the pattern you will write weekly

iThe mental model
A generic is a function over types exactly as a function is a computation over values. identity<T> takes a type argument and returns it; Outcome<T, E> computes a union from two type arguments. When you read <T>, say “for all T” — the body must be correct for every T, which is precisely why generic code is hard to write but safe to reuse.

Knowledge check

Why does function first(arr: any[]): any lose something first<T>(arr: T[]): T keeps?

The any version forgets the element type: callers of first(names) get any, so downstream operations go unchecked. The generic version captures the relationship “return type = element type of the argument” per call site: first(names) is string, and a typo like .toUppercase() is caught. Generics are about preserving relationships, not avoiding annotations.

When must you write the type argument explicitly, like get<User[]>("/users")?

When there is no argument from which to infer T — here the only parameter is the URL string, and the response type lives in the return position. Inference flows from arguments (and contextual return hints), so generic functions whose type parameter appears only in the return type need explicit instantiation at the call.

Advanced Generics and Constraints

extends bounds, keyof constraints, defaults — and the judgment to stop

Constraints: what T must provide

Walk getProperty slowly, because it concentrates every idea in this module: K extends keyof T says the second argument must be a key of the first argument’s type; inference solves T from the object and K from the key together; and the return T[K] (indexed access, Module 12) is the exact property type. One generic function, zero annotations at the call site, total precision.

Multiple constraints and defaults

!What a constraint does NOT mean
T extends User does not mean “T is exactly User” — it means “T is at least User-shaped”, so T may be User, Admin, or any subtype. Two consequences: (1) inside the body you may only use the User part of T — treating it as exactly User; (2) at the call site, the specific T survives into the signature, so return values keep the caller’s precise type. Constraints widen what the body may do; they never narrow what the caller gets back.

Generic factories and class design

When NOT to reach for generics

×Excessive genericity is a maintainability bug
Each type parameter multiplies the space the reader must simulate. Heuristics that keep designs honest:
  • No relationship to preserve? A plain parameter type is enough. function parse<T>(s: string): T preserves nothing a caller could not write with one assertion — prefer returning unknown + a guard.
  • Used in exactly one place, once? Inline it. A generic with one call site is indirection without reuse.
  • Three-plus parameters where two are always the same? Give defaults, or collapse them.
  • A union of two shapes does the job? Overloads or a union parameter beat T extends "a" | "b" machinery when the bodies diverge.
The professional question is never “can I make this generic?” — it is “does the caller need the relationship?”

Knowledge check

In size<T extends { length: number }>, can the body call value.toUpperCase() if T happens to be a string?

No — the body sees only the constraint, and the constraint promises merely length: number. The body must be correct for every T that satisfies the bound, including [1,2,3] and { length: 2 }. If a method genuinely requires strings, constrain to string — or handle members via narrowing after a runtime check.

Compare <T extends "GET" | "POST"> with a plain method: "GET" | "POST" parameter. When is the generic version justified?

The plain union parameter is simpler and should be the default: the value is checked, the body narrows normally. The generic earns its place only when the specific literal must flow somewhere — typically the return type, e.g. function route<M extends Method>(m: M): Handler<M> so route("GET") returns a GET-typed handler. No downstream dependency on the literal → no generic.

Advanced Type Compatibility and Variance

Why some assignments surprise you — the rules behind assignability

Assignability: the question behind every error

TypeScript’s core judgment is a single question, asked millions of times per build: is a value of type S assignable to a variable of type T? (S → T). Structural rules make it recursive: object members must be assignable, function signatures must be compatible, arrays elementwise, generics after instantiation. Variance is the vocabulary for how a position inside a compound type reacts when its own type argument moves.

The two directions, with the classic examples

The mnemonic engineers actually use: outputs narrow, inputs widen. A producer may over-deliver (more specific output); a consumer must over-accept (more general input). Getting this backwards is the single most common “the compiler is wrong” moment — and it is not wrong.

strictFunctionTypes and the bivariance caveat

!Method parameters are checked bivariantly — a deliberate hole
Under strictFunctionTypes, function-type parameters are checked contravariantly (the sound rule), but parameters of methods declared with method syntax (class C { on(e: E): void } or interface I { on(e: E): void }) remain bivariant — assignable in either direction — for compatibility with the enormous amount of existing JavaScript built on subclassing (DOM events, Array, and friends). Declaring the same member as a property with a function type (interface I { on: (e: E) => void }) opts that member into strict contravariance. Teams that want maximal soundness standardize on property-style declarations for callback-heavy interfaces.

Readonly, arrays, and generics in practice

TypeScript 4.7 added variance annotations (in, out, in out) for generic type parameters, letting library authors declare intent explicitly — the compiler then verifies it: interface Repo<in out Entity> asserts invariance and fails to compile if the usage contradicts it. Annotations do not change behavior; they turn implicit, computed variance into a checked contract.

Textbook variance is about sound subtyping. Knowledge check

Why is (e: PuppyEvent) => void rejected where (e: DogEvent) => void is required?

Callers may invoke the handler with any DogEvent, including plain dogs that are not puppies. A handler that can only process PuppyEvent would receive values it cannot handle — so parameter positions must accept at least what the target promises (contravariance). Accepting more (AnimalEvent) is safe: it over-promises tolerance.

Your event-bus API uses method syntax and a reviewer flags it. What is the issue and the fix?

Method-syntax parameters are checked bivariantly, so a handler expecting a subtype of the event can be registered without error — and then receive a broader event at runtime. Switching the interface to property syntax (on: (e: E) => void) makes the parameter contravariant under strictFunctionTypes, and the unsound registration becomes a compile error.

iNamespaces are legacy, with two survivors

Augmentation: adding to what you cannot edit

Augmentation is structural typing’s escape hatch: the original declaration merges with yours. Power tool, sharp edges: augmenting a library you do not own couples you to its internals — when the library changes, your augmentation may silently describe a lie. Most popular JavaScript libraries have community types on DefinitelyTyped, installed as npm i -D @types/library-name and picked up automatically. Knowledge check

What breaks if you import a type with a regular (non-type) import and then delete the module’s implementation?

With verbatimModuleSyntax or isolatedModules (the norm in bundler projects), the import is emitted verbatim and the bundler fails at runtime/build because the runtime module no longer exports that name. A import type is erased entirely, so it can never produce a broken runtime import — which is exactly why bundler-era configs encourage type-only imports for types.

It is an ambient declaration: it tells the compiler “this module exists in the runtime world with this shape”. You are supplying type information for a JavaScript fact that already exists.

Knowledge check

In the fluent builder, why does build declare this: HttpRequestBuilder<"url", "method">?

It restricts which receivers may call the method: build only exists on builders whose accumulated type parameters prove both required values were provided. A builder missing either requirement has that method missing from its type — so the incomplete chain fails to compile at the call site, before any runtime null-check would fire.

Why does the state machine’s transition use Extract<Event, { type: keyof OrderMachine[S]["on"] }>?

To narrow the legal events to those declared for the current state S: keyof OrderMachine[S]["on"] is that state’s transition table keys, and Extract filters the global event union down to matching members. The result: “ship” from “draft” is not a runtime error check away — it does not type-check.

Exercises

  1. Extend the fluent builder with withBody(data: unknown) required only when method is POST (conditional requirements — project 21’s extension, done as a study).
  2. Add a timeout state to the order machine with legal transitions from submitted, and verify the two illegal-transition examples still fail to compile.
