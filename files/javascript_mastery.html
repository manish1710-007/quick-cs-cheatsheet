Execution Contexts, Call Stack & Memory

How the JavaScript engine actually parses, allocates and executes code line by line

Two phases of every Execution Context

Whenever JavaScript runs a script or invokes a function, the engine creates an Execution Context (EC) and pushes it onto the Call Stack. Every EC runs in two distinct phases:

  • Creation Phase (Memory Allocation). The engine scans declarations in the scope before running line 1: function declarations are stored with their full body, var bindings are initialized to undefined, let/const bindings are allocated in an uninitialized state (TDZ), and the this binding + outer lexical reference are wired.
  • Execution Phase (Code Evaluation). Code runs top-to-bottom. Assignments fill bindings, expressions evaluate, and every function call pushes a brand-new Function Execution Context onto the Call Stack.

    • Call Stack vs Memory Heap

    Call Stack (LIFO)Execution Context frames · primitives & refs
    Memory HeapObjects, Arrays, Functions, Closure Envs
    function returns → stack frame popped · heap objects live while reachable

    Because JavaScript has one Call Stack (single-threaded execution per realm/worker), only one frame executes at any instant. Deep or unbounded recursion exhausts stack memory and throws RangeError: Maximum call stack size exceeded. Objects, arrays, functions, and captured closure environments live on the Heap; stack variables hold references (pointers) to them.

    Check yourself — execution contexts

    Q1. Why does passing an object into a function allow mutating its properties, yet reassigning the parameter variable does not affect the caller?

    JavaScript is strictly pass-by-value, where the value for objects is the reference. Mutating obj.x = 1 follows the reference to the shared heap object; reassigning obj = {} only overwrites the local parameter slot in the callee’s stack frame.

    Scope, Lexical Environments & Hoisting

    Lexical scoping, var vs let vs const, Temporal Dead Zone, and the Scope Chain

    Lexical Scope (Static Scope)

    JavaScript uses lexical scoping: where a variable is accessible is determined by where it is written in source code (author-time), never by where a function is called (runtime). Every block or function creates a Lexical Environment consisting of an Environment Record (local bindings) and an Outer Reference pointing to its enclosing Lexical Environment. Identifier resolution walks this Scope Chain outward until found or throws ReferenceError.

    var vs let vs const

    Featurevarletconst
    ScopeFunction (or Global)Block { ... }Block { ... }
    HoistingHoisted & initialized to undefinedHoisted, uninitialized (TDZ)Hoisted, uninitialized (TDZ)
    Re-declarationAllowed in same scopeSyntaxErrorSyntaxError
    Re-assignmentAllowedAllowedTypeError (binding is immutable; object contents remain mutable)
    Global object propertyCreates window.x (sloppy script)Does not attach to windowDoes not attach to window

    Hoisting & the Temporal Dead Zone (TDZ)

    “Hoisting” is not code moving physically to the top — it is the Creation Phase allocating bindings before execution starts. For let and const, the gap between entering the block and reaching the declaration line is the Temporal Dead Zone (TDZ). Touching the variable inside the TDZ throws a ReferenceError.

    !Common misconception
    People often say “let and const aren’t hoisted.” They are hoisted — the block above proves it: if inner let x weren’t registered in the Creation Phase, console.log(x) would have walked up and printed "outer". Instead it throws a TDZ ReferenceError.

    Closures Deep Dive

    [[Environment]], live binding capture, loop traps, private state, memoization & memory retention

    What a closure actually is

    Closure invariantflagship
    Closure = Function Code + [[Environment]] (pointer to birth Lexical Environment)

    A closure is created when a function remembers and continues to access its lexical scope even when executed outside that scope. Crucially, closures capture live variable bindings (references), not frozen snapshots of values.

    When an outer function finishes executing, its stack frame pops — yet its Lexical Environment survives on the Heap as long as any returned or registered inner function still holds a reference to it via its internal [[Environment]] slot. Trace this live in Lab B: Closure Visualizer.

    The classic loop trap: var vs let

    Production patterns powered by closures

    • Function factories & currying: const multiplyBy = a => b => a * b;
    • Once / rate-limiting (debounce & throttle): storing timerId or called flag privately across invocations.
    • Memoization: keeping a private Map cache across calls.
    • React Hooks & stale closures: a useEffect callback closes over the state binding from the render in which it was created. Omitting a dependency leaves the effect reading a stale closure; functional updates (setCount(c => c + 1)) or useRef break the staleness.

    Memory retention & accidental leaks

    !Shared Scope Context Trap in V8
    In engines like V8, all inner functions created inside the same outer function share one heap Context object for variables captured by any of them. If inner function A captures a 50 MB buffer and inner function B is kept alive long-term (e.g. as an event listener), B can unintentionally keep the 50 MB buffer alive even if B never references it! Always null out huge local references or split scopes when creating long-lived closures.
    Check yourself — closures

    Q1. Does a closure freeze the value of a variable at creation time?

    No — it captures the binding. If the outer scope mutates x after the inner function is created, calling the inner function later sees the updated value of x.

    Q2. Why did for (let j = 0; j < 3; j++) fix the setTimeout bug?

    The ECMAScript spec explicitly creates a brand-new per-iteration Lexical Environment for let loop variables and copies the previous iteration’s value into it, so each callback closes over its own j.

    this Binding & Call-Site Rules

    The 4 rules, strict precedence order, call/apply/bind, and arrow function lexical this

    Unlike lexical scope (determined where a function is written), this for regular functions is dynamically bound at the call site — how the function is invoked. Check the four rules in exact precedence order (highest to lowest):

    PriorityRuleCall-site shapeWhat this becomes
    1 (Highest)new bindingnew Fn()The newly constructed object
    2Explicit bindingfn.call(obj), fn.apply(obj), fn.bind(obj)()obj (hard-bound via bind cannot be overridden by call/apply, only by new)
    3Implicit bindingobj.fn()The immediate owning object to the left of the dot (obj)
    4 (Lowest)Default bindingfn()undefined in strict mode; globalThis (window/global) in sloppy mode

    Arrow functions break the rule (by design)

    Arrow functions (() => {}) have no own this. Instead, they inherit this lexically from the enclosing scope — just like a closure variable! Neither call, apply, nor bind can change an arrow function’s this, and calling new on an arrow function throws TypeError. Test every pattern in Lab D: this Binding Resolver.

    Property Descriptors

A descriptor is either a Data Descriptor (value, writable) or an Accessor Descriptor (get, set), plus enumerable (shows up in for..in / Object.keys) and configurable (can be deleted or reconfigured).

    Prototypes & Prototype Chains

    [[Prototype]], .prototype vs __proto__, delegation, shadowing & Object.create

    Delegation, not copying

    JavaScript does not copy methods onto instances like classical languages do. Instead, every object has an internal link called [[Prototype]] pointing to another object (or null). When you read obj.prop, the engine checks obj’s own properties; if absent, it follows [[Prototype]] hop by hop until it finds prop or hits null (returning undefined).

    const arr = [1, 2]own: 0, 1, length
    Array.prototypemap, filter, push, ...
    Object.prototypetoString, valueOf, ...
    nullend of chain
    arr.[[Prototype]] → Array.prototype.[[Prototype]] → Object.prototype.[[Prototype]] → null

    The #1 confusion: .prototype vs [[Prototype]]

    iMemorize this distinction
    [[Prototype]] (read via Object.getPrototypeOf(obj), legacy obj.__proto__) exists on every object and is the live delegation link used during property lookup.
    Fn.prototype is a regular property that exists only on constructor functions. It is the blueprint object that becomes the [[Prototype]] of instances created via new Fn().

    Walk any lookup hop-by-hop in Lab C: Prototype Chain Lookup Explorer.

    !Never mutate prototypes at runtime
    Calling Object.setPrototypeOf() or assigning __proto__ on an existing object de-optimizes V8’s hidden classes and inline caches for every code path touching that object. Always set prototypes at creation time using Object.create() or class / new.
    Check yourself — prototypes

    Q1. What is Object.getPrototypeOf(Function.prototype) and Object.getPrototypeOf(Object)?

    Object.getPrototypeOf(Function.prototype) === Object.prototype (a prototype object is an object). Meanwhile Object itself is a constructor function, so Object.getPrototypeOf(Object) === Function.prototype!

    Q2. When does writing child.x = 5 NOT shadow a property x on the prototype?

    Two cases: (1) proto.x is marked writable: false (fails silently in sloppy mode, throws TypeError in strict mode), or (2) proto.x is a setter accessor, which gets invoked instead of creating an own property.

    Constructors, new, class & Inheritance

    The 4 exact steps of new, ES6 class desugaring, extends/super, and private #fields

    What the new operator actually does

  • Creates a brand-new empty plain object obj = {}.
  • Links its internal prototype: Object.setPrototypeOf(obj, Constructor.prototype).
  • Calls Constructor.apply(obj, args) with this bound to obj.
  • If the constructor explicitly returns a non-null object/function, returns that; otherwise returns obj.

    • Key differences between class and function constructors: class bodies always run in strict mode, class declarations are not hoisted out of TDZ, methods on the prototype are non-enumerable, and calling a class without new throws a TypeError.

    The Event Loop, Call Stack & Task Queues

    Single-threaded JS, Web APIs, Microtask vs Macrotask queues, rendering, starvation & Node.js phases

    How a single-threaded language does async I/O

    In a typical browser page, JavaScript jobs run to completion on that page's main thread; this does not mean every JavaScript environment has only one thread (Workers, for example, have their own agents). The host runtime coordinates timers, network activity, DOM events and other work. When a callback becomes eligible, the host schedules it through a task source. The event loop coordinates task execution, microtask checkpoints and rendering opportunities; it is not simply one universal FIFO queue of all asynchronous callbacks.

    Call Stacksync JS runs to completion
    Host / Web APIstimers, fetch, DOM, libuv
    task completes → microtask checkpoint → rendering opportunity (when due) → next eligible task
    Microtask Queue (VIP)Promise.then, queueMicrotask, MutationObserver
    Task sourcestimers, user interaction, networking, messaging

    Browser event-loop checkpoints (practical mental model)

  • Run the current task (for example, the initial script, a timer callback or an input event) to completion.
  • Perform a microtask checkpoint: drain queued microtasks, including microtasks added by earlier microtasks, until the queue is empty.
  • Rendering may happen when the browser reaches a rendering opportunity. Animation-frame callbacks run as part of the rendering update before the corresponding paint; rendering is not guaranteed after every task.
  • Select another runnable task from the host's task sources. Do not assume every browser task source shares one global FIFO queue.

    • This is a teaching model for browser event-loop behavior, not a frame-by-frame guarantee. A 60 Hz display has a nominal ~16.7 ms frame interval, but actual rendering cadence depends on the browser, display, visibility state and workload.

    Step through this and 4 trickier async traces interactively in Lab A: Event Loop & Microtask Simulator.

    Browser vs Node.js Event Loop

    DetailBrowserNode.js (libuv)
    Macrotask phasesSingle conceptual task queue (multiple task sources)6 ordered phases: timers → pending → idle/prepare → poll → check (setImmediate) → close
    Highest-priority microtaskPromise.then / queueMicrotask (FIFO)process.nextTick() runs before Promise microtasks!
    setTimeout(fn, 0) vs setImmediateNo setImmediateNon-deterministic at top-level; inside an I/O callback, setImmediate ALWAYS runs first
    !Microtask Starvation
    A microtask that continually queues another microtask can prevent the microtask checkpoint from finishing. In a browser this can starve rendering and later tasks (including timers), without growing the call stack indefinitely. Break long work into tasks or yield with a suitable scheduler API such as scheduler.yield() where supported, with a task-based fallback such as setTimeout.

    Callbacks, Inversion of Control & Zalgo

    Why callbacks failed at scale — and the exact trust problems Promises were invented to solve

    Callback hell (“pyramid of doom”) is merely cosmetic. The real engineering flaw of callbacks is Inversion of Control: when you pass your continuation cb to a third-party function, you trust it to call cb exactly once, asynchronously, with errors properly forwarded. If it calls cb twice (double-charging a credit card), never calls it, or calls it synchronously on cache hit and asynchronously on cache miss (“releasing Zalgo”), your state breaks unpredictably.

    Promises Inside Out

    State machine, immutability, chaining, error propagation & combinators (all, allSettled, race, any)

    The Promise State Machine

    Promise guaranteesflagship
    pending → fulfilled(value) OR pending → rejected(reason) [immutable once settled]

    A Promise settles at most once. Calling resolve or reject a second time is silently ignored. Every .then / .catch / .finally handler is guaranteed to run asynchronously in the Microtask Queue, even if the Promise is already settled, and always returns a brand-new Promise.

    Chaining & Error Propagation Rules

    • Returning a value from .then() fulfills the next Promise with that value.
    • Returning a Promise (or thenable) from .then() automatically flattens/adopts its state — the chain waits for it.
    • Throwing an error (synchronously inside the executor or inside .then()) rejects the returned Promise and skips downstream .then handlers until the next .catch().
    • Recovering in .catch(): returning a normal value from .catch() switches the chain back to fulfilled!
    • .finally(fn) receives no arguments and passes through the previous fulfillment value or rejection reason unchanged (unless fn itself throws or returns a rejected Promise).

    The Four Promise Combinators

    CombinatorShort-circuits when?Resolves toRejects with
    Promise.all(iter)First rejectionArray of values (in input order)First rejection reason
    Promise.allSettled(iter)NeverArray of {status, value|reason}Never rejects
    Promise.race(iter)First settled (fulfill OR reject)First fulfilled valueFirst rejection reason
    Promise.any(iter)First fulfillmentFirst fulfilled valueAggregateError (if ALL reject)

    Test all four combinators with custom timings and failures in Lab E: Promise Combinator Lab.

    !Note on fetch()
    fetch() only rejects on network failure or abort — an HTTP 404 or 500 still fulfills with res.ok === false! Always check if (!res.ok) throw new Error(res.status).

    async / await & Production Async Patterns

    How await pauses via microtasks, sequential vs concurrent traps, AbortController, retry & concurrency pools

    What async / await actually does

    An async function always returns a Promise. When execution hits await expr, it evaluates expr synchronously, wraps it in Promise.resolve(expr), suspends the function, pops its frame off the Call Stack, and schedules the remainder of the function body as a microtask once that Promise settles. Everything before the first await runs synchronously!

    The #1 performance mistake: Accidental Serialization

    !Never use async callbacks inside Array.prototype.forEach
    forEach ignores returned Promises and does not await them. Use for...of when you want sequential execution, or await Promise.all(items.map(async x => ...)) when you want concurrent execution.

    Types, Coercion & Equality Semantics

    7 primitives + Object, == vs === vs Object.is, ToPrimitive, truthy/falsy & typeof quirks

    JavaScript has 7 primitive types (undefined, null, boolean, number, bigint, string, symbol) and 1 reference type (object, which includes functions and arrays). Famous legacy quirk: typeof null === "object" (a 1995 type-tag bug kept for backwards compatibility).

    Iterators, Generators & Modern Collections

    Symbol.iterator, lazy yield sequences, Map/Set vs WeakMap/WeakSet

    Any object implementing [Symbol.iterator]() returning { next() { return { value, done }; } } works with for...of, spread [...x], and destructuring. Generators (function*) automate this state machine via yield, enabling lazy infinite streams and pull-based pipelines. WeakMap / WeakSet hold weak references to object keys so entries are garbage-collected automatically when the key has no other references — ideal for private metadata or DOM-node caches without memory leaks.

    Memory Management, Garbage Collection & V8 Shapes

    Reachability, generational GC, the 4 classic leaks, Hidden Classes & Inline Caches

    Garbage Collection & The 4 Classic JS Memory Leaks

    Garbage collectors reclaim objects that are no longer reachable from roots. Modern V8 uses generational collection and several complementary strategies; names and details vary by engine version. In broad terms, young objects are collected frequently, while longer-lived objects may be promoted and handled by older-generation collectors. A memory leak is often an object that remains reachable even though the application no longer needs it:

    • Forgotten timers / listeners: setInterval or addEventListener never cleaned up on unmount.
    • Detached DOM nodes: removing an element from the DOM while a JS array/map still holds a reference to it.
    • Accidental globals: assigning to undeclared variables in sloppy mode (leaked = bigArray).
    • Unbounded caches & closure retention: Maps that grow forever (consider an eviction policy such as LRU). A closure can keep referenced state reachable; engines may optimize captured environments, so do not assume every outer local is retained.

    V8 Hidden Classes (Shapes / Maps)

    V8 uses internal object shapes (often called Maps or hidden classes) and inline caches to optimize property access. Objects created with consistent layouts can help an engine reuse shape information, while frequent structural changes may make optimization harder. These are V8 implementation details, not ECMAScript guarantees: avoid treating a particular property order or the cost of delete obj.prop as a universal performance rule. Measure real workloads before changing object design.

    Debugging, Security & Production Pitfalls

    Prototype pollution, floating-point traps, async race conditions & structuredClone

    • Prototype Pollution: Naive recursive merge functions copying untrusted JSON keys like "__proto__" or "constructor" can inject properties onto Object.prototype globally! Guard with Object.create(null), Map, or rejecting __proto__/constructor/prototype keys.
    • IEEE-754 Floating Point: 0.1 + 0.2 === 0.30000000000000004. For money/INR calculations, always store integer paise (smallest unit) or use integer arithmetic, never binary floats.
    • Stale Async Responses (UI Race Conditions): User types “a” then “ab”; request 1 returns after request 2 and overwrites newer state. Fix by cancelling previous requests with AbortController or tracking a monotonically increasing request ID.
    • Deep Cloning: Prefer native structuredClone(obj) over JSON.parse(JSON.stringify(obj)) (which drops Date, Map, Set, undefined, and crashes on circular refs).
